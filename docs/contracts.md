# easl contracts

Interfaces every slice builds against. The API wire format and object model live in `schema/easl-api.json`; this file covers what the schema can't express: sockets, environment, the Swift tile protocol, the mention context format, and ownership rules.

## Sockets

| Socket | Path | Speaks | Owner |
| --- | --- | --- | --- |
| easl API | `~/Library/Application Support/Easl/easl.sock` | `schema/easl-api.json` | App |
| cmux browser subset | `~/Library/Application Support/Easl/cmux.sock` | cmux v2 JSON lines, browser methods only | App (isolated, deletable) |

Both sockets are created with mode `0600`. The cmux subset lives on its own socket so it never shares method names with our API and can be removed in one step.

The easl API checks every request's params, and each `object.batch` op's, against the method's schema before it runs (`ApiRouter.checkParams`, from `ApiParams`, which `scripts/gen-clients.ts` generates from the schema): a param the schema doesn't list, or a required one missing (or `null`), is `invalid_params` naming the unknown and missing keys and every param the method takes, required ones marked. A `caller` is honored when it is a terminal tile on any open board, so an agent working on another board (`board`) is credited there (`createdBy`/`updatedBy`, `board.history`) as on its own; placing beside the caller applies only on its own board.

### cmux browser subset

Exactly what omp's cmux browser backend sends (`src/tools/browser/cmux/`), framed as cmux v2 JSON lines: requests `{"id","method","params"}`, replies `{"id","ok":true,"result"}` or `{"id","ok":false,"error":{"code","message"}}`. Surfaces are object ids: a terminal tile is the calling surface (`CMUX_SURFACE_ID`), a browser tile is a browser surface; workspaces are boards. Every browser result carries `surface_id`.

Surface and workspace ids stay `obj_…`/`brd_…` on the wire, which omp 18.3 accepts; omp ≤18.1's owner inspection (`surface.list` via its surface-observation module) requires UUID ids and is unsupported.

Agents without omp's tool use the same subset through the CLI (`cli/easl.ts`): `easl browser <verb> [<tile>] [--key value]` sends one request per call on its own connection (`auth` first when `CMUX_SOCKET_PASSWORD` is set; `CMUX_SOCKET_PATH`, else `cmux.sock` beside the easl socket): `open [url]` is `browser.open_split` from `CMUX_SURFACE_ID`, `list` is `surface.list`, `close` is `surface.close`, any other verb is `browser.<verb>` with `<tile>` as `surface_id`; `screenshot` writes the PNG (`--out`, else `$TMPDIR/easl-renders/screenshot-<ms>-<pid>.png`) and prints its `path` instead of `png_base64`.

A page an agent is driving stays visible to WebKit for 60 s after its last command, even when its tile is offscreen, the window is minimized, in a background tab, on another Space, or covered, or the app is hidden: `document.visibilityState` is `visible` and `requestAnimationFrame`, timers and `IntersectionObserver` run as they would for a user. Window occlusion detection is off for the page, and while its tile can't show it the web view waits in `WebStage`, a transparent click-through window of its own that stays on screen (ordered in only while something waits in it). A page that was hidden gets up to 0.5 s to present a frame before the command runs, so the first command already sees it visible. Then the tile's normal policy resumes: a page nobody can see (its tile offscreen or zoomed out, its window minimized, covered, in a background tab or closed, the app hidden) waits hidden in its tile, so WebKit treats it as hidden (no `requestAnimationFrame` or CSS animation, timers throttled more the longer it stays hidden), and one whose tile isn't live is released 2 minutes later (`object.get` then says `page.loaded: false`; the next command or render loads it again from `props.url`, with its in-page state gone). A hidden page still commits a frame for every DOM change, and each commit wakes WebKit's display link in the app for a moment; releasing is what makes an unseen page with a clock or a live-reload socket cost nothing. `view.render` of a browser tile counts as a command: a page that isn't loaded loads (in the stage) and is waited for until the render's `timeoutMs`.

The terminal a command comes from (its driver) is the one the connection opened splits from, else the one that opened the tile, else none. `board.history` credits a page's URL changes and the tiles it opens (`_blank`, `window.open`, ⌘-click) to whoever last acted on the page within 10 s (`NavigationCredit`): a driven command that can act (`navigate`, `back`, `forward`, `reload`, `eval`, element actions, `type`, `fill`, `press`) → its driver (`system` when none), the user clicking or typing in the page, its address bar, back, forward or reload → `user`; otherwise (a redirect or timer later on) `system`. A tile the user opened from a page is revealed (least pan) and selected; one an agent's command opened isn't. The same address opened again from the same page within 2 s gets the first tile back.

Error codes: `invalid_params`, `not_found`, `method_not_found`, `unauthorized`, `timeout`, `js_error`, `unavailable`. The plain-text line `auth <password>` answers `OK: …` or `ERROR: …`.

### Page log (console, errors, failed requests)

Every browser tile's main frame runs `PageCapture` (CanvasCore/PageLog.swift) in the page's own world at document start, so it sees the page from its first line on. It records console messages (`log` `info` `warn` `error` `debug`, as the console formats them, up to 1,000 characters; warnings and errors with the `url:line:column` of the code that logged), uncaught errors and unhandled rejections (message, source, stack), and failed requests: `fetch` and `XMLHttpRequest` answered 400 or more or never answered (network error; an aborted request isn't a failure), and elements whose resource failed to load (`img`, `script`, `link`…, from their `error` events; WebKit exposes no status for those). Errors and warnings go in one ring of 200, other messages in another of 200, so a chatty page never pushes out its errors; what falls out is counted (`dropped`). The tile hears nothing but the page's error count, at most once per 100 ms burst and 0 at every new document (message handler `canvasPageLog`, page world); everything else is read on demand (`__canvasPageLog.read()`, a non-enumerable, non-configurable global). The page's own document answered 400 or more is its first entry (`resource: document`, from the navigation response, once that navigation commits: `DocumentFailureTracker`; a page back from the back/forward cache has no response of its own and takes its history entry's, so Back from a 404 drops the entry and Forward to it brings it back). Web vitals: LCP by `PerformanceObserver` (buffered) where WebKit has the entry type; CLS and long tasks (`layout-shift`, `longtask`, which WebKit lacks) are null and listed in `vitals.unsupported`; FCP, TTFB, DOMContentLoaded and load from the paint and navigation timings, null until they happen. Hooking `console` means the Web Inspector's console attributes messages to `canvas-page-log.js`; their stack traces still lead to the caller.

It also starts omp's cmux capture globals in the shapes omp installs after load, which omp then leaves in place: `__ompConsoleCapture` (`{entries: [{seq, ts, type: console|pageerror, level, text, args, location?, stack?}], nextSeq, dropped}`, 500 entries; `args` serialize when omp reads them) and `__ompCmuxResponses` (`{nextId, records: [{id, ts, method, resourceType, url, status, statusText, headers, requestHeaders, body, durationMs}]}`, 200 records, text bodies up to 64 KiB, none for streams or binary types). A record is every `fetch` and `XMLHttpRequest` that got an answer (`resourceType` `fetch`/`xhr`, its status), plus every request the page log counts as failed without one: a `fetch` that never got an answer and an element whose resource failed to load, with `status: 0`, `statusText` the reason (`failed to load`), and `resourceType` the element's tag (`script`, `img`, `link`…; omp's `requests()` reports every type but `xhr` as `fetch`). So omp's `requests()` lists what `object.get`'s `page` lists as failed requests, except the page's own document (in `page` only), and never the page's successful document, script, style, image or font loads. omp's `tab.console()`, `errors()`, `requests()` and `waitForResponse()` cover the page's load. XHR is observed through `XMLHttpRequest.prototype` (`open`, `send`, `setRequestHeader`), not by replacing the constructor.

`object.get` on a browser tile adds `page` (schema `PageLog`): the counts since the page loaded, the latest 100 entries (after `since`, a `page.cursor` from an earlier call; one from an earlier document returns all of this one with `reloaded: true`), and the vitals; `loaded: false` when the tile has no page (released or never shown). `visibility` says how WebKit runs the page now (`PageReport.Visibility`): `visible` (on screen: requestAnimationFrame at the display's rate), `hidden` (in its tile where nobody sees it: no rAF, timers throttled more the longer it stays hidden), `driven` (kept visible for an agent though nobody sees it: rAF and timers run, irregularly and slower), `released` (no page). A page easl releases leaves its log behind: the tile reads it from the page as it goes, and `previous` returns it (the same fields plus `releasedAt`) until the page loads another document after the reload, and until `since` names the current document; while released, `cursor` is the released page's, so a cursor loop goes on across the release (the reload returns all of the new page with `reloaded: true`). The badge in the tile's address bar ("2 errors", only while there are any) opens a list of the errors, newest first (message, kind, `file:line`, time); a Hyper-click on a row stages a `console` mention (schema `MentionTarget`: `object`, the page's `url`, and the `entry`). A click on a row shows its whole message and stack; a `file:line` or stack frame served from a file under the board root opens that file's code tile at the line (`PageSource.file`).

## Terminal tile environment

Every terminal tile's process (inside zmx) gets:

| Variable | Value |
| --- | --- |
| `EASL_ENV` | `1` |
| `EASL_SOCKET` | easl API socket path |
| `EASL_TILE_ID` | This tile's object id |
| `EASL_BOARD_ID` | This board's id |
| `EASL_BOARD_ROOT` | Board root directory |
| `CMUX_SOCKET_PATH` | cmux subset socket path |
| `CMUX_SURFACE_ID` | This tile's object id |
| `CMUX_WORKSPACE_ID` | This board's id |
| `CMUX_SOCKET_PASSWORD` | Only when the app was launched with it; the cmux socket then requires `auth <password>` |
| `PATH` | easl's `bin/` (`easl`, and the `claude`/`codex`/`gemini`/`opencode` wrappers) first, then the app's PATH |
| `PYTHONPATH` | The app's `clients/python` (only the `easl_sdk` package in a bundle), before an inherited value: `from easl_sdk import canvas` works in every tile |
| `BROWSER` | The app's `bin/open`: the shim below, for programs that open a web page |
| `ZDOTDIR` | `extensions/shell/zsh`: zsh shell integration (below) |
| `EASL_ZSH_ZDOTDIR` | The user's own `ZDOTDIR`, only when the app's environment had one (see below for an app launched from a tile) |
| `PROMPT_COMMAND` | `. <extensions/shell/bash/easl.bash>` (before an inherited value): bash shell integration |
| `EASL_GHOSTTY_INTEGRATION` | Ghostty's shell-integration directory (libghostty-spm's `Ghostty/shell-integration`), unless the user's Ghostty config says `shell-integration = none` (`TerminalShellIntegration`). Interactive zsh sources `zsh/ghostty-integration` at the end of `_canvas_finish` (after the user's files, so a prompt framework's hooks run first; not when `_ghostty_integration_loaded` or real Ghostty's `_ghostty_state` is set); bash sources `bash/ghostty.bash` on `easl.bash`'s first run and installs bash-preexec's hooks at once, so the first command is marked. Ghostty injects its integration only into shells it starts itself, and tiles run `sh -c … zmx attach … zsh -l`: without this there are no OSC 133 marks (jump to prompt, click to move, command exit status). |

Nothing else the app inherited reaches the shell except what a fresh login session starts with (`LoginSession`: `HOME`, `USER`, `LOGNAME`, `SHELL`, `TMPDIR`, `LANG`, `LC_*`, `__CF_USER_TEXT_ENCODING`), `SSH_AUTH_SOCK`, `XDG_*`, and what Ghostty sets on the child (`TERM`, `TERMINFO`, `COLORTERM`, `GHOSTTY_*`): the zmx attach runs under `env -u` for every other inherited name. The app's environment is whatever launched it; launched from an agent's tool shell it held `CI`, `NO_COLOR`, `EDITOR=true`, `GIT_EDITOR=true`, pagers set to `cat`, and `CLAUDECODE` (Claude Code then refuses to start). The user's startup files set their own variables again, as in a terminal opened from the Dock.

`bin/open` (first on `PATH`, so `open`, and `$BROWSER`) is easl's shim of the system command: inside a tile (`EASL_SOCKET` answering, `EASL_TILE_ID` set) with every argument an http(s) URL without a quote, backslash, space or control character, it sends each to `view.open_url` with the tile as `caller` and exits 0 once the app answered `ok`: the page shows in a browser tile beside the terminal, or the tile already showing that address (same scheme, host, port, path, query and fragment) is reused. It needs only `sh` and `/usr/bin/nc`, and waits at most 6 s for the app. Anything else, or any failure, runs `exec /usr/bin/open "$@"` with the arguments the app has not shown, so files, `-a`, flags, other schemes and an app that is not answering behave as without easl; an agent that must reach the default browser calls `/usr/bin/open` by its full path. A user's startup files that set `BROWSER` win over the tile's.

An app launched from inside an easl tile (an agent's `scripts/dev.sh restart`, `open` in a tile) inherits that tile's integration, possibly of another bundle: a non-interactive shell and what it starts keep `ZDOTDIR` pointing at the tile's `extensions/shell/zsh`, and every shell keeps its `PATH`, `PYTHONPATH` and `PROMPT_COMMAND` entries. Taken as the user's own, that `ZDOTDIR` made each new tile source easl's zsh files instead of the user's (`.zlogin:3: command not found: _canvas_finish`, no `~/.zshrc`, no nvm). So the tile's variables (`LoginSession.tileShellIntegration`) leave out every easl integration the app inherited: `<resources>` is easl's when an inherited `ZDOTDIR` or `EASL_ZSH_ZDOTDIR` is `<resources>/extensions/shell/zsh` or `PROMPT_COMMAND` sources `<resources>/extensions/shell/bash/easl.bash`; its `bin/`, `clients/python` and `easl.bash` entries are dropped, and the user's `ZDOTDIR` is the inherited one that isn't easl's (`ZDOTDIR`, else the `EASL_ZSH_ZDOTDIR` that tile kept aside), else none (`HOME`).

Integrations report only when `EASL_ENV=1` and the variables they need are present, so they are no-ops outside the app.

Shell integration keeps easl's `bin/` first on PATH after the user's startup files, which may prepend directories (e.g. `~/.local/bin`, Claude Code's install location) that would shadow the wrappers. zsh: each startup file in `ZDOTDIR` sources the user's file of the same name with the user's `ZDOTDIR` in place (their files may set their own), and the last one zsh reads re-prepends `bin/`; interactive shells then restore the user's `ZDOTDIR` (unset if they had none), so shells they start are plain zsh. History stays the user's: macOS's `/etc/zshrc` runs while `ZDOTDIR` is easl's and points `HISTFILE` there, so before each user file a `HISTFILE` inside that directory moves to the user's `ZDOTDIR` (or `HOME`), and their own setting wins. A non-interactive login shell (a tile's `zsh -l -c '<command>; exec zsh -l'`, e.g. resuming an agent) keeps the integration for the command and the shell after it. bash: `easl.bash` runs before the first prompt, after the user's startup files, as long as they keep an inherited `PROMPT_COMMAND` when setting their own; `bash -l -c` commands and other shells (fish, nushell) resolve `claude`/`codex` with whatever PATH their startup files leave. Before each prompt, interactive zsh (a `precmd` hook) and bash (`easl.bash`) report the shell's directory as OSC 7 (`file://host/path`, percent-encoded, as macOS Terminal's own shell files do), which the tile keeps as the directory `path:line` references resolve against first.

zmx session names: `canvas-<tileId>`, labelled `canvas.board=<boardId> canvas.tile=<tileId> canvas.home=<support dir path, every byte outside [A-Za-z0-9._-] as _>` (zmx label values allow only those characters). `canvas.home` names the instance that created the session: board copies in another home (replicas, dev instances) carry the same ids, so `scripts/dev.sh stop` kills only sessions labelled with its own home. Because `zmx attach --labels` relabels a session that already exists, a tile never attaches to or ends a session labelled for another home (`TerminalTile.ownerGuard` runs before `attach` and `kill`): the copy's tile says whose session it is instead of taking it over. The default home also takes sessions labelled with an older install's default support directory as its own (`TerminalTile.legacyHomeLabels`), and attaching relabels them. A session zmx lists but can't reach (`err=Timeout status=unreachable`: its daemon stopped, say by SIGSTOP, or wedged) is waited for before that check (`SessionReach`): `zmx attach --labels` to it fails at once and would leave the tile detached once it answers, so the tile says it isn't answering and checks again after 1 s, doubling to every 30 s, and attaches when it answers; after an hour of waiting it gives up, and a key press in the tile starts over. `scripts/dev.sh` trusts a `pid` file only while that process owns the home's socket, since a copied home carries the original's pid file. Names stay short because zmx sockets live under `$TMPDIR/zmx-<uid>` (a long `/var/folders/…` path for GUI apps) and a socket path is capped at 104 bytes. Tiles inherit the app's `TMPDIR`, so `zmx list` inside a tile shows easl's sessions. Deleting a terminal ends its session on every path (the UI close, `object.delete`, an `object.batch`, undo of its creation, redo of its delete): `Board.onTerminalsEnded` reports the terminals a step removed once its outermost step closes (a failed batch that put its delete back reports nothing), and the app runs `TerminalTile.killSession(tile:)` for each (owner-guarded). Undoing the delete brings the tile back with a new session (its `command`, or `omp --resume` for a recorded omp session).

## Hosted terminals

A terminal with `props.host` (an ssh target, `deckbox`) runs its session on that machine (`HostedTerminal`, `TerminalHost`, easld's `internal/session` and `internal/relay`). `props.cwd` is then a directory there (default: the user's home); the tile's process here is only the attach. A terminal's host is fixed when it is created: an update that changes or removes it (or gives a local terminal one) is `invalid_params` (`Board.write`), since the live tile stays attached where its session started and its history, render and kill would otherwise go to another machine.

- **Sessions are easld's.** The host runs easld as the system unit `easld@<user>.service` (`easld/packaging/linux/easld@.service`: `User=%i`, `Slice=agents.slice`, `KillMode=process`, home `~/.local/state/easl`, socket `~/.local/state/easl/easl.sock`). The app asks it to start the tile's session (`session.spawn`: `canvas-<tile>`, labelled like a local one, the command as argv in the login shell, `PATH` before easld's own), so the session and everything it runs stay in the unit's cgroup and slice: a process started through an ssh session or `systemd --user` would land in `user-<uid>.slice`, which has no cap. Docker containers escape the slice: a container a hosted agent starts needs `--cpuset-cpus` within the slice's CPUs and `--memory`. zmx's sockets and logs for hosted sessions are in `~/.local/state/easl/zmx` on both sides (`ZMX_DIR`, which easld sets on every zmx it runs, whatever a spawn's `env` says), never zmx's shared default `/tmp/zmx-<uid>`, which another user of the host could make first and plant a log symlink in: easld makes it 0700 and refuses (`unavailable`) a symlink, another user's directory or one others can write to, at startup and before each zmx call. A session whose `canvas.home`, `canvas.board` or `canvas.tile` label isn't the caller's is never taken over (`session.spawn`: `conflict`) or ended (`session.kill` with `home`); one zmx found dead while listing it (`status=cleaning up`, its socket deleted) doesn't exist, so a spawn starts it again. `session.kill` ends one (deleting the tile, on every delete path); `session.list` answers whether it still runs. The app answers all three `unsupported`.
- **One ssh connection per host** and app instance: a master (`ssh -M -N`, control socket `$TMPDIR/easl-ssh-<host>-<hash>`, `BatchMode`, `ServerAliveInterval=10`) that the attaches, the calls to easld (`nc -N -U` on its socket where the host's nc has `-N`, else `nc -U`; one line each, ended once the reply is in) and `zmx history` (agent.read `lines`, cards, renders) multiplex over. The tile's command (`HostedTerminal.attachLoop`) waits for it, attaches with `ssh -tt … zmx attach canvas-<tile>` (on the host: only once easld has started the session, only if its `canvas.home`, `canvas.board` and `canvas.tile` labels are this instance's, this board's and this tile's, else it says whose the session is and the tile holds there without attaching, as a local tile's `ownerGuard` does; and with `SHELL=/bin/false` so zmx never starts one itself), and attaches again whenever ssh fails (255), so a network loss reattaches the same session; zmx's own exit ends it as a local tile's does. While the host is unreachable the tile shows a banner, "<host> is offline. <why>", with Reconnect; the app retries after 1 s, doubling to 30 s. A tile closed while the host is offline leaves its session there.
- **The way back** (`relay.open`): the master forwards a dynamic loopback port on the host to this instance's `RelayGate` (`$TMPDIR/easl-gate-…sock`), and easld serves it as `~/.local/state/easl/run/<instance>/easl.sock` and `cmux.sock` (the user's only; `<instance>` is the Mac's name and a hash of its support directory), passing each connection on to the port. Every user of the host can reach the port, and anyone can listen on it once the forward is gone (easld keeps the port until the app opens the relay again), so neither end sends the token: easld sends `<easl|cmux> <nonce>`, the gate answers `<nonce> <proof>`, easld `<proof>` (hex HMAC-SHA256 keyed by the token over `easl-relay <gate|easld> <name> <easld's nonce> <the gate's nonce>`, `relay.Proof`, `RelayGate.proof`), and only then does the gate splice it to the API's or cmux's socket. A connection the gate doesn't take (refused, or no proof) closes at once, the integration spooling its report, and disarms the relay until the app opens it again. The gate gets a new token on every connection to the host (`RelayGate.rotate`, before easld hears of the port), so a forward or port from before a drop opens nothing. Not ssh's forward of a unix socket: Tailscale SSH creates that socket owned by root, mode 0600. The app opens the relay again every 30 s while connected, so it comes back after easld restarts or a disarm (`opened`: replay the spool). A new token rebinds the sockets at the same paths, so after the app restarts (or reconnects) the integrations' `watchCanvasReturn`, which watches the socket's identity, sees the board come back and reports again, clearing the restored `working` state.
- **The session's variables**: `EASL_ENV`, `EASL_SOCKET` and `CMUX_SOCKET_PATH` (the relayed sockets), `EASL_TILE_ID`, `EASL_BOARD_ID`, `CMUX_SURFACE_ID`, `CMUX_WORKSPACE_ID`, the shell integration of `~/.local/share/easl` (`PATH`, `PYTHONPATH`, `ZDOTDIR`, `PROMPT_COMMAND`, `BROWSER`), `EASL_GHOSTTY_INTEGRATION` (`~/.local/share/easl/ghostty/shell-integration`), `TERM=xterm-256color`, `COLORTERM=truecolor`; no `EASL_BOARD_ROOT` (a directory of this Mac). Reports an integration couldn't deliver spool beside the relayed socket (`run/<instance>/agent-reports/`). On each connect, when the relay re-arms, and when a hosted tile opens on a host already connected, the app fetches them for those tiles, replays them (`Board.replay`) and deletes them there, before it asks easld to start their sessions: an agent the user exited while the app was away released its tile, so a host that rebooted meanwhile doesn't resume it.
- **Setup**: `scripts/offload-setup.sh <host>` (idempotent, no root, starts nothing) installs zmx 0.8.1 (checksum-verified), easld built for the host, the `easl` CLI and `~/.local/share/easl` (the bundle's agent files), links `~/.omp/agent/extensions/easl.ts`, and prints the unit for the host's administrator. The host needs bun and OpenBSD `nc`.
- Not on a hosted terminal: the foreground program and its directory (no process table here), so `agent.prompt`'s foreign-program check and the tile's program name don't apply; `path:line` ⌘-clicks resolve against this Mac's files.

## Agent integrations

Claude Code, Codex, Gemini CLI and opencode get omp's integration (`extensions/omp/easl.ts`) through easl's wrappers `bin/claude`, `bin/codex`, `bin/gemini` and `bin/opencode`, one hook script (Claude Code, Codex, Gemini CLI) and one opencode plugin, `extensions/agent-hooks/hook.ts` (`run <claude|codex> <event>`, the agent's hook JSON on stdin). A wrapper execs the next `claude`/`codex` on PATH that is not an easl wrapper (any directory beside `extensions/agent-hooks`, so two easl installs never recurse), or exits 127 naming the missing binary. ## Client connection

The Python SDK, TS client, and CLI find the socket in this order: an explicit value (`connect(socket=…)`, `new CanvasClient({ socketPath })`), then `EASL_SOCKET`, then `~/Library/Application Support/Easl/easl.sock` only if that file exists; otherwise they fail with `unavailable`, naming `EASL_SOCKET`, the path checked, and the explicit-connect fix. `caller` and `board` come from the client's own tile/board (explicit, else `EASL_TILE_ID`/`EASL_BOARD_ID` at construction). omp's `eval` Python kernel runs with an allowlisted environment that drops `EASL_*`, so the omp extension prints the explicit `connect(...)` line in the system prompt.

Connection failures are always `unavailable`; clients never surface raw socket errors. A socket file that exists but refuses this process (EPERM/EACCES, or ENOENT although the file is there, twice in a row: what Codex's seatbelt sandbox answers; a single one is an app binding its socket just after the connect missed it) fails at once, without waiting for the app, with a message naming the socket and saying a sandbox (e.g. Codex's) may be blocking it. A request that never left (connect failed, write failed, or its newline was unflushed when the connection closed) is sent once more on a fresh connection after waiting up to 15 s for the socket (an app restart). A request that left and lost its reply is not resent: `unavailable: … it may or may not have applied — re-read before retrying`. The exception is a read the schema marks `"resend": true` (`agent.wait`; generated as `RESEND_METHODS`): the client waits up to 15 s for the app to come back and sends it again with `timeoutMs` reduced by the time already spent, so a wait survives an app restart. Image methods (`view.render`, `view.snapshot`) take `out` as an absolute path the app writes (format by extension, png or jpg); clients resolve a relative `out` against their cwd. Without `out` the app writes a new file under `$TMPDIR/easl-renders/` (`ApiRouter.scratchImages`, out of the user's repo); the result's `path` names the file either way, and images never travel inline.

The app writes replies and events through a per-connection queue, in order, and never blocks on a slow reader. An `events.subscribe` client that stops reading can't freeze the board; one that falls more than 32 MB behind is disconnected.

## Activity log

`board.history` reads `Board.activity` (`Sources/CanvasCore/ActivityLog.swift`): in memory, the newest 2000 entries per board, restarted with a `restart` entry when the app opens the board. Board mutations log themselves with their actor (`caller` → `agent:<tile>`, none → `user`, the app's own write-backs → `system`; undo/redo → `user`, prefixed `undo:`/`redo:`). Cascades of a change (a group re-fit to its members, an arrow end freed because its bound object was deleted) are credited to that change's actor and carry a `cause`; within one revision each object gets one cascade entry, amended to its net change (dropped when the changes cancel out), so a batch that moves or deletes 40 members of a lane logs the lane once. Bookkeeping (a terminal's lifecycle, session, title; a browser's `pageTitle`) is never logged. Follow re-aims log one `follow` entry, not the create/update beneath. The board reports viewport and selection changes continuously; the log records them once they have been still for 0.8 s and differ from the last logged state.

A composition is a module in a compositions directory. ## Object model rules

- Ids are prefixed: `brd_` board, `obj_` object, `men_` mention.
- `frame` is in board coordinates (points at 100% zoom) and is the whole box the object draws: a tile's includes its `RenderMath.tileTitleHeight` (26 pt) title bar at the top, and its content (the body, what `TileRenderRequest.size` and `contentSize` describe) is the frame below it (`RenderMath.body`). Measure, fit, groups, placement, `layout.*`, arrow attachment, and `view.render` pixel rects all use this one box. `z` orders siblings.
- Stored boards carry `format` (`Board.format`, 2). A board without it (format 1 stored a tile's body, its title bar drawn above) loads with every tile frame 26 pt taller, the same box on screen; saving writes format 2.
- `rev` increments on every change; `object.update` with a stale `rev` fails with `conflict`. The app's bookkeeping writes (`Board.writeBookkeeping`: a browser's `pageTitle`, the page's own title; `Board.reanchor`: a code tile's `range` and `anchor` re-found by content) leave `rev`, `updatedBy`, and `updatedAt` alone, but still take a board revision (`board.get since`), announce `object.updated`, and are saved.
- `createdBy`/`updatedBy` record the actor. An agent is identified by its terminal tile, on whichever board the object is.
- Deleting an object removes every staged mention that targets it, and its attention marker.
- Attention markers (`Board.attention`, one per object) are stored with the board until the user sees the object or someone clears them, and restored on open (markers on objects no longer there are dropped; `board.export` leaves them out). A marker belongs to its raiser's turn: when a terminal's lifecycle goes to `working` from `idle`, `done`, or no state (the user's next prompt reached it; blocked → working, an answered approval, and repeated `working` reports continue the turn), its markers are marked `earlierTurn`, and its next `view.attention` clears those (`cleared` in the result); markers from the current turn stay together. A raise without a terminal `caller` is never cleared that way. A terminal's own notification or bell (OSC 9, OSC 777 `notify`, BEL; `Board.raiseTerminalNotice`) raises a marker on that terminal with no `raisedBy`, unless the terminal has keyboard focus in the active window; the same message again, or a bell over any existing marker, changes nothing.
- Props a type doesn't define (`ObjectType.knownProps`, mirroring the schema's `*Props`) are kept, and `object.create`/`object.update` name each in `warnings`.
- `props.key` (any type, `ObjectKey`; `Board+Keys.swift`) names an object for scripts, unique per board. `Board.keyHolders` maps each key to its holders and changes only where `objects` does (`commit`, `delete`, `init(snapshot:)`), so undo, redo, a failed batch's rollback, and load leave it exact; it holds sets so a board file edited to give two objects one key still loads, and looking that key up is `conflict` naming both. `Board.checkKey` rejects a key another object holds (`conflict`, naming the holder) on `object.create` and in `Board.write` (every update); an empty or non-string key is `invalid_params`, `null` removes it. UI-made objects never carry one. An `object.create` of a changes tile that gives a key is never `reused` for another tile.
- `object.find` looks a key up on one board (`board` defaults as for create): `key` answers what `object.get` would for the holder, `keyPrefix` lists holders by key order. `object.upsert` becomes the `object.create` (key added to its props) or `object.update` (props merged, `frame`/`size` as update; the holder's type must match, else `conflict`) it is when it runs (`ApiRouter.upserted`), and says which in `created`. In `object.batch` that resolution happens in the planning pass, against the board plus what earlier ops do to keys (`ApiRouter.KeyPlan`: keys created, keys given by updates, holders deleted or re-keyed), so `$n` of an upsert names the object whether created or updated and an upsert of a key an earlier op creates updates it; when the op applies, its key's holder must be the planned one, else the batch fails with `conflict` and rolls back.
- A board belongs to one root directory; code paths are stored relative to it (absolute outside it).
- Board identity (`BoardStore.boardID`, `RepoBoards.swift`, docs/design/repo-boards.md): a directory in a git repository opens the repository's board, id `brd_` + SHA-256 of its common git directory as `GitWorktree` finds it (filesystem only, no git process), rooted at the main checkout (`GitWorktree.canonicalRoot`: the opened checkout when it is the main one, else the common dir's parent), whichever worktree, branch or subdirectory opened it; any other directory its own, id from its path. `BoardRegistry.open` tags the board with the worktree it was opened from (`Board.opened(from:)`: records a linked worktree in `repo.worktrees` and makes it the in-memory working worktree, where New Terminal starts; the main checkout clears it) and the window names it and reveals its branch's region (`CanvasWindowController.showWorktree`). A terminal created with a `cwd` in the board's repository gets `props.worktree` and `props.branch` (`Board.stampingWorktree`). `board.list` reports `repo` and `worktrees` (`RepoRecord.worktreeList`: live worktrees, main first, then recorded ones; `live` means that worktree has that branch checked out), `board.open` the `worktree` it was opened from, and `board.get --branch` one branch's part (`Board.objects(ofBranch:)`). A `board` param naming a legacy board a repository board merged (`repo.merged`: shells started before the migration keep it in `EASL_BOARD_ID`) means that repository board (`BoardRegistry.board(id:)`).
- Repository-board migration (`RepoBoardMigration`, run by `BoardStore.migrateToRepoBoards` at launch before any board opens, and for one repository when its board loads while legacy boards stay unresolved): legacy boards (keyed `<common dir>\n<branch>` or, detached, `<common dir>\n<top level>`, or by path in a repository with no commit) are identified by recomputing those ids, merged into their repository's board, re-rooted, and moved to `pre-repo-migration/`; boards outside git are never touched. Placement, re-rooting and the report are in docs/design/repo-boards.md.
- `props.zoom` (every tile but an image; `ObjectZoom`, 0.25–8, absent = 1) is how big a tile's content draws inside its frame, in place; the frame is the tile's size, which only resizing changes. The title bar stays at 1× (its height is the tile's geometry, `RenderMath.tileTitleHeight`; a client's chrome text size scales its text, not the bar, and `view.render` always draws it at 100%); `TileFrameView` holds the content in a body view (`ContentZoomView`) whose bounds are the body ÷ zoom, so the content lays out, hit-tests, and takes mentions in its own points, at `CanvasObject.naturalFrame` (`ObjectZoom.natural`: the same title bar over the body ÷ zoom, the tile as it would be at 100%; `RenderMath.body(of:)` is that body), and draws zoom×; renders draw the content at its zoom under a 1× title bar. A browser tile keeps its address bar at 1× too (`BrowserTile.chromeExtent`: `chromeHeight ÷ zoom` of its points, its bounds undoing the zoom), so only the page zooms, as a browser's page zoom does. An image tile doesn't take it (`ObjectZoom.applies`: the picture is already fitted to the frame): `zoom` there is an unknown prop, kept, warned about, unread. A text shape's font is `DrawingStyle.textPointSize` × `props.textSize` (`ShapeSpec.textSize`, 0.25–8, absent = 1), and its box grows with it. What agents get is in board points: `object.measure` and `size: "fit"` (laid out at `width` ÷ zoom; the frame is the title bar plus the body × zoom, `ObjectZoom.zoomed`), `layout.check` overflow, `view.render` `contentSize`/`overflow` (the layout extent × zoom), and line anchors (`CodeMetrics.lineY`). A mention's "over <tile> at (x, y) w×h" region is in the host tile's content points (below its title bar, ÷ its zoom; `ObjectZoom.canvasRect` maps them back). The user zooms with the title bar's `−  150%  +` (`TileZoomControl`, left of the ✕: the % whenever it isn't 100%, − and + while the tile is hovered or selected; a click on the % resets to 100%) or Object ▸ Content Zoom (Zoom Content In ⌃⌘=, Zoom Content Out ⌃⌘- through `ObjectZoom.levels`, the presets, Reset Content Zoom ⌃⌘0; `CanvasView.setZoom`/`stepZoom` on `zoomTargets`: the selected tiles and text shapes, else the tile holding the keyboard), one undo step: a tile's frame stays as it is, a text shape's `textSize` changes with its box, grown or shrunk from its top-left. An `object.update` that sets `zoom` never changes the frame. `props.scale` is gone: `object.create`, `object.update`, `object.upsert`, `object.batch` ops, and `object.measure` with it fail with `invalid_params` naming `zoom` and `textSize` (`ObjectZoom.retiredProblem`, no alias). A board saved with it migrates once on load (`ObjectZoom.migrated`, idempotent): a tile's `scale` becomes its `zoom` with the frame unchanged (it keeps its size on screen and its content its size; only the title bar is 1× again), an image's is dropped, a text shape's becomes `textSize`; a `zoom` or `textSize` already there wins, and 1 is dropped. Liveness and zoomed-out handles use magnification × zoom (`RenderMath.isZoomedOut`).
- A group's `frame` is derived: its members' bounds (arrows excluded) plus `padding` and a `GroupSpec.titleHeight` title band, recomputed by `Board` in the same undo step as any change to a member's frame (nested groups outward), and on load. Frames written to a group are ignored. Stored groups labelled by the old `name` prop load with it as `title`.
- Placement (`Board.place`): an object created without a frame (an agent's, the follow tile, a pin, a link opened from a note or HTML tile) goes to the free slot nearest the caller's tile, touching it 24 pt away when there's room (right, then below, left, above), else nearest the viewport center; beside a tile, slots wholly (then partly) in view win over nearer ones out of it only within `Board.nearbyDistance` (600 pt, the gap between the frames) of the tile; further out the nearest free slot wins, in view or not, so on a busy board an agent's object stays by its terminal rather than landing in view beside someone else's (the agent raises a marker when the user should look); `place(_ ideal:)` finds the free slot nearest a given frame. An agent's own frameless creates (`object.create` without a frame or with `size: "fit"`, `browser.open_split`; `place(stacking: true)`) stack instead of going round the terminal: when the caller created a tile within `Board.answerStackWindow` (10 minutes) that is still on the board and isn't a follow tile, the free slot beside the newest such tile, by the same rules with sides ordered below, right, left, above, is taken if it touches that tile 24 pt below or right of it and is no less in view (wholly, partly, not at all, against the viewport inset 24 pt) than the slot beside the caller; otherwise the caller rule applies. Follow tiles, pins, links, and the user's objects never stack. Free means 24 pt clear of every tile and group, other agents' included; drawings and arrows never block. While the caller's tile (or the ideal spot) is on screen, a slot wholly inside the viewport (`Board.viewport`: the part of the window clear of the toolbar and tray, inset 24 pt) wins over a nearer one outside it, and when none fits, a slot partly in it wins over one wholly outside, one whose top edge (a tile's title bar) is in view first: a terminal an API call made without a frame used to land above the one filling the view, its title bar under the toolbar. A new follow tile (`place(width:height:near:shrinkingTo:)` with `Board.followMinimumSize`, 400×300, about 45 columns of code) may also be cut down to the part of such a slot that is in view: when no full-size slot fits wholly in view, a smaller one that does beats one partly outside (beside a default 1000-pt terminal in a 1976-pt view: 440×446 on its right, not 640×446 partly off-screen); a narrower sliver (198 pt in a 1492-pt view) keeps the full-size slot, since code wrapped at 18 columns is unreadable. The view never moves for it. Origins are whole points. The app places the user's own new objects by the same rule (`CanvasView.openForUser`: File › Open File, New Note, New Browser Tile, New HTML Tile, ⌘T, Go to's file rows at the viewport center; Edit Here's terminal beside its code tile), then pans the least that shows the object (`Layout.reveal`), selects it, and gives it the keyboard. API creates without a caller use the viewport center and never move the viewport.

## Layout

`object.measure`, `size: "fit"`, `layout.place`/`stack`/`translate`/`grid`, `object.batch`, and `layout.check` live in CanvasCore (`ObjectMeasure`, `Layout`, `Board.atomically`). Measured sizes are whole object frames, tile title bar included: code follows `CodeMetrics` (`ObjectMeasure.code`: as wide as the range's longest line up to the max width, `width` or `CodeMetrics.defaultFitWidth` = 1546 pt, 200 columns (`CodeMetrics.autoColumns`) beside a 4-digit gutter; longer lines wrap and count in the height; `layout.check` measures code at its frame's width; a code tile created without a frame, by the API or the user, other than a follow tile, takes `Board.newCodeSize`: 446 tall and as wide as the working-tree file's longest line needs at its zoom, by `SideText`'s lines and `WrapText`'s columns, from 640 up to `defaultFitWidth` of content, 640 for a tile shown from git or a file it can't read within 1 MiB; easld's `Board.NewCodeSize` matches it, decoding malformed UTF-8 as Swift does), images (`LocalImage`: the picture at one point per pixel, at most `width` wide, default 960, plus the caption strip; an image created without a frame height is fitted like a note), notes (an `object.create` of a note without a frame height is fitted like `size: "fit"`, at `frame.w` or `ObjectMeasure.defaultNoteWidth`; `title` only names the tile) lay out `NoteRenderer` output with TextKit 2 at the note tile's own insets, its tables' columns fitted and their cells wrapped to that width (`ObjectMeasure.note`, `noteInset`; `NoteRenderer`, `NoteLayout`, and `DrawingStyle` are in CanvasCore for this), text shapes use `DrawingStyle`'s font, and HTML pages are laid out by the app's WebKit (`ObjectMeasure.html`, set by the app to `HtmlTile.measure`: the page loads offscreen exactly as `view.render` loads it, in a throwaway tile 1 pt tall at the width, and its document scroll size once the kit reports `view.rendered`, at most 3 pages at once, 10 s each; `size: "fit"` gives `frame.w` or 640 and the title bar plus the document height, capped at `ObjectMeasure.maxHtmlFitHeight` = 4000; `layout.check` measures each HTML tile at its frame width, uncapped; CanvasCore alone reports HTML `unsupported`). Measuring reads files, so `object.measure`, a `size: "fit"` create/update, `object.batch`, and `layout.check` are resolved asynchronously; a batch measures every op first, then applies all of them synchronously inside `Board.atomically`, so no other request interleaves with its writes. `Board.atomically { }` is one undo step and one board revision; when its body throws, the changes it made are reverted (announced as normal changes, not recorded) and the error is rethrown. Layout ops move objects through one private `Board.shift` (groups by their leaf members, each object once) inside `Board.deferringRefits { }`, which holds group re-fits until the op's end and then re-fits each affected group once; group frames are stale only inside that scope. `size: "fit"` on an `object.update` without `frame.x`/`y` takes `Board.refitFrame`: grown from its top-left corner when that overlaps nothing it didn't already, else from the first other corner that doesn't (`Layout.refit`: top-right, bottom-left, bottom-right), else the free slot nearest the top-left-grown frame among those whose origin is within the frame's longer side of it (`place(_:)`'s rule, in view first, the object and its groups not blocking; `freeSlot(within:)`), else top-left anyway. Fitted results (and fitted batch ops, after the whole batch) carry `overlaps`, `Board.overlaps(of:)` by `layout.check`'s overlap rule, when not empty. Batch side effects stay per revision, not per op, in the app too: `avoid` arrows, whose routes depend on every tile, re-route once after a burst of changes (`ShapeLayer.rerouteAvoiding`: next main-queue turn or before the layer draws or renders), keeping the drawn route until then.

`layout.check` judges what is drawn: tile frames are whole tiles; arrows route with `BoardGeometry.routing(rows:)` (a value snapshot of the board taken when the call arrives, computed off the main actor) (line-bound ends by the model scroll rule, over each bound code tile's rows as it wraps them at its frame width: `CodeRows(file:width:)`), routed on from the drawing layer's last routing (`Board.settledRouting`): `ConnectorRouter.route(previous:)` keeps every `avoid` route nothing has touched since, so on a settled board the check computes exactly the routes, tracks and labels on screen, and after a change it computes what the layer will draw when it settles. Labels are placed as the drawing layer places them (`DrawingStyle.arrowLabel` for the chip size, `ConnectorRouter.placeLabels` for every arrow on the board together, against `BoardGeometry.blocksRoutes` objects, group title bands, other arrows' lines and each other) and reported as `labelOverlaps` when they lie on a blocking object (their own ends included), a group's title (the group id), another label (that arrow's id), or another arrow's line (`lines`), each with the caption and the chip's frame (an arrow's own frame leaves its label out). `arrowOverlaps` are pairs of arrows collinear within `ConnectorRouter.overlapTolerance` (3 pt) for at least 2 pt (`length` in points, `at` the middle of the first shared run); `arrowIntersections` are pairs whose lines cross (`count`, `at` the first crossing); both come from `ConnectorRouter.overlaps`/`intersections` over the same routes. The drawing layer routes the whole board again (incrementally) whenever a tile, blocking shape, or group comes, goes, or changes frame, blocking or flow, and whenever an arrow changes (`ShapeLayer.scheduleRouting`), so a label never stays under a tile that arrived after it and the check and the picture agree; while a tile is dragged or a code tile scrolls, only the arrows bound to it re-route (each alone), and the board routes once the change pauses (`ShapeLayer.routingPause`, 0.25 s) or ends. With `ids` or `rect`, a crossing or label overlap counts when the arrow or anything it crosses or lies on is in scope (a new tile checked by its id reports the labels it covers); line-bound arrows whose ends lie within 300 pt of a scoped object have their tiles' rows read for it. Unfilled rects and ellipses are annotations (a box drawn around or across things): like ink and arrows they never take part in `overlaps`. A code tile's range compares its rows (`ObjectMeasure.codeRows`, wrapped at the frame's natural width in whole points, so a zoomed fit tile's 611.99… pt is still its 612) with the frame and a taller range is `scrolls`, never `overflow`: code wraps at its width and scrolls to its range, so only its height can be short, and a fixed-height viewer usually means to scroll; a caption wider than the frame (`ObjectMeasure.captionWidth`, the header's own `CodeCaption.string` and `CodeMetrics.captionInset`) is `truncated`, not overflow; so is a note whose table doesn't fit its frame's width even with its cells wrapped and words broken (`NoteRenderer.tableShortfall`, via `ObjectMeasure.note`: `what: "table"`, `x` the points of width it lacks); follow tiles (`followOf`) are fixed-size viewers and are skipped for both.

## Swift tile protocol

Every tile's content view conforms to `TileContent` (`Sources/CanvasApp/TileContent.swift`); `TileFrameView` supplies the shared chrome (title bar, content zoom control and the body at its zoom, drag, corner resize and ⌥-drag proportional resize, lifecycle badge, zoomed-out card) and `TileFactory` maps an object type to its content view.

```swift
@MainActor
protocol TileContent: NSView {
    func setLive(_ live: Bool)                                  // false: detach heavy resources, show the card
    var liveZoom: CGFloat { get }                                // below this zoom the tile is its card (default 0.3; terminals 0.15)
    func render(_ request: TileRenderRequest) async -> TileRender   // offscreen image for view.render
    func cardSnapshot(_ deliver: @escaping @MainActor (NSImage?) -> Void)  // default: render at card scale
    func whenLiveReady(_ ready: @escaping @MainActor () -> Void)  // just made live: call once the live view is drawn (default: at once)
    func showSnapshot(_ show: Bool)                              // view.snapshot: cover Metal/WebKit content
    func mentionTarget(at point: NSPoint) -> MentionTarget?      // what a Hyper-click here mentions (element level)
    func outline(for target: MentionTarget) -> NSRect?           // hover highlight, in this view's coordinates
    var takesKeyboardFocus: Bool { get }                         // terminal, browser: true; code, note, HTML: false
    var surfaceLuminance: Double? { get }                        // what default-ink drawings over it contrast with (page background, image, terminal theme); nil: the app's own (default); post .tileSurfaceChanged on change
    var accessibleText: AccessibleTextElement? { get }           // VoiceOver's read-only text area while live: code lines (numbered), a terminal's screen; built only when asked (default nil)
    func update(_ object: CanvasObject)                          // a new revision of the backing object
}
```

`render` draws the content offscreen for `view.render`, independent of liveness, window, Space, and viewport: from the tile's model (or an AppKit view that draws itself anywhere, like a code tile's header, drawn offscreen), never by capturing what is on screen. `TileRenderRequest` = `size` (the body in the content's points: the frame below the title bar, ÷ the tile's zoom), `scale` (pixels per point, the render's × the tile's zoom), `full` (the whole content, not the frame's window), `appearance` (resolve colors under it). `TileRender` = `image` (points, top-left at the body; `max(size, contentSize)` when full), `contentSize` (the content's extent at that width; overflow = content − size; a code tile's is its range, `CodeDocument.content`, which is what `size: "fit"` sizes), `state` (`rendered`, or `placeholder`/`failed` with a `reason`; never `rendered` with a blank image). The renderer cancels a render at the request's deadline (tiles should return what they have when cancelled) and reports a tile that still hasn't answered a second later as a placeholder. Tile chrome (title bar at 1×, with the content zoom's % when not 100%, and border) is drawn around the image by the renderer, the image at the tile's zoom inside the frame; app chrome never is.

Zooming never redraws the scene: everything in the document (tiles, groups with their titles and borders, drawings, selection rings) is drawn in document coordinates and scales with the board, so its size relative to everything else never changes. Only window chrome (toolbar, tray, pills, edge pills), the dot grid, shape resize handles, selected tiles' resize handles, and attention markers stay screen-sized. A selected tile's handle (`TileHandles`) is a window-space view above `AttentionLayer`, so a marker ring never hides it; it takes no clicks: `TileFrameView`'s corner grip reaches under it, `TileHandles.reach` screen points past the corner, for every tile in a group or not. A marker's ring is its own view (`MarkerRing`) that pulses three times when the marker appears or its message changes; the bubble never fades. Bubbles keep off their object's header: `PillLayout.Marker.header` is the title bar plus `TileContent.headerHeight` (a browser's address bar, a code tile's header). Markers (`AttentionMarker`) live in `AttentionLayer`, a window-space view over the scroll view that passes clicks through except on a bubble; `CanvasView.layoutPills` places each around its object's on-screen rect, with the edge pills (`AttentionEdgeView`), on every bounds change (each pan and live-pinch step), so a marker tracks the zoom continuously and keeps its fixed size. Edge pills cover no tile (`PillLayout.place(... bands:)`): the nearest stretch of their edge clear of every on-screen tile, pill and prompt, else a chip in `CanvasView.chromeBands` covering the least tile area there, then nearest the ideal spot (the window controller's free parts of the toolbar row, left and right of the drawing toolbar, in window coordinates; none while the toolbar is hidden), else the earlier compromise on the edge. While `CanvasView.chromeHidden` (View › Hide Board Chrome) marker views are hidden and left out of placement; blocked terminals' are not. Cards are what the live tile shows: code cards draw the tile's own header view offscreen (`CodeHeaderBar.prepareForSnapshot`, its real controls) above rows drawn from the model at the tile's scroll; HTML cards are the live page's last capture. Going live, `TileFrameView` keeps the card over the content, which renders beneath it, until `whenLiveReady` fires (HTML: the page's first `view.rendered` after it attaches, once WebKit has presented that frame, `WebStage.afterNextPresentationUpdate`; browser: the page loaded and presented), at most `TileFrameView.revealLimit` (2 s).

Arrows, shapes, and groups have no tile; the board draws them.

Tiles never read or write the board store directly; they go through the board model on the main actor, which persists and broadcasts events.

### Code navigation

Code views get language features by conforming to `CodeNavigationHost` (`Sources/CanvasApp/CodeNavigation.swift`) and attaching a `CodeNavigation(host:board:tile:accessories:reservedWidth:)`:

```swift
@MainActor
protocol CodeNavigationHost: AnyObject {
    var navigationPath: String { get }                           // board-relative path of the file shown
    var navigationView: NSView { get }                           // the view showing rows; its coordinates are the host's document coordinates
    var navigationLineHeight: CGFloat { get }                    // row height, so panels open below the hovered line
    func sourcePosition(atViewPoint point: NSPoint) -> (line: Int, character: Int)?  // point in navigationView; 1-based line, 0-based UTF-16 column (a wrapped line's continuation rows map past the break); nil on peeked base rows/gutters
    func reveal(line: Int)                                       // scroll a 1-based line into view
}
```

The controller adds a hover tracking area to the view only while `setActive(true)` (hosts deactivate it when the tile goes not live: tracking areas on hidden tiles are rebuilt on every frame of a pan), handles ⌘/⌥⌘-click and right-click on it through an app-level event monitor (Hyper stays with `HyperMonitor`), extends the view's own `menu(for:)` rather than replacing it, and places an Outline button in the host's header (`accessories:`), inside the trailing `reservedWidth` points the host keeps free (`CodeHeaderBar.reservedTrailing`). Hosts call `contentChanged()` when they scroll or show new content, which dismisses hover and panels.

- **Outline** lists `LSPSymbol.outline`: every top-level symbol and the members of modules, namespaces, classes, enums, interfaces, structs and objects, never what a function or method holds (its locals). Its panel (`NavigationPanel.filterList`, shared with Find References and a list of several definitions) takes the keyboard, because the user asked for it: a filter field narrows the rows to names containing the text, ↑/↓ move the highlight, Return reveals it, Esc closes; closing gives the keyboard back to whoever had it (a terminal through its own focus path, `CanvasView.returnKeyboard`) unless something else took it. Hover panels never take it.
- **From the keyboard** (Code ▸ Go to Definition ⌃⌘J, Open Definition in New Tile ⌃⌥⌘J, Find References ⌃⌘R, Outline ⌃⌘O, on the focused code tile, else the one selected, else the one last clicked (`KeyboardFocus.codeTarget`), and with none a notice says there is no code tile to act on; `CodeTile.navigate`): no pointer names a symbol, so they act at the rows' selection, else at the first name that isn't a declaration keyword from the tile's first range line (else its top row) down through its range and the rows in view (`CodeSubject.first`: `write_usage` in `    def write_usage(self, …):`; a tile aimed at a closing brace, a comment or `@MainActor` means the next line's name). With no name there, a message in the tile says to select one; the commands never do nothing silently.
- **Find References** lists the references, each line once (servers list a line twice, e.g. a re-export's two names), in a filter list like Outline's that takes the keyboard (↑/↓, Return, Esc; ⌘↩ is Open All); a row opens that one (`Board.openForNavigation`, see Navigating to code). The list's **Open All** lays out every reference as a code tile (`Board.openExcerpts`): the reference line with 3 lines of context either side (clamped to the file), captioned "Reference N of M to `name` · L…", measured like `size: "fit"`, stacked top to bottom (a new column past 2400 pt) in a group titled "M references to name" in the free slot nearest the tile (`Board.place(near:)`); one undo step; the board pans the least that shows the first reference.
- **Without a language server** (`CodeNavigation.textFallback`: `LSPError.unavailable`, `unsupportedLanguage`, `startFailed`, `serverExited`; a timeout or the server's own error is shown as it is): Go to Definition, Find References and Outline answer from text (`TextNavigation`, CanvasCore). The search root is the board root for a file under it, else the repository holding the file (`searchRoot`). References: `git grep -n -z --column -w -I -F --max-count 60 --untracked -e <name>` (`--no-index --exclude-standard` outside a repository) through `GitRunner`, at most 200 matches (`truncated` says there were more). Definition: the same word matches filtered to lines that declare the name (`declarations(inLine:pathExtension:)`), ranked this file, then its language family, then the rest (`rankDeclarations`). Outline: `TextNavigation.outline` (tree-sitter `SyntaxSymbol`s with their `kind`, minus anything nested in a function, plus unindented pattern declarations on lines no symbol starts on). Every such list is titled as text search ("no language server") and carries the server's error as its one-line `note` (`NavigationPanel.filterList(note:)`).
- **Workspace symbols** (`LanguageService.workspaceSymbols`, `workspace/symbol`): one request per language and project root among the given files, starting servers as needed; a project whose server is missing or fails adds nothing. Go to asks with the files the board's code tiles show, else the first file of the language most listed files are in.
- **Call hierarchy and type definitions** (`LanguageService.prepareCallHierarchy`, `incomingCalls`, `outgoingCalls`, `typeDefinition`; LSP `textDocument/prepareCallHierarchy`, `callHierarchy/incomingCalls`/`outgoingCalls`, `textDocument/typeDefinition`): the client offers both capabilities at `initialize`, and each request first checks the server's answer (`callHierarchyProvider`, `typeDefinitionProvider`): a server without it throws `LSPError.unsupportedRequest` naming the command and the capability (sourcekit-lsp 6.3 has no type definitions) instead of an empty answer. Items go back to the server verbatim (`LSPCallHierarchyItem.json`, its `data`); incoming and outgoing calls are asked of the server of the item's file, with that file open for the request.
- **Projects**: a file is read by the server of its language and project: the nearest directory with one of the language's root markers (`Package.swift`, `package.json`, …) within the board root, or, for a file in another worktree of the board's repository, within the board root's place in that worktree (`GitWorktree.counterpart`), so a worktree's files are that checkout's project with its own build index; anything else, its directory.
- **Paths** are real paths (`GitDiffEngine.realPath`, realpath(3)), never `resolvingSymlinksInPath`/`standardizedFileURL`, which turn `/private/tmp` and `/private/var` back into `/tmp` and `/var`: a project root spelled that way is one sourcekit-lsp can't match to its package's files, so it answers from fallback settings (no index answers; its semantic AST builds can crash sourcekitd).

### Navigating to code

`Board.openForNavigation(_ aim: CodeAim, from source:, preview:, extra:)` (CanvasCore, `CodeNavigationTarget.swift`) is the one rule for every user navigation to code except a terminal's ⌘-click (`Board.openCode`, its own preview): Go to's file/symbol/Recent rows (source nil), definitions (the code tile), changes-tile lines (`preview: true`, `extra: diffBase`), an HTML page's `code.open` and a note's `path:line` link. In order: the tile `Board.tileShowing(aim, near: source's frame)` finds anywhere on the board (a code tile, any author, not a follow tile, showing `aim.path` at exactly `aim.range`, else a captioned one whose range contains it; exact first, then in view, then nearest, then topmost): nothing changes and `CodeOpened.existing` is true, and the board goes to it (`CanvasView.goToShown`: selected, `Layout.present`; a definition inside the clicked tile scrolls it instead). A terminal's ⌘-click (`Board.openCode`) asks `tileShowing` first too; with `preview`, the tile this source created last (`codePreviews[source]`) while its `rev` is unchanged and it is still `isNavigationSurface`; a navigation-surface tile in view showing `aim.path`, nearest the source's center (the viewport's without a source); else a new code tile (`place(near: source, shrinkingTo: followMinimumSize)`, or at the viewport center), which becomes the source's preview with `preview`. `isNavigationSurface`: a code tile the user created whose last writer is the user, with no caption, no `parent`, no group listing it, no `followOf`. Re-aims (`Board.reaimForNavigation`, also a terminal's ⌘-click preview and a follow tile's history strip) are `Board.unrecorded` updates credited to the user (logged, never an undo step); the answer (`CodeOpened`) carries the `CodeReaim` (tile, `before`, `after` aims). Without a viewport (no window) every tile counts as in view.

Back/Forward (`NavigationHistory`, per `CanvasView`): `CanvasView.navigating(landing:_:)` wraps a navigation, recording `Entry(from:, to:, reaim:)` with the viewport before and after (nested navigations are one entry; one that neither moved the view, re-aimed nor changed a step's selection is dropped; 100 entries). An ⌥⌘-arrow step (`CanvasView.moveToNeighbor`) records its entry directly with `selectedBefore`/`selectedAfter`, and `Move.selection` selects that object again on Back/Forward and visiting `landing` in `RecentLocations` (20, newest first, one per path and start line; Go to shows 5). Back pops an entry onto Forward and shows `from`, re-aiming `reaim.tile` from `after` to `before` only while `Board.restoreAim` finds it still navigation surface showing `after`; Forward the reverse. A new entry clears Forward. The window takes ⌘[ / ⌘] ahead of the focused view (`CanvasWindowController.navigationAction`); with a browser page (not its address field) holding the keyboard they go to the page's `goBack`/`goForward`.

### Code tiles

One view per tile, no modes: the whole file (the base version for a deleted file), scrolled to `props.range`, the range tinted only while the tile shows rows outside it (`CodeMetrics.tintsRange`: a tile fitted to its range, or a whole-file range, shows no tint; live, cards, and renders alike). Geometry is `CodeMetrics` (CanvasCore): fixed 16 pt rows, the 12 pt system monospaced font (every column `charAdvance` wide, tabs to 4 columns, East Asian wide characters and surrogate pairs 2), a gutter of line numbers plus a sign column, and header/caption/history strip heights; `object.measure` uses the same numbers. Rows soft-wrap at the tile's text width (`CodeMetrics.textColumns`, `CodeMetrics.wrap`): a line wider than the text column continues on rows with no line number (a faint ↪ instead), its gitsign continuing down the gutter, and its text indented by the line's own indentation plus 2 columns (at most half the row); tabs expand against the unwrapped line and breaks never split a surrogate pair. Nothing scrolls sideways. A resize by the user rewraps live, keeping the top line in place; any other change of the tile's natural size (an agent's `object.update` frame or `size: "fit"`, undo) re-aims the scroll at the range by `CodeMetrics.scrollOffset` (`CodeTile.resizedElsewhere`, called by `CanvasView` when the content's size changed under it), so a fitted tile shows exactly its range. The model is CanvasCore's `CodeDocument` (built off the main thread from `GitDiffEngine`'s `FileDiff`): `GitSign`s from the diff's change records (added bar, modified bar, deleted wedge on the top edge of the line after the deletion, `lineCount + 1` at the end of the file), per-line highlight runs (`SyntaxLines`) for both sides, and the header's status and warning (`noBase`: no commits yet / no default branch / no merge-base, `diffTooLarge`, deleted). A file not in the base is `added` (every line an added bar; `untracked` when git doesn't track it yet: "new file, not tracked by git yet"), unless git ignores it (`git status --porcelain --ignored=matching` says `!!`, e.g. a node_modules frame): `ignored`, plain source with a quiet "ignored by git". The base picker names the base as the changes tile's does (`ChangesBaseChoice.title`: Uncommitted changes, Branch vs origin/main, vs <commit>); the status adds the base's commit unless the picker shows it (a commit typed as its sha), and `CodeDocument.baseDescription` (`against merge-base with origin/main b57db4f`) is the picker's and status's tooltip. `CodeRows` inserts peeked base lines above the lines that replaced them (entries: logical rows) and maps entries to visual rows (wrapped entries take several): `row(_:)`/`segment(_:)` give a visual row's logical line and slice, `index(ofLine:)` a line's first visual row, `rows(ofLine:)` all of them; `WrapText` measures each line's columns once per load so rewrapping skips lines that fit. Selections are `CodeRows.Position`s (entry + UTF-16 offset), so they survive rewraps and ⌘C copies logical lines; mentions, LSP positions, range tint, edit flash, peeks, hunk jumps, `reveal`, and `aim` all go through the same mapping, and cards, `render`, and the live view draw through one `CodePainter`. `CodeEdits.changes` diffs the texts of consecutive loads of the same file: those rows flash for 3 s (a follow tile also jumps to the first). A tile with `pinnedCommit` shows the file as of that commit instead (`GitDiffEngine.pinned`: `rev-parse` then `cat-file blob`, `FileDiff.State.pinned`, or `.pinUnavailable` with the reason as its notice): no signs, no base picker or change stepping, no Edit Here, header status `pinned at <sha7> (<revision>) · read-only`, and its mentions carry the commit (no side), so they quote those lines; `object.measure`, `layout.check`, and line anchors read the same text (`NoteSource.read` with the commit). `FollowLock` holds a follow tile's re-aims for 10 s after the user scrolls, clicks, or selects in it, counting them ("N new ▸"), then shows the newest.

Ranges stay on their code (`CodeAnchor`, `NoteAnchor.resolve`): a code tile with a `range` that isn't a follow tile or pinned to a commit re-finds its range whenever it installs a new text of the file (live reloads, and the reload before a render or card) or its `range`/`anchor` change: by the text the range held when the tile last found it (in memory), else `props.anchor` (the range's first line, trimmed). A range found elsewhere, or longer or shorter by lines inserted or removed inside it, is written back with its first line as `anchor` by `Board.reanchor`: bookkeeping like `writeBookkeeping` (no `rev`, undo step, or log; a board revision and `object.updated`), so agents, `layout.check`, measure and renders see the moved range and an agent's `object.update rev:` still holds. Undo restores `range` and `anchor` together, and the tile re-finds the range from there. A range whose code is gone keeps its lines, loses its tint, and the header shows "⚠︎ stale: …" before the status. An `object.update` (or any re-aim) that changes `range` or `path` without an `anchor` drops the old `anchor` (it named another line); an agent may pass `anchor` itself. `object.get` on such a tile adds `rangeStatus` (`AnchorStatus`): the tile reloads the file unless it is current (re-anchoring as above, and the returned `object` carries the result) and resolves the range with the text it last found there (`ApiRouter.codeRangeStatus`), so a first line repeated elsewhere never passes for it; without a tile, by `props.anchor` alone. Links are positions: `<canvas-link line=>`, `<canvas-code lines=>` and a note's `path:line` don't move with the code (`<canvas-code>` shows a stale badge when its `symbol` is lost); only ranges that anchor do.

The view draws only visible rows (a CTLine per visible row, cached only while visible) and scrolls itself, with no NSScrollView; not live, it keeps no line cache, layer contents, tracking areas, or views in the window, and cards, `snapshot()`, and `render(_:)` draw rows straight from the model.

Mentions: a row is the line on the side it shows; a sign in the gutter is the whole change (a deletion: its base lines, `side: old`); a peeked row is a base line (`side: old`, `commit` = the base). While a tile shows changes against a base, its new-side mentions carry `side: new` and that base's commit.

Follow tiles (`props.followOf`): `Board.follow` (`follow.report`) re-aims the terminal's one follow tile (at `range`, else at the hunk of `changes` spanning the most lines, the last of equals: `Board.followAim`; `changes` is kept as `props.lastChanges`, which the tile flashes when it loads the file fresh, and a re-load of the file it shows flashes whatever changed), creating it with `Board.place` beside the terminal (shrunk to stay wholly in view when the terminal is on screen, see Placement). Reports are ignored while the terminal's `props.follow` is `false`, and for paths `FollowFilter.follows` rejects: outside the board root, the terminal's cwd, and every other worktree of their repositories (`GitWorktree`: directories whose `.git` leads to the same common git directory, read from the filesystem, no git process; such a file keeps its absolute path, so the tile diffs it in its own worktree); under the temp directory (`NSTemporaryDirectory()`, `/tmp`, `/var/tmp`) unless the project containing it is there too; missing, a directory, larger than the code tile's limit (`GitDiffEngine.maxFileSize`, 4 MiB, by its size, unread), a binary extension (images incl. svg, pdf, archives, objects, media, fonts), or a NUL byte in the first 8000 bytes. The tile keeps its last accepted file. Deleting a follow tile other than by undo/redo sets its terminal's `props.follow` to `false` in the same undo step; `Board.setFollowing` (the terminal's "Follow Files" menu item) sets it back to `true` (the next report creates the tile) or to `false` and deletes the tile, one undo step. Deleting a terminal deletes its follow tiles in the same step. The history (`props.history`, newest first, at most `Board.followHistoryLimit` = 8) records each location with its action; a location revisited moves to the front and stays `edit`/`write` once edited, and past the limit the oldest reads go first, so every edit of a parallel burst (omp lands three edits within 50 ms) stays listed. The history strip (`CodeHeaderBar.fitStrip`) marks edit and write chips with a pencil in orange, always shows the current location, then the edits, then as many of the newest reads as fit whole, in history order; the oldest reads drop off a narrow tile first instead of the strip clipping or squeezing the current one. A re-aim to another file and back before the other file loaded (two reports a millisecond apart) still scrolls to the newest range when the load installs the same file (`CodeTile.rangePending`). A code tile whose file is on neither the disk nor its diff base (`FileDiff.State.missing`, checked again 0.6 s later so a delete-and-recreate save doesn't count) calls `Board.codeFileVanished` with the history paths found on disk: a follow tile steps back to the newest `history` entry still there (its `path`, `range` and `action` as `lastAction`, no edit flash) and drops the entries that are gone; with none left, or for a ⌘-click preview in `codePreviews`, the tile is deleted as a replay would (no undo step, and a closed follow tile doesn't turn its terminal's `follow` off); the activity log credits `system`. Other tiles are kept.

### Branch-anchored tiles (`ref`)

Code, note, and HTML tiles take `props.ref`, a branch (or any ref), instead of one checkout (`RefSource`, `GitRefs`, CanvasCore). Paths keep their meaning: relative to the board root's place in the repository, and an absolute path in any worktree of the repository names the same repo path (`RefSource.url(for:)`). Each resolve (`GitRefs.resolve(repo:ref:lastKnownSha:)`) picks one state, which the code tile's header leads its status with (`RefSource.label`):

- **live** (`live in <worktree>`): a worktree of the repository (the common git dir, found from the filesystem, `GitRefs.liveWorktree`) has the branch checked out. The tile reads that working tree: a code tile diffs against its `diffBase` there (default its merge-base), shows the base picker, reloads on edits, and its mentions, Edit Here, and language features name the file in that worktree.
- **objects** (`<ref> @ <sha>`): the ref resolves but no worktree has it. The tile reads git objects at its commit, read-only like `pinnedCommit`; mentions carry the commit.
- **merged** (`merged in <sha>`): the ref no longer resolves and the default branch (origin/HEAD's target, else `main`, else `master`) contains the last SHA. The tile reads the commit that brought it in: the earliest commit on the default branch's first-parent line descending from it (the merge; the SHA itself when it was fast-forwarded).
- **missing** (`branch gone, showing <sha>`): the ref no longer resolves and the default branch doesn't contain the last SHA (a squash merge, or a branch deleted unmerged). The tile reads that SHA's objects while they exist; once they are gone (gc), it says `unknown ref <ref>`.

Every resolve records the SHA it settled on (the live worktree's HEAD, or the ref's commit; never the merge commit) as `props.refSha` (`Board.recordRefSha`: bookkeeping, no rev, no undo step, and only while `props.ref` is still that ref), which is the last SHA the merged and missing states fall back to. `object.create`/`object.update` (single or in a batch) resolve a new `ref` before writing it and add `refSha`; a ref that resolves to nothing, with no `refSha` whose objects remain, is `not_found`, one that isn't a ref name `invalid_params`, and clearing `ref` clears `refSha`. A tile re-resolves on every load: code tiles whenever HEAD, a ref, or a worktree of the repository they hold moves (`.gitRefsMoved` from `GitDiffEngine`'s repository stream), notes on the same paths through their own file events. `object.measure`, `size: "fit"`, `layout.check` line rows, `rangeStatus`, and `agent.prompt` mentions read the same place (the prompt, synchronous, uses the live worktree or else `refSha`).

Precedence: a code tile's `pinnedCommit` wins over `ref` (the ref is neither read nor resolved). A note's or HTML tile's `ref` wins over its `root`. Ranges re-anchor under a ref as on the working tree (`CodeAnchor`), so a range follows its code as the branch moves.

Notes and pages keep their body inline; `ref` sets where the files they name are read: the note's link root and excerpt fences (a fence's own `@<sha>` still wins; `LinkReading.fences`), `path:line` links (the code tile they open carries the same `ref`), and a page's `code.excerpt`/`code.open`. Images and other page files load from the live worktree, else from the board's checkout; a symbol-only fence searches the live worktree, else the board's checkout.

### Changes tiles

`ChangesTile` (`Sources/CanvasApp/Changes/`) draws a `ChangeSet` (CanvasCore) through `ChangesPainter`, live, as its card, and for `view.render`, with `ChangesMetrics`/`ChangeRows` geometry (header strip, the file list with more than one file, file rows, hunk rows, `CodeMetrics` line rows soft-wrapped at the tile's text width by `CodeMetrics.wrap` with the code tile's hanging indent and a faint ↪ in the gutter), which `object.measure` and `size: "fit"` use too (the file list open, deleted and viewed files folded, lines wrapped at the fitted width). The header of the file under the top of the rows stays pinned there while its hunks scroll (`ChangeRows.stickyFile`), pushed up by the next file's, and drawn over the rest of the file's last row when only a sliver of it shows above the next file. The header strip (`ChangesPainter.headerLayout`) holds the summary (`ChangeSet.lead`, drawn with ▾, then `counts`: `Uncommitted changes · 3 files · +40 −12`, `pr-1041 vs origin/main · 6 files · +62 −0`: the reviewed worktree's branch, or `HEAD` detached, against `baseName`), the keys when they fit beside all of the summary (`ChangesMetrics.hint`), and a filter field (an `NSSearchField` while live, drawn text in cards) that limits the list and the sections to files whose board path contains its text. A click on the lead opens the base picker (`ChangesBaseChoice`: `HEAD`, `merge-base` titled `Branch vs <GitWorktree.defaultBranch>`, the typed revision when current, and Commit or Ref…, a popover field); a pick is `object.update` of `props.base` by the user, one undo step.

Listing (`ChangeSet.load`, all through `GitRunner`, off the main thread): the reviewed directory is the board root, or `ChangesSpec.root` resolved against it when that lies in a worktree sharing the board repository's common git directory (`GitWorktree.sameRepository`, from the filesystem); any other `root` is refused (`notice`, nothing listed). `rev-parse --show-toplevel` from that directory; the base resolved as code tiles resolve theirs (`ChangesSpec`: `base` default `HEAD`); `paths` (default the reviewed directory) turned into repository-relative literal pathspecs, and anything resolving outside that worktree refused; `git diff --raw -z -M <base>` plus `git ls-files --others --exclude-standard` (untracked = added), at most 300 files (`omitted` counts the rest); each file's texts and hunks from `GitDiffEngine.diff` (a rename: the base text of its old path and `git diff -M -U0` between the two paths); hunk status from `git diff -U0` (index → working tree), `git diff --cached -U0` (HEAD → index) and, for a base older than HEAD, `git diff -U0 HEAD` (`ChangeHunk.status`: `partial` where the index differs from both the working tree and HEAD over the hunk, i.e. staged and edited again). Board paths are relative to the board root when under it, else absolute (another worktree's files). Hunk ids (`ChangeHunk.id`) hash the path and the unified lines (FNV-1a), so they survive line shifts elsewhere; a file's `fingerprint` hashes its hunk ids, status, and notice. The live tile reloads on `FileEvents` (FSEvents) under the repository's top level, and the worktree's own git directory when it lies elsewhere (a linked worktree's `<common>/worktrees/<name>`), ignoring the git directory except `index`, `HEAD`, `packed-refs`, and `refs/`, and on `.gitDiffBaseChanged` and `.reviewPatchApplied`.

Two commits (`ChangeSet.loadCommits`, `CommitChanges.swift`): with `ChangesSpec.head` (any commit or ref) the tile compares commits instead of a worktree, from git objects alone, never touching a working tree or the index: `head` is resolved with `rev-parse --verify <head>^{commit}`, the base as written (`merge-base`, the default with `head` or `ref`: the default branch; `HEAD` with a `ref`: the ref itself), and the diff's base is their `git merge-base` (`base...head`, a pull request's view, so commits the base gained since the fork never show reversed; a ref gone and merged, `GitRefs` `.merged`, takes the merge's first parent once the base holds the head). `git diff --raw -z -M --no-abbrev <merge-base> <head>` lists the files with both blob ids; `git cat-file --batch-check` then `--batch` reads the blobs, at most `GitDiffEngine.maxFileSize` each (larger: `too large to show`; a NUL in the first 8000 bytes: `binary file`; mode 160000: `submodule`); one `-U0` `git diff <merge-base> <head> -- <paths>` gives the hunks of files at the same path, a renamed file's two blobs are diffed on their own, an added or deleted file is all one hunk. Every hunk is `committed` and every file `ChangedFile.readOnly` (`blobs` set): no Stage, Unstage, or Discard buttons, `s`/`u`/`r` and every `ReviewPatch` builder refuse with `ChangesFailure.readOnly`, and the header offers reading keys only. The header's lead is `<head> vs <base> · <merge-base>..<head>` (short SHAs; `(merged in <sha>)` or `(branch gone)` after the head for a gone `ref`). Viewed fingerprints hash the path, status, notice, old path and both blob ids, so a mark holds while neither side of that file changes, wherever the head moves. A live tile watches only the common git directory's refs (`refs/…`, `packed-refs`). A click on a line opens a code tile pinned (`pinnedCommit`) to its side's commit: the merge-base for a removed line (at the file's old name), else the head (`CodeAim.pinnedCommit`, and `ref`: navigation re-aims or reuses only tiles showing that same version); a mention of a new-side line names the head commit (`· at <sha>`). A commit or ref the repository lacks lists nothing: the notice is `no commit <ref> here; fetch it: <command>` (`ChangeSet.fetchCommand`: `pull/N/head` → `git fetch origin pull/N/head:refs/pull/N/head`, `<remote>/<branch>` → `git fetch <remote> <branch>`, a commit id as it is, any other name into that local branch). easl never fetches: every git process runs with `GIT_NO_LAZY_FETCH=1`, so a partial clone's missing blob is missing, not fetched.

`ChangesSpec.ref` (a branch, instead of `root`) is resolved by `GitRefs.resolve` with `props.refSha` as the last known commit: `.live` reviews the worktree that has it checked out (the board root when that is the board's own checkout) exactly as a `root` tile would; `.objects`, `.merged`, and `.missing` compare that commit with the base as above, read-only. The tile writes the commit it read back to `props.refSha` (`Board.recordRefSha`: credited to the system, no undo step, only while `props.ref` is still that ref), which is what it keeps reading once the branch and its worktree are deleted; `object.create`/`object.update` resolve a changes tile's `ref` as they do a code tile's (`ApiRouter.referenced`), their `not_found` naming the `git fetch` that brings it (`ChangeSet.missing`). `head` with `ref`, or `ref` with `root`, lists nothing and says which to drop.

Actions (`ReviewPatch`, `ReviewGit`): every Stage and Discard is one unified patch, applied with `git apply --whitespace=nowarn -` in the repository's top level (the reviewed worktree's), and its undo is the same patch applied the other way round (`-R` toggled). Patches only name repository-relative paths (no `..`, no `.git`, `ReviewPatch.checkPath`) of files the listing found, and never carry mode changes except a created or deleted file's own.

| Action | Patch | Applied | Undo |
| --- | --- | --- | --- |
| Discard hunk / file, base HEAD | base → working tree over the hunk's changes (all of a file's; a created file is its deletion, a deleted file its re-creation from the base; a renamed file keeps its name), 3 lines of context, from the texts the tile shows | `git apply -R` to the working tree (the index is untouched) | `git apply` of the same patch: the hunk comes back exactly |
| Discard hunk / file, base older than HEAD (`ChangeSet.includesCommits`) | HEAD → working tree changes (`git diff -U0 HEAD`, read at the moment and checked against HEAD's text and the working tree the tile showed) that touch the hunk's working-tree lines, or all of the file's; an untracked file is its deletion, a file deleted since HEAD its re-creation; committed hunks refused (`ReviewPatch.discardUncommitted`) | `git apply -R` to the working tree | `git apply` of the same patch |
| Unstage hunk / file | HEAD → index changes (`git diff --cached -U0`, checked against both texts) that touch the hunk's lines in the index (`ChangeHunk.indexSpan` through the index → working tree changes), or all of the file's; a file new in the index is its creation, a staged deletion its removal (`ReviewPatch.unstage`) | `git apply --cached -R` | `git apply --cached`: staged again |
| Stage hunk / file | index → working tree changes (`git diff -U0`, read at the moment of staging and checked against both texts) that touch the hunk's working-tree lines, or all of the file's; an untracked file is added whole, a file deleted from the working tree removed | `git apply --cached` | `git apply --cached -R`: the index is as it was (an added file is untracked again) |
| Discard / Stage / Unstage selected lines | the hunk's patch as above with only the selected changed lines (`ReviewPatch.LinePick`; a patch not built from the tile's own texts finds a selected line in the other version by its text in the change there, `ReviewPatch.matching`). Within a change the n-th removed and n-th added line stay paired. Forward (stage): unselected `+` dropped, unselected `-` turned into context; reversed (discard): unselected `-` dropped, unselected `+` turned into context; headers recounted | as the hunk | as the hunk |

A patch that doesn't apply (the lines changed since the tile read them, the index is locked by another git) changes nothing and the tile says so in its header (`ChangesFailure`); staging a hunk the index already holds is refused as `already staged`, unstaging one it doesn't as `not staged`, and discarding a committed hunk (`HunkStatus.discardable`; a file whose hunks are all committed, `ChangedFile.discardable`) as `committed: Discard only puts back work not committed yet`: the tile shows no Discard button there. Discard asks first, by key or click alike (`DiscardQuestion`, one pending question naming the file, hunk id and picked lines, with the header's hint: the button's red "Discard?" and the hint are painted from it together): `r` asks and only ⌘⌫ answers (`DiscardByKey`; a second `r` never discards, so text typed into the tile can't), a click on a Discard button turns it into "Discard?" that a second click on it confirms (the header says how to go on). The question never times out; any other press or key in the tile, the keyboard leaving it, or anything else the header says drops it; once applied, the board's notice says `Discarded <path>, lines 13–20 from your files · ⌘Z undoes` (`ReviewPatch.discardNotice`, undo's own naming). Unstage takes Stage's button once all of a hunk (or file) is staged; `u` unstages the selection or the current hunk. `ReviewGit` applies patches one at a time in the order asked, so an undo right after its action waits for it. `Board.recordReview` records an applied action as one undo step: the tile's `props.reviewed` entry (`ReviewPatch.entry`: action `stage`, `unstage`, or `revert`, path, scope `file`/`hunk`/`lines`, the hunk's `id`, `header`, `label`, counts, and the patch text, at most 200 lines; at most 100 entries, oldest first) and an `UndoEffect` named for it (`ReviewPatch.name`: `Stage of src/a.rs`, `Discard of src/a.rs, lines 15–46`, `Unstage of 2 lines of src/a.rs`) whose undo and redo apply the patch reversed and forward; one whose patch no longer applies is reported to the tile (`.reviewPatchFailed`) and leaves the files alone.

Viewed: the file header's check writes `props.viewed[boardPath] = fingerprint` (one undo step, dropping entries whose diff changed since) and folds the file; an entry counts only while the fingerprint matches (`ChangedFile.isViewed`), so a changed file unfolds on the next listing. Fitted tiles (`ChangesMetrics.grown`): after a reload, a tile whose natural height equals `ChangesMetrics.fit` of the previous listing (at its width) grows toward the new fit when that is taller (`Board.growFitted`: into free space only, `Board.grownFrame`, never over a neighbour, the rest scrolls; credited to the system, never an undo step); one sized for an empty listing (or none yet, after a relaunch) grows wider too, a tile the user made (Review Changes: a compact "No changes" when it first lists nothing) to at most the default 820×620. Review Changes (the board menu's per-worktree Uncommitted changes and Branch vs <default branch>, File › Review Changes and Review Branch) lists first (`ChangeSet.load`) and then creates the tile, compact when nothing is listed. `object.create` of a changes tile by an agent (`caller`) that already made one on that board for the same `root` (resolved), `base`, and `paths` is `object.update` of that tile with the call's other props, `frame`, and `size`, and answers `reused: true` (`ApiRouter.reusableChanges`; not in batches).

Scrolling: a trackpad gesture belongs to whoever its first movement picks (the tile when it can scroll and the movement is mostly vertical, else the board) until it ends, momentum included; a gesture's first event without movement never reaches the board while the tile can scroll, so the board can't start tracking a gesture that turns out to be the tile's. Wheel notches and phaseless steps go one by one, as in code tiles. j/k, J/K, ]/[, s/r scroll the current hunk into the tile's view below the pinned file header (`reveal`), never the board.

Opening code: a click on a line opens it by `Board.openForNavigation` with `preview: true` (the tile's own preview, else a plain code tile in view showing the file, else a new one beside the tile, shrunk down to a follow tile's minimum to land wholly in view; see Navigating to code), one step of Navigate Back; then the board pans the least that shows it together with what showed of the changes tile (`Layout.reveal(_:keeping:…)`, the padding cut to the room left when both just fit), or the code tile alone when both can't fit.

Mentions: a diff line is a `code` mention of its side's line (`side: new` for context and added lines, `side: old` with the base's name of the file for removed ones) with `commit` = the base and `diff` = what it is (`ChangeSet.mentionDetail`: `added|removed|context line · unstaged|partly staged|staged|committed hunk`); the prompt names the side either way (`, new side (working tree)`, `, old side (base)`). A hunk header mentions the whole hunk (`ChangeHunk.mentionLines`, `diff`: `whole hunk +a −r · unstaged|partly staged|staged|committed`); a file header mentions the tile. The header's hints (`ChangesMetrics.hints`) leave out staging and Discard for a listing with nothing to stage, unstage or discard (`ChangeSet.actionable`: a branch's commits only). The tile's keys (`ChangesTile.key`) act only once it has the keyboard; pressed while it is only the selection, `keyWhileSelected` says "press ↩ first to use the tile's keys" in its header, and the drawing layer leaves them alone (`ChangesTile.isOwnKey`: `r` there never picks the rectangle tool).

### Image tiles

`ImageTile` shows `props.path` (board-relative, absolute, `~/…`, or a `file://` URL: `LocalImage.tileFile`; any file the agent or user names, unlike notes and pages) decoded by `NSImage` (bitmaps, SVG, a PDF's first page), read off the main thread, aspect-fit and never scaled past its natural size above the optional one-line `caption` strip (`LocalImage.captionHeight`). While live it watches the file's directory (`FileEvents`) and reloads on any change to the file, so a chart re-saved in place, or one written after the tile was created, shows; not live, it reloads when it is again. `view.render` and cards draw from the loaded picture. Natural size is one point per pixel for bitmaps (`LocalImage.naturalSize`, from the header only), the document size for SVG and PDF; `object.measure`, `size: "fit"`, and a create without a frame height give the picture at most `width` (default `LocalImage.defaultMaxWidth`, 960) wide plus the title bar and caption. A Hyper-click on the picture mentions `.image(object, path, x, y)` in image pixels; elsewhere the tile.

### Diagram tiles

A diagram tile (`type: diagram`, `DiagramProps`) is computed from the code, not drawn. `kind: calls` (the only kind so far; the model is kind-neutral so type/ER graphs and pipelines can add kinds with their own builder) is a function's call hierarchy: `CallGraphBuilder` (CanvasCore) resolves the root by its symbol (`symbol`, `Type.member` or a bare name matched against the file's document symbols, without `path`, the file found by `NoteSource.locate` when that file's document symbols declare it, else by `workspace/symbol` for the name, asked of the projects (at most 3) of the tracked files mentioning it (`git grep -w`, at most 40, declaration-like lines first), each answer in the board's files checked against its file's document symbols for the container (typescript-language-server names none): an answer counts once the next one (1.5 s later) finds the same declarations, since a server still reading the project answers with part of it (tsserver just started: the opened file's only); one declaration left is the root's file, several are an `error` listing them as `path:line (Container.name)`; or the document symbol at or around `line`), asks `prepareCallHierarchy` at its name, then walks `incomingCalls`/`outgoingCalls` breadth-first `depth` levels each side and one more level under each node in `expanded`. The graph is of one checkout (`DiagramRefresh.scope`): the one the root's file lies in (`path`, else the root node it last found; a file in another worktree of the board's repository means the board root's place in that worktree, `Board.checkoutRoot`), else the checkout of the agent that created it (`Board.callerCheckout`), else the one the user opened the board from (`Board.workingRoot`); the bare symbol is looked for there and paths are written as the board stores them. Only items in that checkout's files are nodes (the SDK's, generated interfaces and compiler-made `$…` thunks are dropped); at most 60 nodes (`omitted` counts the rest). Node ids are `path#Container.name` (`@line` on a same-named second symbol), so moving code keeps a node's id, expansion and arrows. A node is placed at its document symbol in the file's current text (at the item's position, else the one of its name nearest to it): sourcekit-lsp places items and calls where the last build's index saw them, so code moved since shows where it is now, its calls shifted with it. A node's `lines` are its document symbol's range; its excerpt is the lines of its calls toward the root for a caller, else its signature up to the line opening its body (at most 3 lines).

The graph lives in `props.graph` (`DiagramGraph`), bookkeeping (`UndoHistory.bookkeeping`, `Board.writeBookkeeping`: no rev, no undo step), written by `DiagramRefresh.run` only while the props it was computed for are still the tile's. Freshness: a build is merged with the previous graph of the same aim (`DiagramGraph.merged`): a previous node missing from the new graph whose symbol is no longer declared in its file (or whose file is gone) stays, `stale: true`, with its edges to what remains (`stale` edges); one whose symbol still exists (it stopped calling, was collapsed, is past a smaller depth) is dropped. A root whose symbol is gone keeps the whole previous graph with the root stale and `error` saying so (`DiagramGraph.stalled`); any other failure keeps the previous graph with `error`. Changing `kind`, `path`, `symbol`, `line` or `direction` starts over; `depth` and `expanded` don't.

`DiagramTile` (CanvasApp) draws the graph with `DiagramLayout` (CanvasCore; deterministic from the graph, so the tile, `object.measure` and arrow ends agree): one column per level, callers left of the root and callees right, each column ordered by its neighbours toward the root and centred on the tallest, a status strip above, scaled down (never up) to fit the body and centred. It recomputes on creation, when re-aimed, on a debounced (0.6 s) change of any file it shows while live (`FileEvents`; not live, when it is again), after a launch once it shows, and on `object.reload` (`ApiRouter.refreshDiagram`: the tile's own refresh; a board without a window computes directly). The router waits up to `timeoutMs`, default 60 s (`ApiRouter.computeDiagram`), and then answers `loaded: false` with the graph the tile has while the computation goes on: a language server that doesn't answer never holds the request longer. `object.create` (or an upsert that creates) with `size: "fit"` and no `props.graph` creates the tile at its default size (at the given `x`, `y`), computes it the same way with the 60 s default, then fits it to the measured graph where it is then (moved meanwhile, it stays moved; deleted meanwhile, the create still succeeds, with a warning) as a system write (not an undo step: one ⌘Z removes the tile); the result adds `diagram`, that summary, and a graph not there when the wait ends leaves the default size with a warning (`ApiRouter.createFittedDiagram`). In a batch, sizes are measured before anything changes, so a diagram there fits only once it has a graph. A click on a node with + (or −) toggles its id in `props.expanded` (an undo step); a click on its `path:line` opens the code (`Board.openForNavigation`). A Hyper-click mentions the node as a code mention (`DiagramNode.mention`): its declaration's lines, or the excerpt line under the pointer, `symbol` the node's `Container.name`. A tile still at the default size is sized to its first graph, and a tile whose graph gains nodes (a node opened) grows to show them, never shrinking (at most 1600 × 1100 body; unrecorded writes). Growth never covers another object and never relocates the tile (`Board.grownFrame`): the whole size from a corner with room (`Layout.refit`: it may grow up or left, keeping its other edges), else from its top-left as far as the free space right and below allows, `placementGap` short of neighbours; the graph is drawn scaled to what it got. After the user's own click opens a node (not an agent's `expanded` update, which follows `view.follow` rules), the board pans, animated and never zooming (`Layout.revealGrown`): the least pan that shows the whole grown tile when it fits in view; else the added nodes with the clicked one when those fit; else toward the added nodes' left and top edges, cut short where the clicked node would leave the view. Moving it to a free slot (`refitFrame`) would take the node just clicked from under the pointer, and scrolling inside the tile would make node boxes, and arrows bound to them, depend on per-view state the model can't see.

## Export

The object menu's Copy as Image and Save as PNG… draw the selection with `view.render` (`CanvasView.render`, `.objects(selection)` plus every group whose members are all selected, `SelectionScope.export`, at 2 px/pt: tiles, drawings and groups under it, no app chrome) with `RenderRequest.chrome` false: as View › Hide Board Chrome shows the board, without author marks, close glyphs or the dot grid (a plain board background; `view.render` itself keeps them). They put the PNG (plus TIFF) on the general pasteboard, or write it where a save sheet says (default: the folder last saved into, `canvas.exportDirectory` in user defaults, unless it is gone or inside the board root; else `~/Downloads`; name `ExportFile.name`). An HTML tile adds Save as HTML… and Open in Browser (see HTML tiles). A note adds Copy as Markdown (its `props.markdown` exactly as stored, as a plain string on the general pasteboard) and Save as Markdown… (the same text, UTF-8, in a `.md` file named after the note's title, through the same save sheet and default folder); the main menu's Edit › Copy Note as Markdown and File › Save Note as Markdown… act on the one selected note (`CanvasView.copyNoteMarkdown`, `saveNoteMarkdown`). Save panels run out of process, so replayed input can't type into them; `input key return` on one saves under its suggested name.

A browser tile's Snapshot to Image (its object menu; File › Snapshot Page to Image for the focused or selected one; `CanvasView.snapshotPage`) takes the page as it shows (`WKWebView.takeSnapshot`, the screen's pixels; a released page its last capture), writes it as a PNG under the board's directory (On-disk locations) and creates an image tile with its absolute path, titled `<tile title> · <time>` and captioned with the page's address, as wide as the browser tile (`ObjectMeasure` image size), placed beside it (`Board.place`) and selected. Deleting the tile leaves the file, so ⌘Z brings it back whole.

## Remote boards

A remote board's window (docs/design.md "Client mode") speaks the host's API over a connection (`EaslConnection`; two per board: one for `events.subscribe`, reads, writes and prompts, one for renders) and adds only these to it:

- `view.render` `inline: true` returns the image in the reply as `data` (base64, in `format`, png unless `format` says jpeg) and writes no file; `path` is absent. `inline` with `out` is `invalid_params`, checked before the target. The viewer renders one object at a time (`target` its id, `scale` its screen's backing scale, `timeoutMs` 8000) and shows the body below the title bar (`canvasRect` maps the pixels: the tile's frame less `RenderMath.tileTitleHeight` at the top).
- `agent.prompt` `composer: true` is the user's prompt from a composer in another app: the host sends it exactly as its own composer does (`ApiRouter.composerPrompt`: typed into the terminal with every `agent.prompt` check, also into a terminal that takes peer messages; `mentions` become the composer's own `Mention`s, queued for that prompt's drain, numbered from 1, never the tray or a hand-off). `answer: true` with it is the user's answer to a blocked target: past the blocked check alone, no mentions. `answer` without `composer`, and `composer` with `caller`, `from`, `when` or `force`, are `invalid_params`, checked before the target. The viewer maps its composer's tokens to `PromptMention`s: a code tile's lines, an image tile's pixel, any other target as the objects it names.
- Writes are the API's own: `object.update {id, frame?, props?}` (`props` with the host `rev` the edit was based on, so a crossed edit fails `conflict`), `object.delete {id}`, `object.create {board, type, props, frame, parent?}`. There is no `z` over the API: restacking isn't offered on a remote board.
- Terminals attach with `RemoteHost.terminalAttachCommand(session: "canvas-<tileId>")`, retried every 2 s while it fails (the attach refuses a session the host hasn't started yet) until the tile closes; the viewer reads no process, `zmx history` or notification of a remote terminal: its lifecycle, title and markers are the host's, in props and events.
- Nothing on disk for a remote board (On-disk locations): no board file, viewport or composer file, window frame in user defaults, `open-boards.json` entry or page snapshot.

## Drawing layer

`.shape` and `.arrow` objects are drawn by `ShapeLayer` (`Sources/CanvasApp/Drawing/`), one view in document coordinates above every tile and below the Hyper outline. Geometry lives in `Sources/CanvasCore/Drawing*.swift`. Selection and moves of drawn objects are the scene's (see Scene seams); the layer supplies rendering, hit tests, outlines, resize handles, tools and editors, arrow routing, and region images.

- A shape's `frame` is exactly its drawn box (no title bar). Ink `points` are relative to the frame origin; the frame is the painted stroke bounds.
- An arrow's route is derived, never stored: bound ends attach to the facing edge of the bound object's current outline (a tile's frame, a shape's frame, the curve of an ellipse), so arrows follow moves and resizes without writes. An end bound to a `node` of a diagram tile attaches to that node's box as the tile draws it (`DiagramLayout.canvasRect` in the model, `DiagramTile.rect(ofNode:)` live; the tile posts `DiagramTile.laidOut` when its nodes move and the layer re-routes); a node the graph no longer has binds the whole tile. An end bound to `lines` of a code tile is a row end (`ArrowEnd.row`): it attaches to the tile's left or right edge (right unless the other end lies wholly left) at the first visual row of `lines.start` (wrapped lines above it push it down), `CodeMetrics.lineY`: live, the tile's rows as scrolled (`CodeTile.lineY`; the tile posts `CodeTile.rowsMoved` and the layer re-routes), and in the model (`BoardGeometry.routes`, `layout.check`) the tile freshly aimed by `CodeMetrics.scrollOffset`, the same rule `CodeTile` scrolls by (range start with up to 3 rows of context, fewer when the viewport can't show them and the range). A line out of view clamps to the top of the rows or the bottom of the tile. Orthogonal routes with a row end leave sideways, looping around the right edges when the two tiles overlap horizontally; `avoid` uses only the two side ports and keeps its row. `lines` on other tiles binds the whole tile. `DrawingGeometry.path` (CanvasCore) routes one arrow by `props.route`: `straight`, `orthogonal` (one jog between facing sides), or `avoid` (alone, the router below with one connector). Straight and orthogonal arrows bound to the same two objects in either direction get `parallelOffsets` (`parallelSpacing` apart, relative to each arrow's direction, so opposite arrows take opposite sides). A board's `avoid` arrows route together (`ConnectorRouter`, docs/design.md "Arrow routing"): an orthogonal grid search around every object `BoardGeometry.blocksRoutes` (tiles, text, filled shapes, keeping `avoidMargin`) that picks each end's side by the flow of its group (`GroupProps.flow`, else the way arrows between groups point), then distinct ports for arrows sharing a side, crossing-aware routes, and parallel tracks for arrows sharing a channel, off group borders and title bands. Every arrow's label (all route styles) is placed with the rest (`ConnectorRouter.placeLabels`): beside its own route where nothing else is, else on it, else a short leader away (`ConnectorRouter.Label.leader`, drawn dashed). The caption is `label`, else `relation` in the secondary color when `label` is absent; `label: ""` draws none (`DrawingStyle.arrowLabel`). The layer draws, hit-tests, and selects the routed polyline; `BoardGeometry.routing()` computes the same routes and labels from frames for `layout.check` and detaching, routed on from the layer's last routing (`Board.settledRouting`). An arrow's `frame` records its route bounds when it was drawn. Free ends (`{"point": [x, y]}`) are board coordinates. Deleting a bound object turns that end into a free point where it last attached, in the delete's undo step, so the arrow keeps its direction and its other end keeps following.
- The frame the API reports for an arrow (`board.get`, `object.get`, create/update results, `board.history` summaries; `Board.reported`) is the bounds of its routed line: as drawn (`Board.arrowPath`, supplied by the drawing layer), else routed from object frames (`BoardGeometry.routes(only:)`). The drawing layer routes the board once per burst of changes, off the main thread (a change the API made: once the API is quiet, `ApiActivity`), holding a new or changed `avoid` arrow on a provisional line until then; `Board.reported` first has it route the board when such an arrow is pending (`Board.settleArrows`), except inside a step, and `object.batch` reports its arrows' frames once its step has closed, so a create result is the route drawn, around tiles later ops of the same batch add. An arrow that only moved with its ends (a tile it binds written mid-burst) reports the line it follows them on, alone, until the burst's routing places it with the rest. The stored frame of an arrow with a bound end is a meaningless placeholder.
- The layer never takes keyboard focus (it stays with the prompt-target terminal); tool keys V/R/O/A/T/P/Esc arrive as key equivalents and only act when no terminal or text view has the keyboard. Inline text and arrow editors take focus while open and give it back on Enter/Esc/click-away, never over a responder that took focus meanwhile. The text editor (`ShapeTextEditor`) commits on Enter, Esc, and click-away (an emptied text shape is deleted; the arrow caption editor's Esc cancels), and draws a steady caret itself in a window that isn't key. A text shape's size follows `TextShapeLayout` (CanvasCore): a frame exactly as wide as its grown text keeps growing up to `autoWidth` (320) × `textSize` as it's edited, any other width is its wrap width. An arrow end binds to the topmost shape (within the hit tolerance) or tile under it, else the nearest shape, else the nearest tile, within `ShapeLayer.arrowSnap` (16 screen points).
- Only strokes, text, labels, and fills (`fill: semi|solid`) take the mouse; an unfilled shape's interior passes clicks to the tiles beneath.

## Scene seams

`CanvasView` (`Sources/CanvasApp/CanvasView.swift`) owns selection, moves, groups, attention markers, and the viewport. Drawn objects (shapes, arrows) have no view of their own; the drawing layer plugs in through:

| Seam | Direction | Meaning |
| --- | --- | --- |
| `installShapeLayer(_:)` | drawing → scene | Adds the drawing layer above tiles, below attention markers and the overlay; restacking keeps it there. |
| `shapeHitTest(docPoint) -> ObjectID?` | drawing → scene | Drawn object under a point (strokes, text, fills). Plain clicks there select it and drag the selection; Hyper-clicks mention it. |
| `shapeOutline(id) -> NSRect?` | drawing → scene | Committed document rect, for rings and hover outlines. |
| `drawingOwnsPoint(docPoint) -> Bool` | drawing → scene | True while a tool is active or over a shape handle; scene selection, marquee, and moves stand down. |
| `moveProps(object, dx, dy) -> JSONValue?` | drawing → scene | Props merged into a drawn object's move update (e.g. free arrow endpoints). |
| `onSelectionDrag(ids, offset)` | scene → drawing | Live drag offset in document points; `.zero` just before the move commits. |
| `selection`, `onSelectionChange` | scene → all | Current selection (tiles, drawn objects, groups). |

Groups (`type: group`, props `{members, title?, color?, padding?}`, frame derived by the board, see Object model rules) are drawn by the scene as titled, tinted regions behind their members (`GroupView`), following members live mid-drag with the same `GroupSpec.frame`; only the title band takes the mouse. Title and border are in document space like everything else. `focus(tile:)` zooms a tile to 100%, centers, selects, and focuses it. Attention markers are board state (`Board.attention`, `Attention.swift`): `view.attention` raises and clears them in CanvasCore, the scene shows what the board holds (`attention.changed` events, and the stored markers when a board opens), and every user acknowledgment (selecting, focusing, clicking the bubble, an edge pill, looking a while) is `Board.clearAttention`; the empty board's Clear Attention Markers is `Board.clearAllAttention` (markers aren't undo history). `CanvasView.layoutPills` places every bubble and edge pill in one pass (`PillLayout`, CanvasCore: bubbles above their object, else on its title bar, never on another pill nor on a blocked terminal other than their own; edge pills slide along their edge, off blocked terminals where it has room), for markers and for terminals whose lifecycle is `blocked` (ring and bubble, or edge pill, in the blocked `AttentionStyle`: orange with a raised hand before the lifecycle message; markers are pink; blocked bubbles are placed first; they appear and go with the lifecycle state, and clicking one selects the terminal and gives it the keyboard), on every pan step, object move, and scene pass. A board's tab shows `NeedsYou` (CanvasCore: blocked beats done, nothing for working or idle), refreshed by the window controller on terminal updates. Every user viewport jump (`go(to:)`, `zoomToFit()`, `zoomToActualSize()`, `focus(tile:)`, `jumpToAttention(_:)`, `reveal(_:)`, entering a group, opening a board) aims at the clear area between the floating toolbar and the tray (`chromeInsets`, measured by the window controller, plus a 12 pt margin); the geometry is `Layout.fit`/`center`/`reveal` (CanvasCore).

## Undo

`Board.history` records every create, update, and delete from any actor; ⌘Z (`Board.undo()`) reverts the latest step even when an agent made it, never silently: each step (`UndoHistory.Step`) records its author (the agent when an agent made any of it, else the user), `Step.summary` says what it did by verb and object type (`created 9 code tiles, 6 arrows; moved a note`: updates of objects the step created or deleted are part of that; a group re-fitted or an arrow re-routed is left out beside anything else), and `Step.title` names it for Edit ▸ Undo/Redo (`Undo Create 9 Code Tiles, 6 Arrows (omp)`, the author by `Board.authorName`: the terminal's `name`, else its agent's kind). Every undo or redo shows the board notice for 4 s (`Step.notice`, `CanvasView.showNotice`, also announced to VoiceOver): "Undid moved a note · ⇧⌘Z redoes", with the author for an agent's step ("Undid omp: … · ⇧⌘Z redoes") and an `UndoEffect`'s name for a change to the files or git index ("Undid Stage of src/regex_helper.rs · ⇧⌘Z redoes"); an effect's name leads `Step.summary` and `Step.title`. ⌘Z and ⇧⌘Z stay with a terminal holding the keyboard (Edit ▸ Undo/Redo disabled then). Navigation's re-aims are never steps (`Board.reaimForNavigation`: Go to and links through `Board.openForNavigation`, a terminal's ⌘-click preview through `Board.openCode`, a follow tile's history strip). Every undo or redo is a new revision, newer than any the object ever had, even across a delete and re-creation. Bookkeeping nobody chose is never an undo step and never rewound (`UndoHistory.bookkeeping`, `Board.unrecorded`, `Board.writeBookkeeping`), so ⌘Z reaches the user's last own action through an agent's work: a terminal's `lifecycle`, `agent`, and `title`; a browser's `pageTitle` (the page's own title; `title` is the creator's and stays undoable); a follow tile's `path`, `range`, `lastAction`, and `history` (every `follow.report`), and the follow tile appearing; and every update the app writes back as `system` (a note's resolved `anchor=`). An undo of an earlier step keeps them as they are now (a moved follow tile goes back, still aimed where its agent last looked), and undoing a terminal's creation takes its follow tile along. Multi-object gestures wrap their updates in `Board.transaction { }` to form one step; API writes that must succeed or fail together (`object.batch`, `layout.*`) use `Board.atomically { }`, which also rolls back on error. Repeated updates of one object within a step collapse into one recorded change (first before, last after), never across an `atomically` mark. Undoing a delete restores the object with the same id and `z`; staged mentions of it are not restored. When undo/redo removes a terminal and later brings it back, it returns with the bookkeeping it last had. History lives in memory only. A step can also carry an `UndoEffect`, a change outside the board run on undo and redo (a changes tile's `git apply`, see "Changes tiles"); its slow work runs in a task of its own, so undo itself never waits on git.

## Mention context format

`tray.drain` returns a `context` string that the omp extension injects as hidden context with the submitted prompt. The tray's mentions belong to the terminal it shows, the board's prompt target (`CanvasView.promptTarget`, settled by `CanvasWindowController` from `PromptTarget.choose` over what the rule remembers, `Board.promptTarget`: terminals in focus order and the tray menu's pick, saved in the board file as `promptTarget` so the target survives a restart; the router reads it through `viewState`): a drain whose `caller` tile is another terminal returns no mentions, an empty context, and `held`/`target`, and changes nothing. A drain without a caller, or on a board without a window, takes the tray as before. The one exception is the caller's integration's submission drain (one with `prompt`) whose text contains a prompt the user sent the caller from the composer: it is that prompt's and takes the mentions it carried instead (Composer, below). ## Note fences

A note's `markdown` is plain markdown; the code fence info string selects how the tile renders a fence (parsed by `NoteFence` in CanvasCore):

| Info string | Renders |
| --- | --- |
| `ts file=src/app.ts#L10-40` (`#L10`, `#L10-L40`; no range = whole file) | Live excerpt of the file with line numbers |
| `ts symbol=restoreSnapshot` / `swift file=Sources/Board.swift symbol=Board.update` | Live excerpt of the declaration (best-effort, language-agnostic; `Outer.inner` searches inside `Outer`; without `file=`, the first tracked file that declares it) |
| `… file=src/app.ts@1a2b3c4#L10-40` | Excerpt pinned to a commit (`git show`) |
| any anchored form plus `propose` | The fence body as a diff against the resolved range |
| anything else | Free-written (authored) code; `path:line` references in it open code tiles |

Anchor resolution (`NoteAnchor.resolve`, shared with code tiles' ranges), in order: a symbol that resolves wins (`Outer.inner` searches the whole extent of `Outer`, however long; the declaration's own range stops at 400 lines; a signature's parameter list, over several lines, and braces inside it open no body, so Python's `) -> T:` line is followed by its indented body); otherwise the line range is re-found by the text the tile captured when it first resolved it (when that opens with the fence's `anchor=`, else by the `anchor="first line text"` alone), preferring the candidate whose following lines match best and the written position on ties; with the first line gone, by most of the captured text still standing together; else by the fence body (a proposal's own lines vote for where they sit). Captured text also carries the range's end: the shortest stretch from the start keeping as much of it as a generous window does, so lines inserted or removed inside the range move its end with them (lines gone from its end leave it shorter, unless a line reads like the one it replaced: the next one, or one after up to 4 lines written with it, such as comments ahead of a fix, before any blank line; the range then covers them all); with only an anchor (after a restart) the range keeps its written length. A range that moved or changed length renders with "was L…"; one that can't be found renders a **stale** badge over the last text it showed.

A `propose` fence whose body the file already reads, contiguously and overlapping the resolved range (anywhere in the file when the anchor is lost, for a body of two or more lines or one found once), is **applied** (`NoteAnchor.applied`): it renders the file's lines with a quiet "✓ applied" and no diff. Not while the range's original text (captured, else the range as written) still stands whole around it: a proposal that only drops lines reads as part of its range until it is applied.

`object.get` on a note adds `fences`: per anchored fence (fences with the same info string are one), its `info`, `markdownLines`, `path` (as found by a symbol search), `symbol`, `commit`, `propose`, and `AnchorStatus`: `state` (`live`, `relocated`, `stale`, `applied`, `missing`), the resolved `range`, the `written` range when relocated, and the stale `reason`. The note tile resolves them against disk at that moment with the text it captured (`ApiRouter.noteExcerpts`), and shows the result; without a tile they resolve from the markdown alone. A note that isn't live watches nothing, so `view.render` of it resolves every fence first too; a live note with nothing pending draws what it resolved.

The tile writes anchors back: when a line-range fence without `anchor=`, `symbol=`, or a pinned commit first resolves, it appends ` anchor="<first line>"` to the fence's info string in one `object.update`, so anchors survive restarts and agents see them. It skips first lines that can't be written (blank, or a backtick inside a backtick fence) and falls back to the in-memory capture. `commit=` must name a revision (`abc1234`, `HEAD~2`, `v1.0`); anything shaped like an option makes the fence stale.

Hyper-click on an excerpt or proposal row mentions `code` (object = the note, the row's real path and line, and `commit` for a pinned fence; an added proposal row mentions the line it would be inserted before, or the file's last line when appended at the end of the file). Any other rendered paragraph mentions the markdown block it came from (`MentionTarget.note`, found by `NoteItem.at(line:in:)` from the paragraph's `.noteMarkdownLine`): the innermost list item containing it (with its nested items), else its outermost blockquote, else a fence, table row (the delimiter row stands for the header), or paragraph; a top-level heading takes its section, up to the next heading of the same or a higher level. The target carries the block kind, its heading path (top-level headings above it, levels may skip), its lines, and its markdown as it read (common indentation removed, cut to 40 lines and 2000 characters). The title bar, margins, blank space, and thematic breaks mention the note (`object`).

Code mentions carry the commit their lines are read against (`MentionTarget.code.commit`, schema `MentionTarget`): with `side: old` or no side, the commit whose version of `path` holds the lines (peeked base rows, deleted files, pinned excerpts); with `side: new`, the base the working-tree lines were diffed against; absent, the working tree. The context line names it from the mention alone, never from what the tile shows at drain time: `· diff vs merge-base 1a2b3c4` (the kind word comes from the tile's `diffBase`), `· diff vs merge-base 1a2b3c4, old side` for peeked base rows with the excerpt read by `git cat-file blob <commit>:<path>`, and `· at 1a2b3c4` for a pinned excerpt without a side. `tray.drain` is therefore asynchronous.

Link roots (`LinkRoot.swift`; with `props.ref`, see Branch-anchored tiles): a note's relative paths (fence `file=` paths, `path:line` and markdown links, `![alt](path)` images) and an HTML tile's (`code.excerpt`, `code.open`, `<img>`) resolve against the tile's `props.root` (absolute or board-relative, like a changes tile's `root`), else the board root. `object.create`/`object.update` accept only an existing directory in the board's checkout or another worktree of its repository (inside the board root for a board outside git; `invalid_params` otherwise; empty or null clears it). An agent working in another worktree of the board's repository than the board root's (`caller` a terminal; its directory is where its foreground program, else its shell, works, else `props.cwd`) writes paths relative to its own checkout, the board root's place in that worktree (`Board.callerCheckout`, applied to `object.create`, `object.update`, `object.upsert`, batch ops and `object.measure` by `Board.inCallersCheckout`): a note or HTML tile it creates without `root` gets that checkout as `root`, so it writes `tests/x.ts:16` instead of `../wt-x/tests/x.ts:16`; a code, image or diagram tile's relative `path` is stored absolute in that checkout (not a code tile's with `ref` or `pinnedCommit`: those name the repository path); a changes tile it creates without `root`, `ref` or `head` reviews that checkout. The board's own checkout's agents, the user and calls without a caller keep board-relative paths. Anchoring, `size: "fit"` and `object.measure` use the same root. A link opened from the tile names its file as the API stores paths (board-relative under the board root, else absolute).

## Git

All git in the app runs through `GitRunner.shared` (CanvasCore), which caps concurrent git processes at two, can cap stdout (`maxOutput`) and run time (`timeout`), feeds stdin (`input`, e.g. a changes tile's patch for `git apply`), stops git when the calling task is cancelled (a request still waiting for a slot just leaves the queue), and sets `GIT_OPTIONAL_LOCKS=0` so reads never contend with agents for the index lock, and `GIT_NO_LAZY_FETCH=1` so a partial clone's missing object is never fetched: easl's git never goes to the network. The only writes are a changes tile's Stage (the index) and Revert (working-tree files), each on the user's click or key, inside the tile's repository. Git, file reads, and parsing run on GCD (`offPool`), never blocking a Swift concurrency thread. Code tiles diff through `GitDiffEngine.shared`: live tiles `retain(containing:)` their repository and `release` it when they go offscreen or away; held repositories keep resolved bases and an FSEvents stream that posts `Notification.Name.gitDiffBaseChanged` (object: the repository's top-level path) when a commit, checkout, rebase, or fetch moves a base.

## HTML tiles

- Each tile's page is `canvas-kit://html/<tileId>`, served by the tile's own scheme handler: the kit head (`resources/kit/canvas-kit.css`, `canvas-kit.js`, `vendor/tailwindcss-browser.js`) followed by `props.html`. `/kit/…` serves `resources/kit` (Mermaid loads from there only when a page has diagrams). DOM mentions of HTML tiles use that URL.
- Images: any other request path the handler serves as an image file (`LocalImage.pageFile`), read off the main thread, never cached: the file at that path under the tile's link root (`<img src="out/fig.png">` resolves to `canvas-kit://html/out/fig.png`), else the absolute path it spells (`<img src="/tmp/…/fig.png">`), each only when it has an image extension (png, jpg, jpeg, gif, webp, heic, heif, tif, tiff, bmp, svg, pdf) and lies, symlinks resolved, inside the board root or a temp directory (`NSTemporaryDirectory()`, `/tmp`, `/var/tmp`). Everything else is 404, and `file:` URLs stay blocked by the rule list, so a page never reads other files on disk. A board directory named `kit` is shadowed by the kit.
- Export (the object menu's Save as HTML… and Open in Browser, `HtmlTile.exportDocument`): the page loads offscreen as for `view.render`, and once settled its DOM is serialized with each `<img>` inlined as a `data:` URL, the kit stylesheet inlined, and every script removed (Tailwind's generated styles, `<canvas-code>` rows and Mermaid diagrams are already in the DOM), so the file opens anywhere. Open in Browser writes it to `$TMPDIR/easl-exports/<tileId>-<title>.html` and opens it with the default browser (with `EASL_NO_ACTIVATE` it only logs the file).
- Sandbox: non-persistent website data store per tile; a WKContentRuleList (WebKit's default rule list store, identifiers `canvas-html-<hash>`) blocks `http(s):`, `ws(s):`, and `file:` except `props.allowNetwork` hosts: `host` (any port), `host:port` (that port only; `:443`/`:80` also match the scheme's portless URL), `*.host` (the host and its subdomains). Exceptions pin the whole authority (no userinfo); other entries are ignored. A tile never loads with rules compiled for an allowlist that has since changed. The main frame never navigates away from its page; popups are refused.
- The only native access is the `canvas` script message handler (`window.webkit.messageHandlers.canvas.postMessage(msg)` → promise), accepted from the tile's own top-level page only. Each tile runs at most 4 messages at once with 64 more queued; beyond that a message is rejected (`too many outstanding requests`), and outstanding work is cancelled when the page re-renders or the tile detaches. Messages are strict (`Sources/CanvasCore/HtmlMessage.swift`: known `type`, only its fields, 64 KiB per message):

| `type` | Fields | Reply |
| --- | --- | --- |
| `code.excerpt` | `path`, `lines?` (`"N"`/`"N-M"`), `symbol?` | `SourceExcerpt` (`start`, `end`, `lines`, `language`, `stale`, `reason`, `truncated`) |
| `code.open` | `path`, `lines?`, `symbol?` | `{tile, created, existing}`: `Board.openForNavigation` from the HTML tile (a code tile anywhere already showing those lines, exactly or as a captioned stop whose range holds them: `existing`; else a plain code tile in view showing `path` re-aimed, never an agent's, captioned, grouped or follow tile; else a new one beside the HTML tile); from the live page (a user's click), the board goes to an existing tile (selected, centered when not in view) and pans the least that shows any other clear of the chrome |

## Agent prompts and replies

`agent.list`, `agent.prompt`, `agent.wait`, and `agent.read` describe a terminal with one entry shape (`ApiRouter.agentEntry`, schema `Agent`): `tile`, `board`, `root` (that board's root directory), `address`, `name`, `aliases`, `kind`, `protocol`, `sessionId`, `lifecycle`, and agent control's `open`, `focused`, `pid`, `draft`, `model`, `thinking` (`live` in agent.list; "Agent control" below).

A terminal tile keeps a log of the commands its shell finished since easl attached (`TerminalCommandLog`, at most 200, in memory: each OSC 133 D that `TerminalCommandTracker.finished` counts as a shell command). A block is found by its command's line in the terminal's text (Ghostty's text from the top of the scrollback to the cursor, soft-wrapped rows joined): from the input line up, each logged command's line is the last line above the newer one's that ends with it (`TerminalCommandLog.positions`), so repeated commands each keep their own block; the first command not found ends the search (its line was trimmed from the scrollback), except that one clearing the screen (`clear`/`reset` among its words) owns the text from the top. A Hyper-click names the block holding the clicked line when the output below that command's line is the one Ghostty selected; its command, exit and duration then come from the log, however far its prompt row scrolled. `agent.read` `block: -N` reads the lines below its command's line to the next command's line, less the lines a prompt shows above its input line (measured whenever a Hyper-click selects a logged block, none until then); `block: -1` (`"last"`) is Ghostty's selection of the last block while it is on screen above the prompt. In the output of a program still running (Ghostty's selection goes on to the cursor) a Hyper-click mentions the rows around it. `agent.read` `lines` joins the live screen's rows by Ghostty's own wrap flags (`TerminalTile.screenRows`, matched against the end of zmx's history) and the rows above by the guess.

`agent.prompt` refuses (`conflict`, unless `force`) a target whose agent reports a lifecycle while its terminal's foreground program (`TerminalStatus.program`, from the process table) isn't that agent (`PromptTarget.foreignProgram`: none of the program's words, extension dropped, is the agent's `kind`): an editor or a pager would take the text. For tmux it asks the client's own server (`ForegroundProgram.tmuxPane`: its binary, `-L`/`-S` and `TMUX_TMPDIR`, `display-message -c <the client's tty> '#{pane_pid}'`) what the active pane runs, and sends when that is the agent; another program there (vim, the pane's shell) is the conflict, named; when tmux doesn't answer, tmux itself is. Into a shell at its prompt (the session's shell known, nothing in the foreground) a one-line text of printable characters is typed (`ShellTyping`: Ghostty's `text:` action, one write, no bracketed-paste markers) instead of pasted: once, after 12 idle minutes, zsh ran a pasted command as `[200~clear…~`, most likely its line editor taking the paste's leading ESC apart from `[200~` (KEYTIMEOUT). Ghostty writes the start marker in one write and zmx forwards it in order (that session's zmx log shows the tile's client leader throughout), so the split happened past easl; typing leaves no ESC to split. It reads the target's session text (the last 400 lines, `TerminalTail`, each line with its position in the whole text) before it pastes, and keeps it in memory per terminal until the next prompt, the tile's deletion, or an app restart. `agent.read` `since: "prompt"` reads the last 2000 lines and returns them from the first remembered line that now reads differently (`TerminalTail.Tail.boundary(after:)`: a shell's prompt line that got the command, a TUI's input box its reply overwrote), else from where the old text ended. The scrollback's own trimming can move positions; the reply then starts earlier, never later. A terminal whose lifecycle is `unknown` gets no pending-prompt state, so `agent.wait` on it fails at once instead of waiting for a report that never comes. An agent reporting by notification (`NotifyingAgent`) goes `unknown` as the prompt is submitted (`Board.notifyingAgentSubmitted`), and `agent.wait` on it waits for its next notification, past the first-report grace.

`agent.prompt` `mentions` (`HandoffMention`, schema `PromptMention`: `object`, optional `lines` for a code tile, `point` for an image tile) become the `MentionTarget` a Hyper-click on the same place stages: a code tile's lines (its `range` when no lines are given) are `code` at the tile's `pinnedCommit`, with its `symbol` only for its own range; an image tile's point is `image`; anything else is `object`; lines or a point on another type are `invalid_params`. The objects must be on the target terminal's board, and the target must run an integrated agent (`PromptTarget.drains`: it reports a lifecycle, not `via: "notifications"`), else `unavailable`. They are queued (`Board.handOff`, duplicates of a waiting target skipped) before the text is pasted, so the drain of that very prompt finds them, and withdrawn if the paste fails.

The composer sends through the same path (`ApiRouter.composerPrompt`: in process, or `agent.prompt` `composer: true` from a remote board's viewer, Remote boards): the text to each target with every `agent.prompt` check, except that a target `blocked` on a question or approval takes the text as the user's answer (`answer`: past the blocked check only, unlike `force`) and gets no mentions. On ⌘↩ the submitted draft leaves the composer and its tokens' mentions leave the tray at once (`ComposerSend.begin`, `Board.withdraw`; not an undo step) when a target takes them; when none does (every target only gets an answer, or the text is one its integration doesn't drain for) they stay staged, with a notice, and the router refuses mentions with such a text. The skip rules are each integration's own (`PromptTarget.skipsDrain`): Claude Code, Codex and Gemini CLI skip `/…` and `!…` (hook.ts), omp `/…`, `!…` and `$…`, opencode nothing (its shell mode is only the `!` key binding, so pasted `!…` text is a prompt, and a `/command` expands into one). Only prompts that need their own drain are queued, before the text goes in (`Board.queueComposerPrompt`, `Board.composerPrompts`, per terminal in send order, in memory): a prompt with mentions, with its own copies of them (ids of their own), and an answer to Codex, which submits the answer to a question it queued as a prompt (`PromptTarget.answersAsPrompt`). A prompt without tokens, an answer a dialog takes (Claude Code's, omp's, opencode's, Codex's approvals aside) and a text its integration skips queue nothing and drain as any prompt does (omp's continue shortcuts `c` and `.` among them). **Drain semantics** (`Board.drain`, `tray.drain` `prompt`): an integration's submission drain passes the text it is about to submit (the hooks' `UserPromptSubmit`/`BeforeAgent` `prompt`, omp's `input` text, opencode's non-synthetic text parts). Both texts are compared folded (`ComposerPrompt.fold`: letters and digits only, case-folded), so what agents do to a prompt drops out (Claude Code's `<pasted_content>` wrapper, Codex's IDE context, omp's `:)` → 🙂, text already in the input editor ahead of the paste). The drain claims the oldest queued prompt of its caller whose folded text it contains (equals, for a folded text under `ComposerPrompt.shortest`, 3 characters): it returns that prompt's mentions numbered from 1 in a block without a header, never the tray (whether or not the caller is the prompt target), followed by what agents handed the caller (`agent.prompt` `mentions`); a prompt with mentions stays queued until `tray.commit` names them (a peek takes nothing), an answer is taken by the claiming drain. A prompt typed in the terminal or sent by `agent.prompt` doesn't contain a composer prompt's text, so its drain claims nothing, whatever is waiting ahead of it. A submission drain that claims nothing while prompts wait logs one line with lengths only, and takes the tray; so does every drain without `prompt` (Hyper-V, scripts, the CLI, an older integration), which never touches the queue. So `[n]` in each target's text is the n-th token for that target, whatever is staged, retargeted or sent meanwhile. A Codex answer the claiming drain didn't take (an approval Codex takes in its dialog) goes `ComposerPrompt.answerGrace` (2 s) after Codex reports `working` or `idle` while no longer `blocked`. Queued prompts leave undelivered when the terminal's agent is released (`agent.release`, `Board.releaseAgent`), its shell is back at the prompt (`Board.terminalProgram` nil), the terminal is deleted, or at the safety cap `ComposerPrompt.lifetime` (2 h; checked on queue and claim and every minute by the window, `Board.expireComposerPrompts`): their mentions are staged again (`Board.onComposerMentionsReturned`, which the composer announces). omp's extension stages what each submission drained and commits it as `before_agent_start` hands the context back, which omp also runs for prompts it takes mid-turn (steering) without an `agent_start`; a prompt omp never prepares stays uncommitted. A prompt the terminal never took (`submitToTerminal` false) is withdrawn. When every delivery is done (`ComposerSend.settle`): if the text reached no terminal, the submitted draft comes back ahead of what the user typed meanwhile, its tokens staged again; if it reached terminals but none that took the mentions (only an answer went in), the tokens come back the same way. While a draft is on its way it is kept in the composer state's `outgoing` until a terminal takes its text; one left there when the app quit comes back ahead of the draft on the next launch (`ComposerState.recoverOutgoing`). A target without an integration gets `Board.context(for:caller:)`, the same block numbered from 1, pasted ahead of the text. A drained composer mention counts as delivered (`Board.delivered`). Known gap: a typed prompt that contains a waiting composer prompt's whole folded text (the same words resent by hand) claims it.

`agent.report` `final` (only with `idle`) is the final assistant message of the turn that just ended: omp's extension takes the text parts of the last assistant message in `agent_end`'s `messages` (when it doesn't continue), the hooks take `last_assistant_message` from `Stop` (Codex, Claude Code) or `prompt_response` from Gemini CLI's `AfterAgent`; opencode sends none. `Board.finalAnswers` keeps it per terminal until the next turn starts (lifecycle to `working` from idle, done, or no state) or the tile is deleted, saved with the board (`finalAnswers`, `turnErrors`, and the staleness rule's `lifecycleSeq` in the board file; `board.export` leaves them out), so a user returning after a relaunch can still read it; stale-`seq` reports are dropped with their answer. `agent.read` `final: true` returns it as `text` (with `lines`), and fails with `unavailable` while an `agent.prompt` to the terminal hasn't started, while it is `working` or `blocked`, and when no answer is kept.

After `agent.prompt` to an agent that reports a lifecycle and isn't mid-turn, `agent.wait` ignores the state from before the prompt until the agent reports `working` or `blocked` (or exits); a prompt that starts no turn within `ApiRouter.promptStartGrace` (60 s; a `/` command or `!` escape, which the hooks don't report, or text the agent didn't take as a prompt) fails the wait with `unavailable` instead of holding it forever. A prompt that lands while its agent is `working` (`agent.prompt`, the state as the text went in) joins that turn: the router doesn't wait for a `working` that may never come, and `agent.wait` answers when that turn ends, `final` being that turn's answer. That is what both integrated agents that take a prompt mid-turn do. omp takes typed text as a steering message (follow-ups likewise) and its agent loop runs it before the run ends: one `agent_end`, and when a queued message starts a new run right after, its `agent_start` comes within the extension's 250 ms idle debounce, so no idle is reported in between. Codex 0.155 queues it ("Messages to be submitted after next tool call") and submits it after its next tool call, or right after its answer when no tool call comes, firing `UserPromptSubmit` (`working`) then, within the same turn: one `Stop`, whose `last_assistant_message` answers the latest prompt (checked with its hooks, 2026-09-27). A prompt to an agent that is `idle`, `done`, or `blocked` (forced) still waits for the agent's next `working` or `blocked` before its turn can end.

`agent.report` `error` (only with `idle`) says the turn ended on an error instead of finishing: omp's extension sends the last assistant message's `errorMessage` when its `stopReason` is `error` ("Anthropic stream error (overloaded_error)"), `interrupted` for `aborted`, and `stopped at the output token limit` for `length`, beside whatever `final` text it got. `Board.turnErrors` keeps it with the answer (cleared together); the lifecycle stays `idle` with it as the message (never `done`), `agent.read` `final: true` adds `cutOff` (the error) to a text that is the answer as far as it got, and with no text fails `unavailable` naming the error.

### Agent addresses

A terminal is addressed as `name@board`, never by host (`AgentAddress`; the `target` of agent.prompt, agent.wait and agent.read, and omp's `write agent://…`):

- `name` is the terminal's `props.name`. A name only needs to be unique within its board: two boards can each have a `reviewer`.
- `board` is the board's name: the name of its root folder (`basename` of `root`, as the window title shows it: `canvas`, `lindy`; a repository board's root is its main checkout, so its worktrees share it), or its id `brd_…`. Only open boards are looked up, and only one whose root folder still exists by name (an archived board, its folder gone, by its id alone).
- A tile id `obj_…` is an address too, on any open board; it is the `address` of a terminal without a name.
- A bare `name` is looked up on the caller's board first (`caller`, the terminal asking), then on every open board. On each board a current name wins over an alias there, and matches on more than one board are `ambiguous` (an alias on one board and a current name on another included).
- A terminal's `address` (its agent entry's, a message sender's `from.address`, a bounce's) reaches it alone among the open boards: `name@board` while the name is no other terminal's on its board and its board is the only open board found by that folder name; `name@brd_…` when the folder name is shared with another open board or the folder is gone; its tile id when it has no name or shares it on its board.
- Renaming a terminal keeps its old names as aliases (`Board.aliases`, alias → tile, saved in the board file as `aliases`) until another terminal on that board takes the name (is created or renamed with it); deleting the terminal drops them. A tile moved, resized, restarted or resumed keeps its id, so its address and aliases stay.
- Errors: no match is `not_found` ("no terminal tile named or with id X", or "no open board named B", naming the open boards); more than one match is `ambiguous`, listing each candidate as its address and tile (`name@board (obj_…)`), so the caller can name one.
- A sender is identified by its tile id (`caller`), never by environment variables; its name and address are resolved when its message is delivered, so a sender renamed meanwhile shows its new name.
- Cross-host addresses (`name@board@host`, a board on another Mac or on an offload host) are out of scope for now: a remote board's agents are reached through that host's own socket (docs/design/next.md, Remote boards).

### Peer messages

`agent.prompt` to a terminal whose integration takes messages goes out of band: it never types into the terminal, so the user's half-typed draft, an open question and an approval dialog stay as they are. Everything else still types: a terminal without such an integration, and the composer (the user's own text, `ApiRouter.composerPrompt`).

- **Capability.** Every `agent.report` says the integration's `protocol` (an integer, kept as `props.agent.protocol`, shown as `Agent.protocol`; a report without it sets 0, `agent.release` clears it, and so does the integration dying, below). `protocol` ≥ 1 means the integration takes messages through `agent.inbox`. omp's extension reports 1; the Claude Code, Codex, Gemini CLI and opencode integrations report none yet and are typed into.
- **The queue** (`Board.messages`, per terminal, oldest first, saved in the board file as `messages` and left out of `board.export`): `agent.prompt` refreshes the terminal's foreground program (a killed integration is found before anything is queued), checks the target (mentions as typing checks them, `HandoffMention`), records the terminal's tail for `since: "prompt"`, and queues `AgentMessage {id msg_…, text, from, label, when, mentions, queuedAt}` for the agent session there. None of typing's refusals apply (`blocked`, a restored `working`, another foreground program): nothing reaches the screen. The result says `delivery: "message"` and the message's id. A session that ends while the message is being sent (the terminal's text is read first; `Board.agentSession` moves on) gets nothing, and the call fails `unavailable`. Messages leave when the integration acks them, an app restart keeps them, and when their session ends first they bounce.
- **Session ends and bounces** (`Board.endAgentSession`): the agent session a message was queued for ends at `agent.release`; at its integration dying (an `idle` or `done` agent whose integration took messages, its shell back at the prompt with no release, as after a SIGKILL: `props.agent.protocol` goes, its state and answer stay, and `agent.prompt`, typed or not, and `agent.wait` fail `unavailable` until an agent reports there again); at a report of another agent kind, or without `protocol`; at `agent.report_session` with another session id; at `agent.restart`, which kills it (Agent control, below); and at the terminal's deletion, once the step that deleted it closes with it still gone (a failed `object.batch` puts back the deleted terminal's queue and aliases, and the mentions it stripped). What was still queued bounces, never dropped silently: back to a sending terminal whose integration takes messages, as a message from `easl` on the user's behalf (`undelivered to <the receiver's address>: <its first line, cut at 80 characters>…`); a script's, or one whose sender takes no messages or has closed, into the receiver's board.history as a `message` entry (the receiver's id, the same text and `(from <sender>)`). A waiting `agent.wait` on the receiver looks again.
- **Delivery** (`agent.inbox`, the integration's own terminal as `tile`): a long poll (`waitMs`, ≤ 60 s) answers the messages waiting that no open connection holds, each sender's name and address and each message's mentions resolved at that moment (the `context` block is the hand-off block a drain gives, `Board.resolveHandoffs`'s: "Attached by terminal obj_… "name" to its prompt to you (agent.prompt):", or "by a script"). The answering connection holds them until it acks them (`ack`) or closes, when they are offered again, so an integration that restarts or loses its connection mid-reply loses nothing. An integration acks a message once its agent has recorded it, never before, and dedupes by id. `ack` with `started: true` says the delivery started a new turn (the agent was idle), `false` that it joined the running one.
- **omp** (`extensions/omp/easl.ts`): one long poll per tile's root session (subagents have none); messages arriving within 250 ms of each other are delivered as one card: `pi.sendMessage` of easl's own custom message (`customType: "easl:message"`, `display: true`; not omp's `irc:incoming`, which omp's `wait` returns from its queue as a bare text result and whose leftover at a run's end wakes the agent even after Esc). The extension draws it as omp draws its own incoming IRC messages (`pi.registerMessageRenderer`: `💬 IRC ← reviewer@canvas` and its age over the quoted text, three lines until unfolded), and omp's session history and retros print it as `[easl:message] <irc> Message from …`, apart from the user's prompts. A burst is one card, so it is steered, starts a turn, is recorded and acked as a whole. Its `details`: `id` (the message's, a burst's first), `from` (the sender's address, a script's label or a closed terminal's tile id; a burst's senders joined), `message` (the text as written; a burst's joined) and `ids` (every message it carries). Its content, what the model reads, puts each message in an `<irc>` envelope like omp's: who sent it, its text with its mentions' block after it (the `<` of an `irc` or `system-*` tag in them escaped, as omp's `escapeHarnessTags` does), how to reply (`write` with `path: "agent://reviewer@canvas"`, the name and board percent-encoded; a script, or a terminal closed since it sent: no reply address), and `(easl message msg_…)`. `attribution` is the message's (a script's in a burst makes the card the user's); omp keeps it on the card. `when: "now"`: `steer` (`deliverAs: "steer"`) while the agent streams (injected at its next step; an interruptible tool such as `wait` is cut short, a question or approval waits for its answer and the message comes after it); while it streams nothing (idle, or a turn awaiting background work) the card starts a turn (`triggerTurn`). `when: "next-turn"`: held until the running turn ends (`agent_end` without `willContinue`), then a new turn; never a steer. Each sender (tile id, or a script's label) wakes the receiver at most 20 times an hour: past that its messages join the step omp is streaming as an aside (`deliverAs: "aside"`), and while nothing streams (idle, or a turn awaiting background work) wait for the next `agent_start`. A card left in omp's queue when a run ends wakes a turn, unless the user stopped the run (Esc), as a user message's did. omp starts a turn with a card without preparing it (no `before_agent_start`), on the system prompt the last prepared turn left: none of easl's guidance in a session the user never prompted, or standing orders since changed. So every card's id is marked, and until omp next prepares a turn (a prompt of the user's, or a script's queued card, which omp prepares as one), each request of a turn omp didn't prepare gets, through omp's `context` event, the easl guidance and the board's standing orders as they are now (read once a turn), saying they replace any earlier in the system prompt (or that the board has none now; nothing about them when easl doesn't answer), as hidden context just before the first marked card (first, when compaction dropped it); never recorded. A message is acked once omp records it: the card's `message_end`, or a user message carrying its `(easl message msg_…)` line (omp puts a queued user-attributed card, a script's, back in the editor as its text on Esc or Alt+Up, and the user sent it); its id is saved in the session (`easl.messages` entries), so a restarted omp offered it again acks it instead of delivering it twice. One omp hasn't recorded 5 s after it was handed over, with nothing streaming or queued (omp couldn't start the turn: no model; or the user dropped it from the editor), waits for the next turn that starts and the user is told (`ctx.ui.notify`); easl keeps it meanwhile. Polls and acks share the inbox connection, which any failed or timed-out call closes, so easl offers what it held again; a burst whose follow-up fetch fails still delivers what came. On a session switch, messages arriving before easl has the new session's report are the old session's (easl bounces them) and are not delivered.
- **Attribution.** A message with a `caller` and no `from` is the agent's (`attribution: "agent"`, the sender its terminal). With `from` (a script's label: `easl tell reviewer "…" --from machine-watch`, roblox's launchd tick) or without a caller it is the user's (`attribution: "user"`), named by `from` (default `script`), with no reply address.
- **agent.wait and agent.read final keep their meaning**: while a message to the terminal is queued or held, `agent.wait` doesn't answer and `final` is `unavailable`; an ack with `started` starts the prompt grace as a typed prompt to an idle agent does (the turn must start within 60 s); an ack that joined the running turn answers when that turn ends. A typed `next-turn` prompt to a `working` target (no message integration) is `conflict`: typed text would join the turn.
- **Unknown agents in omp.** omp's native `write agent://<name>` knows only its own process's agents. When it fails with "Unknown agent", the extension resolves `<name>` (or `name@board`) through easl (`agent.prompt` with the session's tile as `caller`) and patches the tool result to the delivery: `isError: false`, content naming the address, and `details.message.receipts` outcome `injected`, so omp's IRC card shows it delivered. A failed lookup keeps omp's error and adds easl's.
- **CLI**: `easl agent.prompt --target <name>[@board] --text <t> [--from <label>] [--when next-turn]`, and its sugar `easl tell <name>[@board] <text> [--when next-turn] [--from <label>]`. Inside a terminal the CLI still sends `caller` (EASL_TILE_ID), which puts that board first for a bare name; with `--from` the message is the script's all the same.

### Agent control

What a supervisor (the machine shepherd, a board's chief of staff) needs to see and steer every agent, closed boards included (`Sources/CanvasCore/AgentControl.swift`).

- **agent.list, per agent**: `open` (its board is open), `focused` (`TerminalStatus.focused`: the terminal has keyboard focus in the key window while easl is the active app, `TerminalTile.isWatched`; the user may be typing in it), `draft` (the agent's input editor holds unsent text, `props.agent.draft`), `model` and `thinking` (`props.agent`, from `agent.report_session`), `pid` and `live`. `pid` is the agent's process: the one its integration reported (`agent.report` `pid`, `props.agent.pid`) while that process lives (`kill(pid, 0)`), else the foreground process of the tile's session (`ForegroundProgram.foregroundPid`: the job leader on the shell's terminal, a `-c` shell's child), absent at the shell's prompt or when the session is gone. `live` is whether the tile's zmx session runs: one `zmx list` per call (`ApiRouter.terminalSessions`, `Zmx.sessions`, off the main actor) finds the sessions labelled `canvas.tile=<tile>` with this instance's `canvas.home` (see zmx session names above), each with its `canvas.board` and its shell's foreground process; absent without zmx. A hosted terminal (`props.host`) runs on its host: its `live` is its host's easld's `session.list` (`ApiRouter.hostedSessions`, `TerminalHost.liveSessions`: a session labelled with this instance's `canvas.home`), asked only of a host this app is connected to and absent when it isn't or doesn't answer, never this Mac's zmx; it has no `pid` (its processes are the host's, not this Mac's: neither the app nor easl tests the pid its integration reported on their own machine, where another process may have that number). A remote board's terminals (client mode) are its host's agents: the viewer's agent.list doesn't list them, and its agent.restart doesn't reach them; the host's API does both.
- **Closed boards**: agent.list lists the open boards' terminals (boards by id, terminals by tile id), then those of every stored board that isn't open, read from its board file (`StoredTerminals`, cached per file until its modification date changes, read off the main actor): `open: false`, `focused: false`, the lifecycle as saved with a saved `working` or `blocked` marked `restored: true` (as opening the board marks it), `address` `name@<root folder>`, no title, program or last command. Their agents keep running in their sessions (`live`); what they report while the board is closed is spooled and replayed when it opens (Lifecycle authority). agent.prompt, agent.wait, agent.read and agent.restart reach open boards only.
- **Draft**: every report of omp's extension says `draft`: whether `ctx.ui.getEditorText()` holds anything but whitespace, looked at every 500 ms while its session runs and reported when it flips, so text omp puts there itself (a Ctrl+D draft it restores after `session_start`, the external editor's) counts as much as typed text. A report without `draft` (another integration, an older extension, omp without its TUI) removes it: unknown. omp's extension reports `pid` (`process.pid`) the same way.
- **Model and thinking**: omp's extension sends `model` (`<provider>/<id>` of `ctx.model`, what `omp --model=` takes) and `thinking` (the configured selector, what `omp --thinking=` takes, `auto` kept: `pi.getThinkingLevel()` is the effort auto chose, which as `--thinking` would turn auto off) with `agent.report_session` at session start and switch, and whenever either changes, looked at every 500 ms (`/model` and the thinking toggle fire no extension event), idle or not. The selector is the session branch's last `thinking_level_change` this omp recorded (`configured`, else `thinkingLevel`), else the `--thinking` omp was launched with while the session it launched with is the first the agent runs (process-wide, until a session switch: a session switched to, the launch one too, runs what it recorded), else the branch's last one; none when nothing says (a new session at omp's default before its first turn). Each check reads the branch back from its leaf only to that change or to the leaf it read last time, so checks cost the same however long the session is. The extension counts a report as acknowledged only when easl answers it, and none while one is out (it may apply unanswered); it sends one easl hasn't acknowledged again every 10 s, and again when easl comes back (`watchCanvasReturn`). A report without one keeps the last.
- **agent.restart** `{target, mode, args?, force?}`: refused (`conflict`) while another restart of the terminal runs or a prompt's paste and Enter are going into it (`ApiRouter.pasting`, a bounded step: even forced, the paste would land in the relaunched agent), and unless `force` while the agent is `working` (restored or not) or `blocked`, has a prompt whose turn hasn't started (`ApiRouter.promptPending`: one being typed, its checks and screen reads included, or one submitted, or a message its integration delivered with `started`, that its agent hasn't reported working on within `promptStartGrace`, what agent.wait waits out), has a message queued that its integration hasn't taken yet (`Board.messages`, which agent.wait waits for too; forced, it bounces), may hold a draft (`draft` true, or absent: an integration that doesn't report it may have one), or its terminal is `focused`, checked in that order. The relaunch (`AgentResume.relaunch`): the tile's `command` options when it runs that agent (`AgentResume.options`: its session selectors and prompt left out, as a reboot's resume leaves them), the recorded model and thinking replacing any the command gave (omp `--model=<m> --thinking=<t>`, omp 18.6.1 `--help`; claude `--model`, codex/gemini/opencode `-m`; only omp reports them today), then `args`. `resume` appends the agent's session selector (omp `--resume=<sessionPath>`, which takes a path or id prefix, else the id; `AgentResume.grammar`'s for the others), `unavailable` without a recorded session; `fresh` leaves it out, and a terminal with no known agent reruns its `command`. From then until the restart ends, however it ends, the terminal is reserved (`ApiRouter.restarting`): `agent.prompt` to it, typed or queued, is `conflict` ("… is restarting (agent.restart) …"), `agent.inbox` offers it nothing, and another restart is `conflict`. A typed prompt is for the agent session it found (`Board.agentSession`): one that ends while it reads the screen (released, replaced, restarted, forced or not: those reads have no deadline, so they don't hold a forced restart off) gets nothing typed, `unavailable`, as a queued message's does. The app (`ApiRouter.restartTerminal`, `TerminalTile.restart`) checks the refusals again just before the kill (`killing`; a turn, prompt, draft or focus that came meanwhile calls it off), kills the zmx session as deleting the tile does (`killArguments`: the owner guard, then zmx's log) and confirms it gone (`endSession`: zmx no longer lists it, within 3 s); a kill that can't run, a session another instance owns, or one zmx still lists (or can't list) is `unavailable`, with nothing relaunched, no session ended and no queue bounced. Once it is gone the killed agent's session ends (`Board.endAgentSession`, through `restartTerminal`'s `ended`) and the tile records the relaunch (`Board.restartedAgent`), both before the relaunch starts, so what the relaunched agent reports from then on stays; a tile closed while its session was killed is `not_found`, with nothing relaunched (its delete ended the agent session). The tile keeps its id, frame and name; its `command` becomes the relaunch without the session selector (a reboot reruns it and resumes the session the new agent records), its lifecycle is cleared (`agent.lifecycle` null: agent.wait gives the new agent 15 s for a first report), and `props.agent` keeps kind, protocol, model and thinking (and the session, resumed), taken before the kill, since the old agent's `agent.release` as it exits clears it. Its prompt bookkeeping (`since: "prompt"`, the prompt grace), approval waits and the composer's undrained prompts go with the old agent. Then the surface runs `zmx attach … <shell> -l -c '<argv>; exec <shell> -l'`, which starts a new session: a configuration that differs rebuilds the surface, and one that reads as the old (a second resume of the same session, a plain command rerun) is reattached all the same; the old surface's close within 10 s is ignored (it would otherwise delete the tile as an exited terminal). A hosted terminal is restarted on its host (`TerminalHost.restart`): after the same check its easld ends the session (`session.kill` with this instance's home label), and once its `session.list` no longer lists it (≤ 3 s; else `unavailable`, before `ended`) starts the relaunch (`session.spawn`, `TerminalTile.hostedSpawnParams` with the relaunch as `command`), and the tile's attach loop starts again; `unavailable` while the host is offline, with the session left as it was. A remote board's terminal is never restarted by the viewer (`unsupported`): the host's own easl restarts it, through its API. Peer messages: in either mode what was still queued for the killed agent bounces (Session ends and bounces, above) and none of it reaches the relaunched agent; a restart refused or failed before the kill leaves the queue as it was. easld (`agent.restart` forwarded to a client) checks the call and the refusals itself (focus aside: it has no window), refuses one while it forwards a typed prompt to it (`typing`, even forced: the client's answer is due within its 10 s deadline), then holds the terminal for the restart that owns it (`restarts`) as the app does: `agent.prompt` to it is `conflict`, no inbox poll takes what is queued for it, and another restart is `conflict`; it bounces the queue once the client answered with the relaunch, and offers it again when the client refused or failed. The CLI: `easl agent.restart --target <id> --mode resume|fresh [--args '<json>'] [--force]`.
- **Spawn**: `easl agent spawn --name <n> --cwd <dir> --command '<argv>' [--board <id>] [--prompt <text>] [--wait] [--timeout <ms>]` (cli/easl.ts) is `object.create` of a terminal (`command` a JSON array or shell-like words), then with `--prompt` `agent.wait` until the agent reports `idle` (retrying the first-report `unavailable` until the timeout, default 120 s) and `agent.prompt`; `--wait` waits for that prompt's turn too (without `--prompt`, until the agent is ready).
- **Board standing orders**: each turn omp's extension reads its own board's note keyed `rules` (`object.find {board: EASL_BOARD_ID, key: "rules"}`, one call in `before_agent_start`, so an edit reaches the next turn) and appends its markdown to the system prompt after the easl guidance (`extensions/guidance.ts`), headed as the board's standing orders. A turn an easl message starts, which omp doesn't prepare, gets both as hidden context instead (Peer messages). Nothing when there is no such note, it isn't a note, it's empty, or easl doesn't answer (the client's 1.5 s timeout). More than 8 KB (UTF-8) is cut at a character boundary with a notice saying so and how big the note is.

## Lifecycle authority

- The omp extension is authoritative for omp tiles (`source: "canvas-omp"`). It reports `blocked` while omp waits on its user: an approval dialog (`approve <tool>?`) or the `ask` tool (its first question). omp's `tool_approval_requested` event comes only from its registered-tool wrapper; eval preludes (the `browser` and `computer` globals inside `eval`) ask for approval with no event, so the extension wraps `select` on the session's UI context (the object behind `ctx.ui`, which tools and preludes prompt with) and treats each dialog titled `Allow tool: <name>` as an approval until it settles. It depends on that title; an omp that renames it reports no approval blocking.
- The Claude Code, Codex and Gemini CLI hooks and the opencode plugin ("Agent integrations") report with `source: "canvas-claude"` / `"canvas-codex"` / `"canvas-gemini"` / `"canvas-opencode"`.
- A report with a lower `seq` than the last accepted one from the same source is ignored, across restarts too (`lifecycleSeq` is saved with the board).
- Agent report spool: a lifecycle report an integration can't deliver (`unavailable`: no socket, the app quitting or restarting; `timeout`) is written by `extensions/agent-hooks/report.ts`, which the omp extension, the hooks and the opencode plugin share, to `agent-reports/<tileId>/<seq>-<pid>-<random>.json` beside the socket (`dirname $EASL_SOCKET`), as `{seq, method: "agent.report" | "agent.release", params}`, under a hidden name and then renamed; writing never throws or blocks the agent. When the app opens a board (`BoardRegistry.open`, so at launch for the boards it reopens) it reads its terminals' spools off the main actor, applies them oldest `seq` first as if they had arrived (`Board.replay`: `agent.report` through the staleness rule; `agent.release` only when no report from the same source is newer), and deletes them. A spooled file it can't read (permissions, IO) stays for the next open; one that reads but isn't a report is deleted. So an agent that finished while easl was closed comes back `done` (unseen: ⌘J, the tab dot, a notification) with its `final`, and a report applied before the quit is dropped as stale. A report easl answered with an error is not spooled. Deleting a terminal for good deletes its spool.
- A restored `working` or `blocked` is the agent's last word until it says more (the spool, its next report). The app marks it `restored: true` as it loads the board file (`Board(snapshot:)`), and the agent's next report, live or replayed, writes a lifecycle without it: until then `agent.list` and `agent.wait` show what the agent was, not what it is (an omp extension loaded before the spool existed drops what it says while easl is closed). `agent.prompt` refuses a restored `working` (`conflict`, unless `force`): the agent may now sit in a question or approval, which the pasted text's Return would answer. Integrations that live as long as their agent say it again when easl comes back (`watchCanvasReturn` in `extensions/agent-hooks/report.ts`: a new socket file at `EASL_SOCKET`, checked every 2 s): the omp extension re-reports its current state and the opencode plugin its last report, so a restored state lasts seconds after a restart; the Claude Code, Codex and Gemini CLI hooks run per event and report again at the agent's next one (a finished tool call reports `working`). A restored `blocked` is refused like any `blocked`. An integrated agent claimed `working` or `blocked` while its terminal's foreground is the shell at its prompt (`Board.terminalProgram`, from the process table: killed, or exited while easl was away without its release) is released like an exited notifying agent: lifecycle `unknown`, `agent.wait` fails instead of hanging. An agent still running whose integration stopped reporting keeps its last state until it reports again or the next prompt.
- `done` is derived by the app: an `idle` report on a tile that has not been seen since it was last `working`. Seeing counts only once the turn has ended (`Board.markSeen` ignores a `working` or `blocked` tile): a turn that ends after the user looked away is `done` until they look again (the tile on screen for 3 s, the keyboard in it, or ⌘J there).
- An agent without an integration reports by terminal notification (`NotifyingAgent`, `Board.terminalNotified`): an OSC 9 or OSC 777 `notify`, or a bell, from a terminal whose foreground program isn't its shell and whose lifecycle no integration reports sets `lifecycle` `{state: done, message: <the notification>, seen: false, via: "notifications"}` (`idle`, `seen: true` while the user looks at the terminal) and `agent.kind` to the program's first word (`aider`). A bell within 1 s of a key the user typed in that terminal (`NotifyingAgent.bellAfterKey`: vim at Esc, less at the end) is no such signal, and at the shell's prompt a notification or bell raises an attention marker instead. Return typed into the terminal, or an `agent.prompt` to it, sets `unknown` (a notification comes only when the agent waits after model work, so Return can't mean `working`); it never reports `working` or `blocked`. `agent.report` `unknown` (`bin/aider` as aider starts) sets `via: "notifications"` too, so the tile is an agent before its first notification. The shell back at its prompt (`Board.terminalProgram`) releases it (`agent.release`'s effect); a program it runs meanwhile (its editor) doesn't. Its tile gets no attention markers from its notifications (the dot says it), and its shell's command marks stay the user's (`NotifyingAgent.integrationReports` is false).

## Questions

A question (`type: question`, schema `QuestionProps`; `QuestionSpec` and the `Board` extension in `Sources/CanvasCore/Question.swift`, `QuestionTile` in the app) is how an agent asks the user for a decision on the board. Status runs open → answered | cancelled | expired, each final. **Archive is not a status**: `archived: true` on a closed question hides its tile (the app makes no view for it, `TileFactory.hidden`, nor selects or frames it: ⌘A, the marquee, the selection and Zoom to Fit skip it; the object, its frame and its answer stay, and `object.find`/`board.get` still list it); an open question can't be archived.

- **Validation** (`QuestionSpec.problem`, run by `object.create`/`update`/`upsert` and their batch ops before the write and before the `rev` check): the rules in order, first failure as `invalid_params`: a closed question takes only `archived`, `key`, `zoom` (a patch key whose value differs: `question <id> is answered: only archived can change`); `question` non-empty; `options` an array of `{id, label, why?}` (no other keys, ids unique, labels non-empty; it may be empty: the answer is then a note); `recommended` an option id; `context` items exactly one of `{object: Id}`, `{url}`, `{path, lines?}`; `asker` `{tile?, name?, host?}` with a tile or a name (absent on create: `{tile: caller}`, else `invalid_params`); `status` one of the four, `open` on create (written when absent); `expiresAt` RFC 3339; `answer` with `{option?, note?}` (an option id and/or a non-empty note) exactly when answered; `archived` a boolean, true only when closed. easld applies the same rules with the same messages (the `questions` conformance scenario). Before them, a relative `context` path from a caller terminal working in another worktree of the board's repository becomes absolute in that checkout (`Board.inCallersCheckout`, as a code tile's `path`), so the mention and the tile's link name the asker's file, not the board root's; from the board's own checkout, or without a caller, paths are stored as given.
- **Writes**: answering stamps `answer.at` (UTC, whole seconds) and `answer.by` (the caller's `Actor`; the user from the tile); closing without a `frame` in the call shrinks the frame to `QuestionSpec.size` (148 pt, + 40 with a note, at its zoom) in the same write. A frame-less create is sized by the props: 460 × (194 + 50 per option, + 30 with context). The tile's text scales with the chrome text size; content taller than the frame scrolls.
- **Delivery** (`Board.questionWritten`, from `Board.write` and `restore`): a question going open → answered whose `asker.tile` is a terminal on its board is handed to that terminal (`Board.handOff`, header `Your question <id> was answered (easl ask):`), so its integration's next `tray.drain` carries an object mention of the question, its options and the answer (`QuestionSpec.mentionLines`); nothing is typed into the terminal. That hand-off waits only while the question is answered and not yet drained: undoing the answer takes it back, a redo that restores the answer hands it off again (drained before or not), a failed `object.batch` (`Board.atomically`) puts every hand-off back as it was before the batch, and a drain drops one whose question is no longer answered or gone (`Board.handoffStands`). Every subscriber gets `object.updated`; `easl ask --wait` and `easl ask wait <id>` wait on it (exit 0 with the answer JSON; 2 when cancelled, expired or deleted; `ask wait` on an id `object.get` answers `not_found` for is the deleted outcome). No hook command is stored in a question.
- **Expiry** (`Board.expireQuestions`, `scheduleQuestionExpiry`): one timer per board at the earliest open `expiresAt` (at most a day out, then re-checked), set when the board opens (`BoardRegistry.open`) and whenever a question is committed; a due question becomes `expired` as the app's own write (no undo step, `updatedBy` user, activity `system`) on the next turn after the write that made it due, never inside that call.
- **Needs you**: an open question not past `expiresAt` is a `NeedsYouItem` with reason `.question`, after blocked terminals and before markers, so ⌘J (which gives it the keyboard: 1–9 pick, Return answers, Tab to the note, Esc back) and Go to's flagged rows visit it; `AsksChip` beside the drawing toolbar counts `Board.waitingQuestions` and goes to the next on a click. `object.find` with `type` (and `status`) lists them, oldest first.

## Ownership rules for slices

- The schema file is the only place API shape changes. Changing it means regenerating clients (`bun scripts/gen-clients.ts`) in the same change.
- Swift model types mirror the schema; a slice that needs a new field adds it to the schema first.
- No slice introduces a new socket, environment variable, or on-disk location without adding it here.
