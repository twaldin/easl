# easl contracts

Interfaces every slice builds against. The API wire format and object model live in `schema/easl-api.json`; this file covers what the schema can't express: sockets, environment, the Swift tile protocol, the mention context format, and ownership rules.

## Sockets

| Socket | Path | Speaks | Owner |
| --- | --- | --- | --- |
| easl API | `~/Library/Application Support/Easl/easl.sock` | `schema/easl-api.json` | App |
| cmux browser subset | `~/Library/Application Support/Easl/cmux.sock` | cmux v2 JSON lines, browser methods only | App (isolated, deletable) |
| easld owned-session cmux subset | `<easld home>/cmux/<terminal id>.sock` | The same cmux v2 browser subset | easld, one listener per owned terminal |

All sockets are created with mode `0600`. The cmux subset lives on its own socket so it never shares method names with our API and can be removed in one step.

The easl API checks every request's params, and each `object.batch` op's, against the method's schema before it runs (`ApiRouter.checkParams`, from `ApiParams`, which `scripts/gen-clients.ts` generates from the schema): a param the schema doesn't list, or a required one missing (or `null`), is `invalid_params` naming the unknown and missing keys and every param the method takes, required ones marked. A `caller` is honored when it is a terminal tile on any open board, so an agent working on another board (`board`) is credited there (`createdBy`/`updatedBy`, `board.history`) as on its own; placing beside the caller applies only on its own board.

### cmux browser subset

Exactly what omp's cmux browser backend sends (`src/tools/browser/cmux/`), framed as cmux v2 JSON lines: requests `{"id","method","params"}`, replies `{"id","ok":true,"result"}` or `{"id","ok":false,"error":{"code","message"}}`. Surfaces are object ids: a terminal tile is the calling surface (`CMUX_SURFACE_ID`), a browser tile is a browser surface; workspaces are boards. Every browser result carries `surface_id`.

Surface and workspace ids stay `obj_…`/`brd_…` on the wire, which omp 18.3 accepts; omp ≤18.1's owner inspection (`surface.list` via its surface-observation module) requires UUID ids and is unsupported.

Agents without omp's tool use the same subset through the CLI (`cli/easl.ts`): `easl browser <verb> [<tile>] [--key value]` sends one request per call on its own connection (`auth` first when `CMUX_SOCKET_PASSWORD` is set; `CMUX_SOCKET_PATH`, else `cmux.sock` beside the easl socket): `open [url]` is `browser.open_split` from `CMUX_SURFACE_ID`, `list` is `surface.list`, `close` is `surface.close`, any other verb is `browser.<verb>` with `<tile>` as `surface_id`; `screenshot` writes the PNG (`--out`, else `$TMPDIR/easl-renders/screenshot-<ms>-<pid>.png`) and prints its `path` instead of `png_base64`.

On easld, each owned terminal's socket captures its caller identity, including across fresh CLI connections and when driving a browser on another open board. `browser.open_split`, `surface.list`, `canvas:` adoption and `surface.close` run on easld. Page commands become `browser.call` on the tile's exact drawing client; browser `object.reload` selects the same client. A missing drawing client returns `unavailable`, naming the machine as `draws on <host>, which is offline`. A connected client without the capability is reported separately. Neither case falls back to another Mac. `browser.wait` uses the same rounded, capped timeout as the Mac parser, plus five seconds of delegation grace.

CLI help is local. `easl <method> --help` (or `-h`) and `easl help <method>` print the bundled schema's description, parameters, required fields, types, and result without opening a socket. `easl --help` prints usage; `easl browser <verb> --help` describes the cmux subset below. Unknown methods exit 2 and suggest close matches.

A page an agent is driving stays visible to WebKit for 60 s after its last command, even when its tile is offscreen, the window is minimized, in a background tab, on another Space, or covered, or the app is hidden: `document.visibilityState` is `visible` and `requestAnimationFrame`, timers and `IntersectionObserver` run as they would for a user. Window occlusion detection is off for the page, and while its tile can't show it the web view waits in `WebStage`, a transparent click-through window of its own that stays on screen (ordered in only while something waits in it). A page that was hidden gets up to 0.5 s to present a frame before the command runs, so the first command already sees it visible. Then the tile's normal policy resumes: a page nobody can see (its tile offscreen or zoomed out, its window minimized, covered, in a background tab or closed, the app hidden) waits hidden in its tile, so WebKit treats it as hidden (no `requestAnimationFrame` or CSS animation, timers throttled more the longer it stays hidden), and one whose tile isn't live is released 2 minutes later (`object.get` then says `page.loaded: false`; the next command or render loads it again from `props.url`, with its in-page state gone). A hidden page still commits a frame for every DOM change, and each commit wakes WebKit's display link in the app for a moment; releasing is what makes an unseen page with a clock or a live-reload socket cost nothing. `view.render` of a browser tile counts as a command: a page that isn't loaded loads (in the stage) and is waited for until the render's `timeoutMs`.

The terminal a command comes from (its driver) is the one the connection opened splits from, else the one that opened the tile, else none. `board.history` credits a page's URL changes and the tiles it opens (`_blank`, `window.open`, ⌘-click) to whoever last acted on the page within 10 s (`NavigationCredit`): a driven command that can act (`navigate`, `back`, `forward`, `reload`, `eval`, element actions, `type`, `fill`, `press`) → its driver (`system` when none), the user clicking or typing in the page, its address bar, back, forward or reload → `user`; otherwise (a redirect or timer later on) `system`. A tile the user opened from a page is revealed (least pan) and selected; one an agent's command opened isn't. The same address opened again from the same page within 2 s gets the first tile back.

Error codes: `invalid_params`, `not_found`, `method_not_found`, `unauthorized`, `timeout`, `js_error`, `unavailable`. The plain-text line `auth <password>` answers `OK: …` or `ERROR: …`.

### Page log (console, errors, failed requests)

Every browser tile's main frame runs `PageCapture` (CanvasCore/PageLog.swift) in the page's own world at document start, so it sees the page from its first line on. It records console messages (`log` `info` `warn` `error` `debug`, as the console formats them, up to 1,000 characters; warnings and errors with the `url:line:column` of the code that logged), uncaught errors and unhandled rejections (message, source, stack), and failed requests: `fetch` and `XMLHttpRequest` answered 400 or more or never answered (network error; an aborted request isn't a failure), and elements whose resource failed to load (`img`, `script`, `link`…, from their `error` events; WebKit exposes no status for those). Errors and warnings go in one ring of 200, other messages in another of 200, so a chatty page never pushes out its errors; what falls out is counted (`dropped`). The tile hears nothing but the page's error count, at most once per 100 ms burst and 0 at every new document (message handler `canvasPageLog`, page world); everything else is read on demand (`__canvasPageLog.read()`, a non-enumerable, non-configurable global). The page's own document answered 400 or more is its first entry (`resource: document`, from the navigation response, once that navigation commits: `DocumentFailureTracker`; a page back from the back/forward cache has no response of its own and takes its history entry's, so Back from a 404 drops the entry and Forward to it brings it back). Web vitals: LCP by `PerformanceObserver` (buffered) where WebKit has the entry type; CLS and long tasks (`layout-shift`, `longtask`, which WebKit lacks) are null and listed in `vitals.unsupported`; FCP, TTFB, DOMContentLoaded and load from the paint and navigation timings, null until they happen. Hooking `console` means the Web Inspector's console attributes messages to `canvas-page-log.js`; their stack traces still lead to the caller.

It also starts omp's cmux capture globals in the shapes omp installs after load, which omp then leaves in place: `__ompConsoleCapture` (`{entries: [{seq, ts, type: console|pageerror, level, text, args, location?, stack?}], nextSeq, dropped}`, 500 entries; `args` serialize when omp reads them) and `__ompCmuxResponses` (`{nextId, records: [{id, ts, method, resourceType, url, status, statusText, headers, requestHeaders, body, durationMs}]}`, 200 records, text bodies up to 64 KiB, none for streams or binary types). A record is every `fetch` and `XMLHttpRequest` that got an answer (`resourceType` `fetch`/`xhr`, its status), plus every request the page log counts as failed without one: a `fetch` that never got an answer and an element whose resource failed to load, with `status: 0`, `statusText` the reason (`failed to load`), and `resourceType` the element's tag (`script`, `img`, `link`…; omp's `requests()` reports every type but `xhr` as `fetch`). So omp's `requests()` lists what `object.get`'s `page` lists as failed requests, except the page's own document (in `page` only), and never the page's successful document, script, style, image or font loads. omp's `tab.console()`, `errors()`, `requests()` and `waitForResponse()` cover the page's load. XHR is observed through `XMLHttpRequest.prototype` (`open`, `send`, `setRequestHeader`), not by replacing the constructor.

`object.get` on a browser tile adds `page` (schema `PageLog`): the counts since the page loaded, the latest 100 entries (after `since`, a `page.cursor` from an earlier call; one from an earlier document returns all of this one with `reloaded: true`), and the vitals; `loaded: false` when the tile has no page (released or never shown). `visibility` says how WebKit runs the page now (`PageReport.Visibility`): `visible` (on screen: requestAnimationFrame at the display's rate), `hidden` (in its tile where nobody sees it: no rAF, timers throttled more the longer it stays hidden), `driven` (kept visible for an agent though nobody sees it: rAF and timers run, irregularly and slower), `released` (no page). A page easl releases leaves its log behind: the tile reads it from the page as it goes, and `previous` returns it (the same fields plus `releasedAt`) until the page loads another document after the reload, and until `since` names the current document; while released, `cursor` is the released page's, so a cursor loop goes on across the release (the reload returns all of the new page with `reloaded: true`). The badge in the tile's address bar ("2 errors", only while there are any) opens a list of the errors, newest first (message, kind, `file:line`, time); a Hyper-click on a row stages a `console` mention (schema `MentionTarget`: `object`, the page's `url`, and the `entry`). A click on a row shows its whole message and stack; a `file:line` or stack frame served from a file under the board root opens that file's code tile at the line (`PageSource.file`).

## App updates

`app.update` operates on the connected Mac app, not on a board's remote host. Its required `mode` is `check` or `install`. Missing, null, or unknown modes return `invalid_params`. An app router without an updater returns `unavailable`. easld preserves its existing unknown-method refusal, `invalid_params` with `unknown method app.update`.

The CLI accepts `easl app.update check`, `easl app.update install`, and the equivalent `easl app.update --mode check` or `--mode install`. Both modes return the same state fields:

| Field | Type | Meaning |
| --- | --- | --- |
| `currentVersion` | string | The running app's bundle version. |
| `availableVersion` | string or null | The latest feed's version, even when it is not newer, or null before a successful check. |
| `installPending` | boolean | An update is downloading, verifying, waiting in verified staging, or installing. A newer release merely being available does not make an install pending. |
| `phase` | string | `idle`, `checking`, `available`, `downloading`, `verifying`, `ready`, `installing`, or `failed`. `ready` is verified staging awaiting idle or explicit installation. |
| `error` | string or null | The check, download, verification, or installation failure reason, including a persisted failure from the previous attempt, or null. |
| `deferred` | string or null | `"remote viewer active"` while an enabled automatic install is ready but recent remote activity prevents it. Otherwise null. |
| `interruptions` | array | For an accepted `install`, or one already in progress, live remote sessions with `session`, `kind` (`browser`, `board`, or `terminal`), `board`, and nullable `tile`. Empty otherwise. |
| `warning` | string or null | For an accepted `install`, or one already in progress, warns when restarting interrupts the listed remote sessions. The explicit install still proceeds immediately. |

`check` fetches the feed without a modal alert and reports state. `install` checks for a newer version, downloads and verifies it, and starts installation without confirmation or an idle requirement. A failed feed check preserves verified staging, which `install` can still use. An accepted install returns `phase: "installing"`, `installPending: true`, and `error: null`. Only that request's connection can authorize the update to quit. Other `check` or `install` calls during installation report state without controlling the original acknowledgment.

The app waits until the complete acknowledgment, including its newline, is written to the calling connection. It then gives the CLI one second to display the reply. No replacement helper runs during either wait. After the grace period, the app saves the current open-board snapshot again, starts its helper, and requests sheet- and modal-safe termination without suspending between these steps. A snapshot or helper-start failure aborts installation without quitting.

A write failure, closed connection, or failure to finish writing within 30 seconds aborts installation without quitting. A timeout closes the stuck connection and invalidates queued writes. Bytes already written cannot be withdrawn. An acknowledgment observed at the deadline boundary can still be followed by an abort, so reconnect to confirm the outcome. An ordinary quit during the acknowledgment wait or display grace cancels the prepared board snapshot and persists a failure synchronously before closing API connections. It cannot replace or relaunch the app because no helper has started. These aborts retain the existing 24-hour automatic retry cooldown without rejecting the checksum. Staged-copy removal is queued off the main thread and does not delay termination.

The acknowledgment means installation was accepted, not that a helper has started or replacement or relaunch succeeded. The connection closes when the old process quits. A client reconnects to the relaunched app to inspect `currentVersion` and `error`. An unsuccessful request reports its failure in `error`. A retained failure is not cleared merely because another action started.

`UISettings.installUpdatesAutomatically`, stored in the Mac's `ui-settings.json`, defaults to false. The easl menu's **Install Updates Automatically** toggle changes that preference. With it enabled, only newer releases download and pass `AppUpdate.prepareInstall` before waiting in `ready`. Installation requires 600 seconds since both the last input anywhere in the macOS login session and the last remote activity. Remote activity includes fresh browser-stream input, dialog answers, changed frames sent to a viewer, and input from an attached remote board viewer, including typing into its SSH/zmx terminal. Acknowledgments, unchanged browser captures, terminal output, and background API traffic do not reset the wait. Disconnecting a viewer retains the wait until its last activity expires. The policy works without drawable terminal tiles. The updater rechecks both idle durations immediately before it starts the helper and quits.

Local idle is the minimum of the session's HID-idle sample and monotonic time since native app input. Native events renew activity even when the HID clock is stale. This same clock controls terminal redraw throttling, so a later HID sample cannot undo recent app input.

The development `input idle on|off|auto` override controls local idle for redraw throttling and automatic installation. `on` supplies 600 local idle seconds, `off` supplies zero, and `auto` resumes combined HID and native-app activity. Input received while pinned is retained for `auto`. It does not bypass remote activity. Sampling continues while pinned so a deferred update can proceed after remote activity expires. The redraw threshold remains 60 seconds. Development instances check automatically only with an `EASL_UPDATE_URL` loopback feed.

Remote viewers report `viewer.activity` on their board event connection. The Mac host requires that connection's subscription to `object.updated` on the open board. `input: false` registers the attachment without resetting idle time. `input: true` records user input; optional `terminal` must identify a terminal on that board. Viewers coalesce bursts with a one-second trailing report, timestamped on receipt by the host. Closing the connection or board, or deleting the terminal, removes its interruption warning. Older viewers do not report board or terminal input and need an app update for that protection. Browser-stream activity is observed directly on the drawing Mac, including when easld relays it.

Automatic, API, and manual installs use the same size, SHA-256, bundle signature, Team ID, Gatekeeper, and version checks, including verification of the staged copy. The existing development-only Gatekeeper exception for two ad-hoc signed builds remains limited to development instances. It does not accept an unsigned or invalidly signed bundle. A refused update leaves the running app unchanged. Automatic feed-check failures only log and remain available as API errors, without a user notice even when automatic installation is off. Download, verification, installation, and recovery failures persist and show a nonactivating board notice when the user looks at a visible, nonminimized board on the active Space. Startup cleanup reconciles the running bundle before any pending install failure notice appears. A staging folder matching the running bundle's version counts as installed even without a helper result and clears the interruption marker. Unresolved board recovery also sets a dock badge. Failures do not open a modal failure sheet. Only artifact trust failures reject a release checksum. A missing or invalid downloaded bundle is a trust failure, but a missing or invalid local staged copy at installation is not. Transient failures wait for a scheduled check instead of retrying at every idle poll. Install handoff persists a retry deadline 24 hours ahead. A failed or interrupted handoff blocks automatic staging and installation until that deadline, including after relaunch and its first feed check. Download interruption markers have no cooldown. Manual and API installs bypass the automatic cooldown. Successful staging or installation clears the previous failure and cooldown.

Before installation starts, the app saves an update-specific snapshot of its open local and remote boards, tab order and groups, selected tabs, and minimized windows. A snapshot write failure aborts installation. An abort while the old app is still running removes only the current attempt's snapshot. Only the marked update relaunch attempts restoration, once, before the normal initial-board fallback. It reattaches remote boards in order and does not open closed background-only boards or an extra home board. Successfully restored local roots are saved to the normal reopen list even on partial failure. Failed or malformed recovery retains information for explicit Retry or Discard, but ordinary launches use the latest normal reopen list and recovery failures do not permanently block later updates. This update snapshot is independent of the user's **Keep Remote Boards Attached** preference.

The helper waits for the old app to quit through its sheet- and modal-safe termination path. It invokes the installed old executable's internal `--update-swap` mode before AppKit or app bootstrap. The mode atomically exchanges the verified incoming bundle and installed bundle with same-volume `RENAME_SWAP`, leaving a complete app at the canonical path even if replacement is interrupted. The old bundle then occupies the incoming path. Archiving it is best-effort and an archive failure does not fail installation.

A per-transaction `.lease` file beside the incoming bundle holds an advisory lock from before download through the idle wait. The helper inherits that lock when the app quits. Startup cleanup preserves locked or uninspectable transactions regardless of age. Unlocked leftovers expire after an hour. A swap child's abnormal exit is reconciled against the canonical bundle's filesystem identity, so a completed exchange is not reported as unchanged.

The helper opens the app through background LaunchServices with `open -n -g` and the one-launch `EASL_UPDATE_RELAUNCH=1` marker. Relaunch neither activates easl nor changes the user's Space. App entry stores and unsets the marker before spawning children. The marker does not change persistent activation settings or leak into terminal shells. `EASL_NO_ACTIVATE` remains honored. Gatekeeper assessment precedes quarantine removal, so background launch does not wait on an unseen first-launch prompt.

The release feed retains the `version`, `url`, `sha256`, `size`, and `notes` wire fields used by 0.2.7 and 0.2.8. Those versions can discover a release that adds automatic installation through their existing manual updater. Enabling the preference requires the updated app.

### Guest-local update artifacts

`scripts/update-proof.py` prepares artifacts from an existing `.build/easl.app` in a claimed `agent-gui` guest. It requires an explicit `EASL_DEV_HOME` below a scratch directory in `/tmp` and `EASL_GUI_GUEST` naming that guest. It never builds, launches a GUI, reads signing identities, publishes a release, or writes production app paths.

The helper copies the real source bundle into `EASL_DEV_HOME/update-proof/old/easl.app` and `new/easl.app`, changes their bundle versions, and signs both ad hoc. Both carry the same isolated bundle identifier and scratch home. They contain the same compiled executable. This exercises a real bundle swap, not historical 0.2.7 or 0.2.8 binaries. The manifest records the source executable's SHA-256.

In the claimed guest, after building the source app separately, prepare the artifacts:

```sh
export EASL_GUI_GUEST=agent-gui
export EASL_DEV_HOME=/tmp/eg.REPLACE/view
export EASL_NO_ACTIVATE=0
python3 scripts/update-proof.py prepare --app .build/easl.app --old-version 0.2.7 --new-version 0.2.8
```

Use the concrete acquired guest name, not `any`. Preparation passes explicit `EASL_NO_ACTIVATE`, `EASL_DEV_SSH`, `EASL_DEV_REMOTE_HOME`, and `EASL_DEV_FRAME` values into both bundles. `EASL_NO_ACTIVATE=0` allows a relaunch-focus proof to exercise the one-launch update marker instead of relying on the development launch guard. Start the old bundle directly with background `open -g -n`, not `dev.sh start`, which replaces launch environment values. Follow the guest claim and capture procedure for every actual launch and pixel capture.

Run the loopback server in a separate guest shell with the same exported home and guest:

```sh
python3 scripts/update-proof.py serve
```

The default feed is `http://127.0.0.1:18766/latest.json`. `prepare --port` chooses another port. The server runs in the foreground, prints its PID and feed URL, and records them in `update-proof/server.json`. Stop that server through its own foreground shell or its recorded, ownership-checked PID.

`update-proof/manifest.json` names both bundles and every artifact. `update-proof/http/` holds `valid.zip`, `corrupt.zip`, `unsigned.zip`, their matching JSON feeds, `notes.txt`, and the selected `latest.json`. Every feed has the actual archive's SHA-256 and byte size. `corrupt` changes a signed bundle resource after signing, and `unsigned` removes the app's signature. Both reach bundle trust checks rather than failing synthetic download pins.

Feed selection is atomic and does not touch the running app:

```sh
python3 scripts/update-proof.py select corrupt
python3 scripts/update-proof.py select unsigned
python3 scripts/update-proof.py select valid
```

Preparation refuses an existing `update-proof` directory instead of overwriting a running source or installed target. Use a fresh scratch home for another old-to-new run. Feed creation alone is not end-to-end evidence. The proof must retain API answers, the old and new PIDs, exact-window captures, focus and Space observations, and mixed local and remote tab restoration.


## App environment

Variables the app itself reads, besides the development ones docs/testing.md lists (`EASL_HOME`, `EASL_NO_ACTIVATE`, `EASL_DEV_*`) and the socket's for clients (Client connection).

| Variable | Default | Effect |
| --- | --- | --- |
| `EASL_UPDATE_URL` | Unset: `https://easl.sh/latest.json` | The `latest.json` that update checks read (`AppUpdate.source`). Set and empty uses the default too. An `http` or `https` address with a host replaces it. Any other value fails checks with "EASL_UPDATE_URL isn't an http or https address". The feed's zip `url` requires HTTPS except on `127.0.0.1`, `localhost`, or `::1`. `scripts/dev.sh` carries the override into the development bundle's `LSEnvironment` for relaunch. Development instances check on request. A development instance with an explicit loopback feed also enables scheduled checks for isolated automatic-update proof. |
| `EASL_UPDATE_RELAUNCH` | Unset | The update helper sets `1` for its background relaunch. The app suppresses activation for that launch without persisting a user preference. |

Nothing else the app inherited reaches the shell except what a fresh login session starts with (`LoginSession`: `HOME`, `USER`, `LOGNAME`, `SHELL`, `TMPDIR`, `LANG`, `LC_*`, `__CF_USER_TEXT_ENCODING`), `SSH_AUTH_SOCK`, `XDG_*`, and what Ghostty sets on the child (`TERM`, `TERMINFO`, `COLORTERM`, `GHOSTTY_*`): the zmx attach runs under `env -u` for every other inherited name. The app's environment is whatever launched it; launched from an agent's tool shell it held `CI`, `NO_COLOR`, `EDITOR=true`, `GIT_EDITOR=true`, pagers set to `cat`, and `CLAUDECODE` (Claude Code then refuses to start). The user's startup files set their own variables again, as in a terminal opened from the Dock.

A tile with an initial command (a spawn's `command`, an agent resumed after a reboot, `agent.restart`'s relaunch) runs `$SHELL -l -c "PATH=<path> <command>; exec $SHELL -l"` (`LoginSession.tileStart`; `<path>` one single-quoted word, with fish's `\\` and `\'` escapes when `$SHELL` is fish); one without runs `$SHELL -l`. `-l -c` reads `.zprofile` but not `.zshrc` (bash: a `.bashrc` that returns when not interactive), where installers often put PATH (bun's, nvm's), and the app's PATH is launchd's `/usr/bin:/bin:/usr/sbin:/sbin` when Finder, the Dock, `open` or the updater's relaunch started it. So `<path>` is what the user's interactive login shell sets up in the tile's directory (`LoginShell.interactivePath`: `$SHELL -lic` in `props.cwd`, else the board's root, with the tile's `PATH`, the user's `ZDOTDIR` if the app had one, and only the session variables, `XDG_*` and `LC_*` above), with easl's `bin/` moved first: a bare command resolves as at the tile's prompt, however the app was started. Only what the shell prints between a start and an end marker counts, so a `.zlogout`, `.bash_logout` or EXIT trap that prints doesn't end up in it. The answer is kept per directory until one of the shells' startup files changes (`stat` of zsh's in `HOME`, `~/.config/zsh`, the app's ZDOTDIR and the ZDOTDIR the shell ended with, e.g. one `~/.zshenv` set; bash's; fish's under `XDG_CONFIG_HOME`; `/etc`'s, `/etc/paths`, `/etc/paths.d`; files they source aren't followed). A shell that fails or hasn't exited by 5 s, also after closing its output (killed with its process group), leaves the prefix out, and the command has the login shell's own PATH, as before; a failed answer is asked again in the background after 30 s. The interactive shell after the command reads the user's files itself and gets no prefix. easld does the same for its sessions (owned and hosted terminals, `session.spawn`), asking `$SHELL -lic` in the session's environment and directory at each start that creates a session (5 s, `Manager.PathTimeout`). The question runs outside the lock spawns and kills share: a spawn looks the session up under the lock, and finding none, unlocks, asks, re-locks and looks again, so a session ended meanwhile (a restart's kill) is still created with its PATH.

`bin/open` (first on `PATH`, so `open`, and `$BROWSER`) is easl's shim of the system command: inside a tile (`EASL_SOCKET` answering, `EASL_TILE_ID` set) with every argument an http(s) URL without a quote, backslash, space or control character, it sends each to `view.open_url` with the tile as `caller` and exits 0 once the app answered `ok`: the page shows in a browser tile beside the terminal, or the tile already showing that address (same scheme, host, port, path, query and fragment) is reused. It needs only `sh` and `/usr/bin/nc`, and waits at most 6 s for the app. Anything else, or any failure, runs `exec /usr/bin/open "$@"` with the arguments the app has not shown, so files, `-a`, flags, other schemes and an app that is not answering behave as without easl; an agent that must reach the default browser calls `/usr/bin/open` by its full path. A user's startup files that set `BROWSER` win over the tile's.

An app launched from inside an easl tile (an agent's `scripts/dev.sh restart`, `open` in a tile) inherits that tile's integration, possibly of another bundle: a non-interactive shell and what it starts keep `ZDOTDIR` pointing at the tile's `extensions/shell/zsh`, and every shell keeps its `PATH`, `PYTHONPATH` and `PROMPT_COMMAND` entries. Taken as the user's own, that `ZDOTDIR` made each new tile source easl's zsh files instead of the user's (`.zlogin:3: command not found: _canvas_finish`, no `~/.zshrc`, no nvm). So the tile's variables (`LoginSession.tileShellIntegration`) leave out every easl integration the app inherited: `<resources>` is easl's when an inherited `ZDOTDIR` or `EASL_ZSH_ZDOTDIR` is `<resources>/extensions/shell/zsh` or `PROMPT_COMMAND` sources `<resources>/extensions/shell/bash/easl.bash`; its `bin/`, `clients/python` and `easl.bash` entries are dropped, and the user's `ZDOTDIR` is the inherited one that isn't easl's (`ZDOTDIR`, else the `EASL_ZSH_ZDOTDIR` that tile kept aside), else none (`HOME`).

Integrations report only when `EASL_ENV=1` and the variables they need are present, so they are no-ops outside the app.

Shell integration keeps easl's `bin/` first on PATH after the user's startup files, which may prepend directories (e.g. `~/.local/bin`, Claude Code's install location) that would shadow the wrappers. zsh: each startup file in `ZDOTDIR` sources the user's file of the same name with the user's `ZDOTDIR` in place (their files may set their own), and the last one zsh reads re-prepends `bin/`; interactive shells then restore the user's `ZDOTDIR` (unset if they had none), so shells they start are plain zsh. History stays the user's: macOS's `/etc/zshrc` runs while `ZDOTDIR` is easl's and points `HISTFILE` there, so before each user file a `HISTFILE` inside that directory moves to the user's `ZDOTDIR` (or `HOME`), and their own setting wins. A non-interactive login shell (a tile's `zsh -l -c '<command>; exec zsh -l'`, e.g. resuming an agent) keeps the integration for the command and the shell after it. bash: `easl.bash` runs before the first prompt, after the user's startup files, as long as they keep an inherited `PROMPT_COMMAND` when setting their own; `bash -l -c` commands and other shells (fish, nushell) resolve `claude`/`codex` with whatever PATH their startup files leave. Before each prompt, interactive zsh (a `precmd` hook) and bash (`easl.bash`) report the shell's directory as OSC 7 (`file://host/path`, percent-encoded, as macOS Terminal's own shell files do), which the tile keeps as the directory `path:line` references resolve against first.

zmx session names are `canvas-<tileId>`, labelled `canvas.board=<boardId> canvas.tile=<tileId> canvas.home=<support dir path, every byte outside [A-Za-z0-9._-] as _>`. `canvas.home` names the creating instance, so copied boards with the same tile ids cannot take over or end its sessions. `TerminalTile.ownerGuard` checks ownership before attach and kill because `zmx attach --labels` relabels an existing session. The default home also accepts older installed support-directory labels through `legacyHomeLabels` and relabels them on attachment. An unreachable listed session says it isn't answering and is waited for through `SessionReach`, starting at one second and doubling to thirty seconds. Attaching immediately to a timed-out session fails and would leave the tile detached after recovery. After an hour, a key press restarts the wait.

Dev lifecycle commands identify the running instance by its open lock, or by a PID that still owns the home's API socket. A copied PID file alone never authorizes stopping another instance.

The generated session name is 29 bytes. macOS zmx 0.8.1 permits 103 socket-path bytes before the terminating NUL. Development guards therefore reject an `EASL_HOME` longer than 69 UTF-8 bytes for `<home>/zmx/<session>`. The supplied home spelling is preserved for ownership labels; physical resolution is used only for safety checks. Development terminals inherit `ZMX_DIR=<home>/zmx`, so attach, `zmx list`, and `scripts/dev.sh zmx-env` use the same namespace. Installed launches keep their existing TMPDIR-based attach behavior.

Deleting a terminal ends its session on every path, including UI close, `object.delete`, `object.batch`, undo of creation, and redo of deletion. `Board.onTerminalsEnded` reports each removed terminal once the outermost step closes; a failed batch that restores it reports nothing. `TerminalTile.killSession` checks its owner before ending it. Undoing a deletion creates a new session with the recorded command or resumes the recorded agent.

## Hosted terminals

A terminal with `props.host` (an ssh target, `deckbox`) runs its session on that machine (`HostedTerminal`, `TerminalHost`, easld's `internal/session` and `internal/relay`). `props.cwd` is then a directory there (default: the user's home); the tile's process here is only the attach. A terminal's host is fixed when it is created: an update that changes or removes it (or gives a local terminal one) is `invalid_params` (`Board.write`), since the live tile stays attached where its session started and its history, render and kill would otherwise go to another machine.

- **Merged boards.** A hosted session stays attached when its board merges into a repository board. The Mac passes `repo.merged` to both `HostedTerminal.attach` and `session.spawn` as `merged`. Both accept a `canvas.board` label naming the current board or a board in that list, while `canvas.home` and `canvas.tile` must still match. A board the caller did not merge, another home, another tile or a missing board label is still refused. The running session keeps its original labels. `merged` items must match the schema's Id pattern (`^[a-z]+_[0-9A-Za-z]+$`); the Mac drops invalid ids, and easld rejects them with `invalid_params`. A restart omits `merged` because the previous session is confirmed gone, so relaunch works with an older easld. Other starts and spawn rechecks on merged boards need the host's easld updated; an older one rejects the new parameter.
- **Sessions are easld's.** The host runs easld as the system unit `easld@<user>.service` (`easld/packaging/linux/easld@.service`: `User=%i`, `Slice=agents.slice`, `KillMode=process`, home `~/.local/state/easl`, socket `~/.local/state/easl/easl.sock`). The app asks it to start the tile's session (`session.spawn`: `canvas-<tile>`, labelled like a local one, the command as argv in the login shell, `PATH` before easld's own), so the session and everything it runs stay in the unit's cgroup and slice: a process started through an ssh session or `systemd --user` would land in `user-<uid>.slice`, which has no cap. Docker containers escape the slice: a container a hosted agent starts needs `--cpuset-cpus` within the slice's CPUs and `--memory`. zmx's sockets and logs for hosted sessions are in `~/.local/state/easl/zmx` on both sides (`ZMX_DIR`, which easld sets on every zmx it runs, whatever a spawn's `env` says), never zmx's shared default `/tmp/zmx-<uid>`, which another user of the host could make first and plant a log symlink in: easld makes it 0700 and refuses (`unavailable`) a symlink, another user's directory or one others can write to, at startup and before each zmx call. A session whose owner labels don't match the ownership rule above is never taken over (`session.spawn`: `conflict`). `session.kill` with `home` ends only a session labelled for that home. One zmx found dead while listing it (`status=cleaning up`, its socket deleted) doesn't exist, so a spawn starts it again. `session.kill` ends one (deleting the tile, on every delete path); `session.list` answers whether it still runs. The app answers all three `unsupported`.
- **One ssh connection per host** and app instance: a master (`ssh -M -N`, control socket `$TMPDIR/easl-ssh-<host>-<hash>`, `BatchMode`, `ServerAliveInterval=10`) that the attaches, the calls to easld (`nc -N -U` on its socket where the host's nc has `-N`, else `nc -U`; one line each, ended once the reply is in) and `zmx history` (agent.read `lines`, cards, renders) multiplex over. The tile's command (`HostedTerminal.attachLoop`) waits for it, attaches with `ssh -tt … zmx attach canvas-<tile>` (on the host: only once easld has started the session and its owner labels match the ownership rule above, else it says whose the session is and the tile holds there without attaching, as a local tile's `ownerGuard` does; and with `SHELL=/bin/false` so zmx never starts one itself), and attaches again whenever ssh fails (255), so a network loss reattaches the same session; zmx's own exit ends it as a local tile's does. While the host is unreachable the tile shows a banner, "<host> is offline. <why>", with Reconnect; the app retries after 1 s, doubling to 30 s. A tile closed while the host is offline leaves its session there.
- `HostMaster` owns the persistent control socket and process, keyed by exact ssh target and app support directory. Startup is single-flight and requires only sshd; `TerminalHost` adds the easld probe, reverse relay, and sessions. File commands use a separate bounded pool of four isolated masters, one command per lease; HTTP keeps its separate single-transfer master. Canceling a file read cannot terminate sibling leases or persistent channels. A persistent master exit clears the terminal relay's forwarded port before reconnecting. Quitting ends every tracked master and client process.
- **Remote viewers.** A viewer of this board attaches directly to `props.host` through its own ssh authorization, using `HostedTerminal.attach` and the same fixed hosted zmx paths above. It checks the board host's home label, not the viewer's or terminal host's home. It starts no session, relay or report replay. An unreachable or denied terminal host shows ssh's reason and retries after 2 s, without falling back to the board host. Password and host-key prompts are disabled, connection attempts time out after 10 s, and keepalives detect a dead link. An invalid ssh target prints a refusal without invoking ssh.
- **The way back** (`relay.open`): the master forwards a dynamic loopback port on the host to this instance's `RelayGate` (`$TMPDIR/easl-gate-…sock`), and easld serves it as `~/.local/state/easl/run/<instance>/easl.sock` and `cmux.sock` (the user's only; `<instance>` is the Mac's name and a hash of its support directory), passing each connection on to the port. Every user of the host can reach the port, and anyone can listen on it once the forward is gone, so neither end sends the token: easld sends `<easl|cmux> <nonce>`, the gate answers `<nonce> <proof>`, easld `<proof>` (hex HMAC-SHA256 keyed by the token over `easl-relay <gate|easld> <name> <easld's nonce> <the gate's nonce>`, `relay.Proof`, `RelayGate.proof`), and only then does the gate splice it to the API's or cmux's socket. A connection the gate doesn't take closes and disarms the relay until the app opens it again; dialing and proving the token each have a 5 s deadline, and subsequent clients of a disarmed relay close without dialing. The integration spools its undelivered report. The gate gets a new token on every connection to the host (`RelayGate.rotate`, before easld hears of the port), so a forward or port from before a drop opens nothing. Not ssh's forward of a unix socket: Tailscale SSH creates that socket owned by root, mode 0600. easld saves each instance's port and token atomically in `run/<instance>/relay.json` (mode 0600), and recreates its relayed sockets before serving its own API socket after a restart. Saving is best-effort. A failure names that file on stderr but does not stop serving, changing the target, or re-arming the live relay. Unchanged persisted targets are not rewritten, and startup reads registrations without saving them again. Disarming removes the registration under the relay's lock so a known-dead target does not return at the next restart. If a new token cannot rebind a socket, easld also retires the old registration as it stops the old relay. Removal failures name `relay.json` on stderr. Re-arming saves the registration again. Startup does not dial the saved target: a missing, silent or impostor target cannot delay startup, and the restored relay still requires its proof and closes failed connections within those deadlines. The app opens the relay again every 30 s while connected to re-arm a disarm and fetch spooled reports. The first keepalive after an easld restart answers `opened: true` for that replay even though the sockets already serve, then later keepalives answer `opened: false`. A new token rebinds the sockets at the same paths, so after the app restarts (or reconnects) the integrations' `watchCanvasReturn`, which watches the socket's identity, sees the board come back and reports again, clearing the restored `working` state.
- **The session's variables**: `EASL_ENV`, `EASL_SOCKET` and `CMUX_SOCKET_PATH` (the relayed sockets), `EASL_TILE_ID`, `EASL_BOARD_ID`, `CMUX_SURFACE_ID`, `CMUX_WORKSPACE_ID`, the shell integration of `~/.local/share/easl` (`PATH`, `PYTHONPATH`, `ZDOTDIR`, `PROMPT_COMMAND`, `BROWSER`), `EASL_GHOSTTY_INTEGRATION` (`~/.local/share/easl/ghostty/shell-integration`), `TERM=xterm-256color`, `COLORTERM=truecolor`; no `EASL_BOARD_ROOT` (a directory of this Mac). Reports an integration couldn't deliver spool beside the relayed socket (`run/<instance>/agent-reports/`). On each connect, when the relay re-arms, and when a hosted tile opens on a host already connected, the app fetches them for those tiles, replays them (`Board.replay`) and deletes them there, before it asks easld to start their sessions: an agent the user exited while the app was away released its tile, so a host that rebooted meanwhile doesn't resume it. A hosted tile that resumes its omp session resumes the file omp reported (`AgentResume.initialArgv`), as `agent.restart` does: the file is on the host, where the Mac can't check it is still there, so one omp's `/move` renamed resumes by its stale path and omp exits (a host-side choice would need `session.spawn` to carry the path and the id). A Mac's own tiles and easld's owned ones take the path only while the file is there, else the id.
- **Setup**: `scripts/offload-setup.sh <host>` (idempotent, no root, starts nothing) installs zmx 0.8.1 (checksum-verified), easld built for the host, the `easl` CLI and `~/.local/share/easl` (the bundle's agent files), links `~/.omp/agent/extensions/easl.ts`, and prints the unit for the host's administrator. The host needs Bun 1.4.3 or later and OpenBSD `nc`.
- Not on a hosted terminal: the foreground program and its directory (no process table here), so `agent.prompt`'s foreign-program check and the tile's program name don't apply; `path:line` ⌘-clicks resolve against this Mac's files, and an HTML file named without a line opens as code, never rendered (`Board.referencePage`).

## Owned terminals

An easld started with `--own-terminals` runs the terminals of its own boards itself, so a board on that machine needs no Mac to run its agents (`easld/internal/router/lifecycle.go`, `restore.go`, `easld/internal/session/env.go`, `resume.go`). `easld@.service` sets it; it is off by default, so an easld on a Mac never competes with the app, which runs its terminals itself. A terminal on a board open on that easld is owned unless it has `props.host` (a hosted terminal's session is its Mac's to start and end, above).

- **Create.** Once the step that created an owned terminal closes (`object.create`, `object.upsert`, an `object.batch` that succeeds, a viewer's new terminal), easld starts its session `canvas-<tile>` as its own child (as `session.spawn` does: in the unit's cgroup and slice, `ZMX_DIR` its `<home>/zmx`), before the call is answered: what a Mac's tile runs (`AgentResume.initialArgv`), the agent session it recorded resumed (below), else `props.command`, in the login shell, then the login shell, in `props.cwd` (a directory on easld's machine), else the board's root. A batch that fails puts back what it did and starts nothing. A start that fails (no zmx, a `cwd` that isn't a directory there, a session of that name labelled for another home) is logged in the board's history as a `restart` entry of the system's, naming the terminal and why; the terminal stays.
- **First view.** The session creator registers with zmx and detaches before the create returns, so the first viewer receives the retained screen and input modes. Creation stays non-TTY, with the same terminal size and unattended DA1 replies, and sends no focus events to the program.
- **The session's variables** are a hosted terminal's above, except `EASL_SOCKET` is easld's own socket and `EASL_BOARD_ROOT` is the board's root there. Integrations report, take messages and spool beside that socket. Easld strips every inherited `CMUX_*` variable, then adds `CMUX_SOCKET_PATH`, `CMUX_SURFACE_ID` and `CMUX_WORKSPACE_ID` only after this owned terminal's cmux listener has bound. It adds no password. The deterministic socket is recreated for surviving sessions after daemon restart and retained across `agent.restart`; ending ownership removes it. Existing sessions from before this feature need a normal restart to receive the variables. Labels remain `canvas.board`, `canvas.tile` and `canvas.home`. The shared terminal-env fixture covers the base variables; router lifecycle tests cover bound socket injection.
- **Delete.** Once the step that deleted an owned terminal closes with it still gone (every delete path: `object.delete`, a batch, a viewer's close), easld ends its session and deletes zmx's log of it, as the Mac's close does (the log also when the session had already exited or died), and the reports spooled for it. It ends only a session carrying all three of its labels: one labelled with another home (a Mac's offload, a board copied into another home) or, in easld's home, with another board (a board file copied to another root keeps its tile ids) is left running, with its log; that, and an end that fails, is logged as for a start.
- **Restore.** easld lists each board it opens in `<home>/open-boards.json` (`[{"root", "board"}]`: the board's id, and the directory it was opened from) and reopens them when it starts, each loaded and its agents' spooled reports replayed before it serves. A board is its id: it reopens from the listed directory while that opens it (`store.Identify`, as `board.open` does: a bare repository's worktree, `proj/work` of `proj/.bare`, opens it where the board's own root `proj` opens another), else from the root its board file names (a repository's main checkout), else from a live worktree of its repository, listed only then (listing reads every worktree the repository names, which can wait on an unmounted volume); worktrees are removed after a merge, their paths reused by other repositories, whose boards never stand for this one, and the list then names the directory that opened it. A board nothing opens any more is dropped from the list, and a board file easld can't read stays on it; each is reported on easld's stderr. As a board opens (at start or `board.open`), each owned terminal without a session of its own gets one, as a create does; at start, once easld serves, so what the agent reports as it starts (`agent.report_session`) reaches it. After a reboot the agent session it recorded (`props.agent`'s `kind` and session, `agent.report_session`: omp's `sessionPath`, as `agent.restart` resumes it, while that file is there, else `sessionId`, which omp finds in any of its projects: omp's `/move` renames the file without a new report, and omp 18.8 refuses a path with no file) resumes with the options of its own `command` (`omp --resume=<path>`, `claude --resume <id>`, `codex resume <id>`, `gemini --resume <id>`, `opencode --session <id>`; the command's own session selectors and prompt left out), and an agent released (`agent.release`: its user ended it; a hangup or SIGTERM, as a reboot sends, releases nothing, Agent integrations), or one easl can't resume, runs its `command`. A session that runs (an easld restart) or doesn't answer (its daemon may only be busy) is left alone, so an easld restart starts nothing; another home's or board's of the tile's name is not taken over, logged as a failed start. The resumed command is the Mac's `AgentResume.argv`; `Tests/Fixtures/agent-resume.json` holds cases both `go test` and `swift run CanvasCoreTests` check.
- **Orphans.** A session labelled with easld's home and an open board that has no owned terminal for it (easld was down when it was deleted, zmx refused to end it, the terminal became hosted) ends, with its log and, unless a terminal of that id is on an open board, its spooled reports, once two sweeps a minute apart find it so with the same pid, and only while that process still runs it: checked again as it is ended (`session.spawn` and `session.kill` don't wait for sweeps), so one started again under its name since is left alone with its log and spool. Each one ended is logged in the board's history (`easld ended session canvas-<tile>: …`); one zmx won't end is tried again at every sweep and logged once for that process. Never another home's session, one labelled with a board that isn't open, or one that doesn't answer or lists no pid.
- **Restart.** `agent.restart` of an owned terminal is easld's own, with or without a client attached (a hosted one's is still its Mac's). After the checks a client's restart gets (target, mode, args, then, unless `force`, what a restart would lose), easld holds the terminal (nothing reaches it, as while a client restarts it), and one lifecycle job checks it again (closed, a prompt being typed into it, and, unless forced, what came since), ends its session (one of the tile's name that is another home's or board's is left running: `conflict`), waits until zmx no longer lists it (3 s at most, each listing cut off at that deadline, since every start and end waits behind it; else `unavailable`, nothing relaunched, logged in the board's history), ends the killed agent's session (what was queued for it bounces) and records the relaunch: the tile's `command` becomes the relaunch's without its session selector (what a reboot then resumes), `props.agent` keeps its kind, model, thinking level and, resumed, its session, without the killed process's `draft` and `pid`, and its lifecycle is unknown until the new agent reports; an `agent.release` before the relaunched agent's first report or session is the killed agent's, sent as it exits, and leaves that record (`relaunchedAgents`, as the app's `Board.releaseAgent`). It then starts the relaunch in a new session with the same labels: `resume`, the recorded session with the options of the tile's command and the recorded model and thinking level in place of any it gave; `fresh`, the same without the session; `args` after either; a terminal running no agent easl knows reruns its command (`AgentResume.relaunch`; `Tests/Fixtures/agent-relaunch.json` holds cases both `go test` and `swift run CanvasCoreTests` check). A relaunch that can't start is logged in the board's history as a failed start, and the terminal stays without a session. The result is a client's: the agent's entry and the `command` relaunched.
- **agent.list** says of each owned terminal, on open boards and closed ones, whether its session runs (`live`: zmx lists one carrying its three labels). Without one it has no `pid`; with one, a pid no integration reported is the session's foreground process (`/proc`: the leader of the job in the shell's terminal, else the command its `-c` runs, else the program it exec'd; none at the shell's prompt), as `ForegroundProgram.foregroundPid` reads a Mac's.
- **Merged boards.** A session labelled with a board id in the board's `repo.merged` (a folder's board its repository board took in, `store.Loading`; its sessions kept running) is that board's own for every check above, so long as its home and tile labels match: reconcile, start, delete, restart, `agent.list`'s `live` and the orphan sweep. A board id the board didn't merge, another home or another tile is still another's. Hosted terminals use the same ownership rule for the Mac's attach and `session.spawn`, as described above.
- Each session easld starts for an owned terminal (a create, a reconcile) is one line of its log (stderr, the unit's journal): `easld: terminal <tile> of board <board> resumes its <kind> session <path or id>`, else `… runs its command: <why>` (`no recorded agent`, `its <kind> agent recorded no session`, `a <kind> agent isn't resumed`; `runs a login shell` for a terminal without a command). Session ids and paths only: a command's words may hold a secret.
- Starts, ends, reconciles, sweeps and restarts run one at a time, in the order they were queued, outside the lock every board call takes, as `session.*` calls do; a reconcile leaves a terminal `agent.restart` holds to its restart.
- Live screen modes of `agent.read` and typed `agent.prompt` require an attached Mac client. Without one they answer `unavailable`.


## Agent integrations

Claude Code, Codex, Gemini CLI and opencode get omp's integration (`extensions/omp/easl.ts`) through easl's wrappers `bin/claude`, `bin/codex`, `bin/gemini` and `bin/opencode`, one hook script (Claude Code, Codex, Gemini CLI) and one opencode plugin, `extensions/agent-hooks/hook.ts` (`run <claude|codex> <event>`, the agent's hook JSON on stdin). A wrapper execs the next `claude`/`codex` on PATH that is not an easl wrapper (any directory beside `extensions/agent-hooks`, so two easl installs never recurse), or exits 127 naming the missing binary. It adds the integration only when `EASL_ENV=1`, `EASL_TILE_ID` and `EASL_SOCKET` are set, `EASL_AGENT_HOOKS` is not `0` (the opt-out), and `EASL_AGENT` is unset; it then exports `EASL_AGENT=<kind>`, so an agent started inside that agent (and a second wrapper) runs plain and never reports as the tile's agent. Nothing is written to the user's agent config or repo.

## Client connection

The Python SDK, TS client, and CLI find the socket in this order: an explicit value (`connect(socket=…)`, `new CanvasClient({ socketPath })`), then `EASL_SOCKET`, then the platform's default socket only if that file exists (`defaultSocket` in the TS client, `default_socket` in the Python SDK; the CLI uses the TS client's): on macOS `~/Library/Application Support/Easl/easl.sock`, elsewhere easld's own (its home: `$EASL_HOME`, else `$XDG_STATE_HOME/easl`, else `~/.local/state/easl`, as `easld` resolves it, so a plain shell on a host that runs easld needs no `EASL_SOCKET`); otherwise they fail with `unavailable`, naming `EASL_SOCKET`, the path checked, and the explicit-connect fix. `caller` and `board` come from the client's own tile/board (explicit, else `EASL_TILE_ID`/`EASL_BOARD_ID` at construction). omp's `eval` Python kernel runs with an allowlisted environment that drops `EASL_*`, so the omp extension prints the explicit `connect(...)` line in the system prompt.

Connection failures are always `unavailable`; clients never surface raw socket errors. A socket file that exists but refuses this process (EPERM/EACCES, or ENOENT although the file is there, twice in a row: what Codex's seatbelt sandbox answers; a single one is an app binding its socket just after the connect missed it) fails at once, without waiting for the app, with a message naming the socket and saying a sandbox (e.g. Codex's) may be blocking it. A request that never left (connect failed, write failed, or its newline was unflushed when the connection closed) is sent once more on a fresh connection after waiting up to 15 s for the socket (an app restart). A request that left and lost its reply is not resent: `unavailable: … it may or may not have applied — re-read before retrying`. The exception is a read the schema marks `"resend": true` (`agent.wait`; generated as `RESEND_METHODS`): the client waits up to 15 s for the app to come back and sends it again with `timeoutMs` reduced by the time already spent, so a wait survives an app restart. Image methods (`view.render`, `view.snapshot`) take `out` as an absolute path the app writes (format by extension, png or jpg); clients resolve a relative `out` against their cwd. Without `out` the app writes a new file under `$TMPDIR/easl-renders/` (`ApiRouter.scratchImages`, out of the user's repo); the result's `path` names the file either way, and images never travel inline.

The app writes replies and events through a per-connection queue, in order, and never blocks on a slow reader. An `events.subscribe` client that stops reading can't freeze the board; one that falls more than 32 MB behind is disconnected.

## Activity log

`board.history` reads `Board.activity` (`Sources/CanvasCore/ActivityLog.swift`): in memory, the newest 2000 entries per board, restarted with a `restart` entry when the app opens the board. Board mutations log themselves with their actor (`caller` → `agent:<tile>`, none → `user`, the app's own write-backs → `system`; undo/redo → `user`, prefixed `undo:`/`redo:`). Cascades of a change (a group re-fit to its members, an arrow end freed because its bound object was deleted) are credited to that change's actor and carry a `cause`; within one revision each object gets one cascade entry, amended to its net change (dropped when the changes cancel out), so a batch that moves or deletes 40 members of a lane logs the lane once. Bookkeeping (a terminal's lifecycle, session, title; a browser's `pageTitle`) is never logged. Follow re-aims log one `follow` entry, not the create/update beneath. The board reports viewport and selection changes continuously; the log records them once they have been still for 0.8 s and differ from the last logged state.

## Compositions

A composition is a module in a compositions directory. Functions whose first parameter is named `canvas` receive the connected client (all API namespaces plus `compositions`); other exports pass through unchanged. Python: `canvas.compositions.<name>.<fn>(…)`, `available()`, `reload()`. TypeScript: `client.compositions.<name>.<fn>(…)` (same surface; a file added to an already-loaded directory needs a new process because Bun caches directory listings).

## Object model rules

- Ids are prefixed: `brd_` board, `obj_` object, `men_` mention.
- `frame` is in board coordinates (points at 100% zoom) and is the whole box the object draws: a tile's includes its `RenderMath.tileTitleHeight` (26 pt) title bar at the top, and its content (the body, what `TileRenderRequest.size` and `contentSize` describe) is the frame below it (`RenderMath.body`). Measure, fit, groups, placement, `layout.*`, arrow attachment, and `view.render` pixel rects all use this one box. `z` orders siblings.
- Stored boards carry `format` (`Board.format`, 3). Format 1 stored tile bodies without the title bar and loads with tile frames 26 pt taller. Formats below 3 convert the previous visible tiers into consecutive z values ordered by tier, old z, and id: groups, tiles, then shapes and arrows. This preserves their visible stacking without recording edits. Loading and repository-board adoption use the same migration. Saving writes format 3, whose explicit z values survive restacking and reopening unchanged.
- Both hosts refuse an existing board file that cannot decode completely, including an unknown object type, or whose `format` exceeds their supported format. `board.open` returns `unavailable` with the file path and reason. A missing file still opens a new empty board.
- The Mac app shows an open failure without creating a writable board. It preserves the original file and attempts one byte-identical sibling copy at `<file>.unreadable-<timestamp>` per distinct unreadable contents. A failed copy still refuses the board and reports the copy error. Restore keeps failed local roots for the next launch. Repository merging leaves unreadable sources and targets untouched, and retains readable sources when their target is unreadable. Closed-board inspection skips the entire unreadable snapshot. Legacy app-name migration refuses to move a directory containing an unreadable board.
- Folder-board adoption uses headers only to identify candidates. An associated candidate must decode completely before its repository opens; unrelated corrupt files do not block a healthy repository.
- A failed legacy app-name migration shows its error and exits before any board opens. It does not expose an empty replacement store while the old boards remain blocked.
- Tiles, shapes, text, ink, and arrows share ascending `(z, id)` paint and point-picking order. Group regions stay below them. Drawing tools, editors, and selection handles stay above them. Full-content renders extend target frames without changing their stacking order.
- Update remote hosts and viewers together for shared stacking and legacy-board migration. Remote mirrors use the host's literal z values. An older live host does not migrate legacy tiers. Older easld versions reject format-3 files; older Mac apps do not preserve the new stacking semantics when rewriting them.
- `rev` increments on every change; `object.update` with a stale `rev` fails with `conflict`. The app's bookkeeping writes (`Board.writeBookkeeping`: a browser's `pageTitle`, the page's own title; `Board.reanchor`: a code tile's `range` and `anchor` re-found by content) leave `rev`, `updatedBy`, and `updatedAt` alone, but still take a board revision (`board.get since`), announce `object.updated`, and are saved.
- `createdBy`/`updatedBy` record the actor. An agent is identified by its terminal tile, on whichever board the object is.
- Objects may carry top-level `expires`, an absolute RFC3339 deletion deadline. `object.create`, `object.update`, and `object.upsert`, including batch operations, accept `expires` as a timestamp with timezone or `null` to clear it. Omission preserves an existing deadline. Alternatively, `expiresIn` takes a finite nonnegative duration matching `^[0-9]+(?:\.[0-9]+)?[smhd]$`. Fractions and zero are valid. The host resolves the duration once per request and stores only normalized absolute `expires`. Both fields together, invalid values, and overflow are `invalid_params` without mutation.
- The host deletes due objects through normal deletion as actor `system` named `easl`, with ordinary `object.deleted` events and deletion cascades. Expiry shares the existing question scheduler (one reusable wall-clock timer on the Mac), stops when a board closes, and resumes from persisted deadlines when the board opens. Overdue objects expire synchronously on open. Remote viewers do not expire objects locally. Question `props.expiresAt` and `easl ask --expires` remain separate.
- `board.stale {board?, olderThan?}` lists cleanup candidates without deletion or changes to timestamps, revisions, or events. `olderThan` uses the duration grammar above and defaults to `7d`. Its `{objects: StaleObject[]}` result is sorted by id. Each object has `id`, `type`, `title`, `createdBy`, `updatedAt`, `reasons`, and optional `key` from `props.key`. Reasons include every applicable value in order `creator-gone`, `expired`, `untouched`, `exited`. They mean an agent creator no longer has a terminal on this board, `expires <= now`, `updatedAt < now - olderThan`, and a terminal process confirmed exited by authoritative session state. Agent idle or release alone does not mean exited. Titles use the existing caption or title, otherwise the first line of markdown, question, text, label, path, URL, or name, otherwise an empty string.
- `exited` requires a session previously confirmed running by the host and a successful later lookup that no longer lists it. Never-started sessions, unavailable lookups, listed but unreachable sessions, and completion of a zmx `run` task do not imply process exit. An unreachable listing also cannot establish that a never-started tile ran.
- CLI object methods map `--expires 2h` to `expiresIn`, preserve RFC3339 timestamps as `expires`, and map `--expires null` to JSON null. Only `board.stale` maps `--older-than` to `olderThan`. TypeScript callers clear with `expires: null`. Python callers clear with `expires=None` and set relative deadlines with `expires_in="2h"`; omitted nullable arguments use a generated sentinel. Other optional Python arguments retain their existing `None`-means-omitted behavior. Generated Go optional nullable scalar pointers cannot distinguish omission from null when marshaled with `omitempty`; raw wire params are needed to send explicit null.
- Deleting an object removes every staged mention that targets it, and its attention marker.
- Attention markers (`Board.attention`, one per object) are stored with the board until the user sees the object or someone clears them, and restored on open (markers on objects no longer there are dropped; `board.export` leaves them out). A marker belongs to its raiser's turn: when a terminal's lifecycle goes to `working` from `idle`, `done`, or no state (the user's next prompt reached it; blocked → working, an answered approval, and repeated `working` reports continue the turn), its markers are marked `earlierTurn`, and its next `view.attention` clears those (`cleared` in the result); markers from the current turn stay together. A raise without a terminal `caller` is never cleared that way. A terminal's own notification or bell (OSC 9, OSC 777 `notify`, BEL; `Board.raiseTerminalNotice`) raises a marker on that terminal with no `raisedBy`, unless the terminal has keyboard focus in the active window; the same message again, or a bell over any existing marker, changes nothing.
- Props a type doesn't define (`ObjectType.knownProps`, mirroring the schema's `*Props`) are kept, and `object.create`/`object.update` name each in `warnings`.
- `props.key` (any type, `ObjectKey`; `Board+Keys.swift`) names an object for scripts, unique per board. `Board.keyHolders` maps each key to its holders and changes only where `objects` does (`commit`, `delete`, `init(snapshot:)`), so undo, redo, a failed batch's rollback, and load leave it exact; it holds sets so a board file edited to give two objects one key still loads, and looking that key up is `conflict` naming both. `Board.checkKey` rejects a key another object holds (`conflict`, naming the holder) on `object.create` and in `Board.write` (every update); an empty or non-string key is `invalid_params`, `null` removes it. UI-made objects never carry one. An `object.create` of a changes tile that gives a key is never `reused` for another tile.
- `object.find` looks a key up on one board (`board` defaults as for create): `key` answers what `object.get` would for the holder, `keyPrefix` lists holders by key order. `object.upsert` becomes the `object.create` (key added to its props) or `object.update` (props merged, `frame`/`size` as update; the holder's type must match, else `conflict`) it is when it runs (`ApiRouter.upserted`), and says which in `created`. In `object.batch` that resolution happens in the planning pass, against the board plus what earlier ops do to keys (`ApiRouter.KeyPlan`: keys created, keys given by updates, holders deleted or re-keyed), so `$n` of an upsert names the object whether created or updated and an upsert of a key an earlier op creates updates it; when the op applies, its key's holder must be the planned one, else the batch fails with `conflict` and rolls back.
- A board belongs to one root directory; code paths are stored relative to it (absolute outside it).
- `board.list {}` returns `{boards:[...]}`. Stored local rows retain their existing `BoardInfo` shape and order, including closed and archived boards. The Mac app appends one `RemoteBoardInfo` row per open remote tab: `{remote:true, host, sshTarget, board, root, title, window, open:true}`. These fields use `board.open_remote`'s vocabulary: `board` and `root` belong to the host, and `window` is the viewer tab's window number. A remote root is not a local path. Closing the tab removes its row rather than retaining `open:false`. Hidden background attachments are not open tabs. Local rows have no `remote` field. Remote rows omit local-only `archived`, `objects`, `updatedAt`, `repo`, and `worktrees`; consumers check `remote === true` before using local metadata. easld's list remains unchanged and contains only its own stored boards.
- The schema keeps `BoardInfo` intact and describes list items as `BoardInfo | RemoteBoardInfo`. TypeScript callers narrow remote rows before reading local metadata. Python and TypeScript SDKs return decoded JSON without result-schema validation, so older SDKs accept the new rows. This does not supply local metadata to older application code that assumes every row is local. CLI method help reads the schema directly (`easl board.list --help` and `easl methods RemoteBoardInfo`); no separate help file is generated.
- Older Mac app viewers do not filter `remote:true` rows in the Open Remote picker. They can offer another app's remote tabs as if that app owned them; opening one fails. This limitation does not affect SDK JSON decoding or easld's host-owned lists.
- An explicit `board` param on the Mac app gives open and stored local IDs precedence, including migrated IDs. A closed local target remains `not_found`, so a surviving local agent cannot redirect writes to a same-ID remote board. Otherwise it resolves an open remote tab by its host board ID. Several matching remote tabs return `ambiguous` with their host-and-socket identities. Mirrors never enter the local `BoardRegistry`. `view.get` reads this app's tab state. `view.render` renders that tab with `inline:true` and no `out`; `view.snapshot` is `unsupported` for remote tabs to avoid writing host content locally.
- For an explicit remote target, `board.get`, `board.history`, `board.undo`, `board.redo`, `board.stale`, `board.export`, `object.find`, `object.create`, `object.upsert`, `object.measure`, `object.batch`, `layout.check`, and `text.measure` forward to the board host. Host capabilities and errors still apply, including structured error data. Paths and returned metadata remain the host's. `tray.list`, `tray.stage`, `tray.drain`, `tray.commit`, and mention-ID-only `tray.unstage` operate on this viewer's private tray, never the host user's tray. `board.close` detaches this viewer, and `board.open_remote` retains its existing host-and-board lifecycle. `events.subscribe` and `viewer.activity` reject app-local remote targets as `unsupported`; clients use the board host's event connection instead. `view.open_url` is unsupported for app-local remote tabs because forwarding would move the host user's viewport. Use the tab's native link action instead. Methods that accept only object IDs remain local-registry lookups on the app socket. Use the host socket for those methods, or `object.batch` with an explicit remote `board` for supported mutations.
- `board.close {board?, endSessions?}` saves and closes an open board without deleting its stored board file. `board.list` still catalogs it with `open:false`. `board` defaults as for `board.export`, from the client's `EASL_BOARD_ID`, otherwise the server's default board including the frontmost fallback. Unknown or already closed targets are `not_found`. A stored local ID, including a migrated ID, takes precedence over a same-ID remote tab even after the local board closes. Such a call neither closes the remote tab nor cancels its pending open; close that viewer through its native tab action instead.
- Without `endSessions`, or with `false` on a local board, terminal objects and sessions stay. `board.open {root}` restores the same board and terminal ids with their live sessions. The root leaves the Mac's `open-boards.json` or easld's `<home>/open-boards.json`, so a server restart does not reopen it. easld's orphan sweeps ignore sessions of closed boards.
- With `endSessions:true`, sessions end before their terminal objects are removed, as with the sheet's End Sessions. The Mac detaches their terminal frontends before ending sessions, including in a window still being prepared, so a pending frontend cannot recreate a session after it ends. easld without `--own-terminals` answers `unsupported`; an owning easld retains hosted terminals in `kept` because it does not own their sessions. `endSessions` must be a boolean, never `null`.
- A caller running inside a session ended by `endSessions:true` can exit before receiving the response. The call does not exempt its caller's terminal.
- The result is `{board, root, kept:[{id,name}], ended:[{id,name}]}`. Both arrays are present and sorted by id. Each name is nonempty `props.name`, otherwise nonempty `props.title`, otherwise `"Terminal"`. There is no `host` field.
- On the Mac, closing the last visible board is `conflict` when it would quit the app, including while the app is hidden or the window is minimized. Hidden background attachments, pending background attachment loads, or pending update tab restoration allow that close because they keep easl running. Update restoration includes Retry and Discard. If restoration finishes without a window, easl stays running until a window reopens or the user quits. A remote tab closes only this viewer, without changing the host's board or sessions. On easld it also detaches that viewer's client. Closing cancels matching in-flight remote opens, including host discovery, so they cannot reopen the tab afterward. Any explicit `endSessions` on a remote tab, even `false`, is `invalid_params`. A local board wins an id collision with a remote tab. The same remote id on multiple hosts is `ambiguous`.
- Closing while an affected terminal is in `agent.restart` is `conflict`. A save or session-ending failure is `unavailable` and leaves the board open. Any failure after confirmed session endings names their terminal ids, including later persistence failures. Those session effects are not rolled back. Board availability transitions emit `board.closed` and `board.opened` with empty `{}` data and leave subscriptions connected. Already-open host tabs and daemon boards emit neither event when opened again.
- Requests that resolve onto a board while it closes answer `conflict`, including reads, integration reports and `board.open` of a path that opens that board. Waits registered before the close keep their timers. Other boards stay available. A prompt still preparing when its board closes answers `not_found`. Reopening the board does not resume that pending prompt.
- Board identity (`BoardStore.boardID`, `RepoBoards.swift`, docs/design/repo-boards.md): a directory in a git repository opens the repository's board, id `brd_` + SHA-256 of its common git directory as `GitWorktree` finds it (filesystem only, no git process), rooted at the main checkout (`GitWorktree.canonicalRoot`: the opened checkout when it is the main one, else the common dir's parent), whichever worktree, branch or subdirectory opened it; any other directory its own, id from its path. `BoardRegistry.open` tags the board with the worktree it was opened from (`Board.opened(from:)`: records a linked worktree in `repo.worktrees` and makes it the in-memory working worktree, where New Terminal starts; the main checkout clears it) and the window names it and reveals its branch's region (`CanvasWindowController.showWorktree`). A terminal created with a `cwd` in the board's repository gets `props.worktree` and `props.branch` (`Board.stampingWorktree`). `board.list` reports `repo` and `worktrees` (`RepoRecord.worktreeList`: live worktrees, main first, then recorded ones; `live` means that worktree has that branch checked out), `board.open` the `worktree` it was opened from, and `board.get --branch` one branch's part (`Board.objects(ofBranch:)`). A `board` param naming a legacy board a repository board merged (`repo.merged`: shells started before the migration keep it in `EASL_BOARD_ID`) means that repository board (`BoardRegistry.board(id:)`).
- Repository-board migration (`RepoBoardMigration`, run by `BoardStore.migrateToRepoBoards` at launch before any board opens, and for one repository when its board first loads in a session, while legacy boards stay unresolved or path-keyed boards of directories now in it are stored; easld's `Registry.load` does the same for path-keyed boards): legacy boards (keyed `<common dir>\n<branch>` or, detached, `<common dir>\n<top level>`, or by path in a repository with no commit or in a directory that has become part of a repository since) are identified by recomputing those ids, merged into their repository's board, re-rooted, and moved to `pre-repo-migration/`; boards outside git are never touched. Placement, re-rooting and the report are in docs/design/repo-boards.md.
- `props.zoom` (every tile but an image or video; `ObjectZoom`, 0.25–8, absent = 1) is how big a tile's content draws inside its frame, in place; the frame is the tile's size, which only resizing changes. The title bar stays at 1× (its height is the tile's geometry, `RenderMath.tileTitleHeight`; a client's chrome text size scales its text, not the bar, and `view.render` always draws it at 100%); `TileFrameView` holds the content in a body view (`ContentZoomView`) whose bounds are the body ÷ zoom, so the content lays out, hit-tests, and takes mentions in its own points, at `CanvasObject.naturalFrame` (`ObjectZoom.natural`: the same title bar over the body ÷ zoom, the tile as it would be at 100%; `RenderMath.body(of:)` is that body), and draws zoom×; renders draw the content at its zoom under a 1× title bar. A browser tile keeps its address bar at 1× too (`BrowserTile.chromeExtent`: `chromeHeight ÷ zoom` of its points, its bounds undoing the zoom), so only the page zooms, as a browser's page zoom does. Image and video tiles don't take it (`ObjectZoom.applies`: the picture is already fitted to the frame): `zoom` there is an unknown prop, kept, warned about, unread. A text shape's font is `DrawingStyle.textPointSize` × `props.textSize` (`ShapeSpec.textSize`, 0.25–8, absent = 1), and its box grows with it. What agents get is in board points: `object.measure` and `size: "fit"` (laid out at `width` ÷ zoom; the frame is the title bar plus the body × zoom, `ObjectZoom.zoomed`), `layout.check` overflow, `view.render` `contentSize`/`overflow` (the layout extent × zoom), and line anchors (`CodeMetrics.lineY`). A mention's "over <tile> at (x, y) w×h" region is in the host tile's content points (below its title bar, ÷ its zoom; `ObjectZoom.canvasRect` maps them back). The user zooms with the title bar's `−  150%  +` (`TileZoomControl`, left of the ✕: the % whenever it isn't 100%, − and + while the tile is hovered or selected; a click on the % resets to 100%) or Object ▸ Content Zoom (Zoom Content In ⌃⌘=, Zoom Content Out ⌃⌘- through `ObjectZoom.levels`, the presets, Reset Content Zoom ⌃⌘0; `CanvasView.setZoom`/`stepZoom` on `zoomTargets`: the selected tiles and text shapes, else the tile holding the keyboard), one undo step: a tile's frame stays as it is, a text shape's `textSize` changes with its box, grown or shrunk from its top-left. An `object.update` that sets `zoom` never changes the frame. `props.scale` is gone: `object.create`, `object.update`, `object.upsert`, `object.batch` ops, and `object.measure` with it fail with `invalid_params` naming `zoom` and `textSize` (`ObjectZoom.retiredProblem`, no alias). A board saved with it migrates once on load (`ObjectZoom.migrated`, idempotent): a tile's `scale` becomes its `zoom` with the frame unchanged (it keeps its size on screen and its content its size; only the title bar is 1× again), an image's is dropped, a text shape's becomes `textSize`; a `zoom` or `textSize` already there wins, and 1 is dropped. Liveness and zoomed-out handles use magnification × zoom (`RenderMath.isZoomedOut`).
- A group's `frame` is derived: its members' bounds (arrows excluded) plus `padding` and a `GroupSpec.titleHeight` title band, recomputed by `Board` in the same undo step as any change to a member's frame (nested groups outward), and on load. Frames written to a group are ignored. Stored groups labelled by the old `name` prop load with it as `title`.
- Placement (`Board.place`): an object created without a frame (an agent's, the follow tile, a pin, a link opened from a note or HTML tile) goes to the free slot nearest the caller's tile, touching it 24 pt away when there's room (right, then below, left, above), else nearest the viewport center; beside a tile, slots wholly (then partly) in view win over nearer ones out of it only within `Board.nearbyDistance` (600 pt, the gap between the frames) of the tile; further out the nearest free slot wins, in view or not, so on a busy board an agent's object stays by its terminal rather than landing in view beside someone else's (the agent raises a marker when the user should look); `place(_ ideal:)` finds the free slot nearest a given frame. An agent's own frameless creates (`object.create` without a frame or with `size: "fit"`, `browser.open_split`; `place(stacking: true)`) stack instead of going round the terminal: when the caller created a tile within `Board.answerStackWindow` (10 minutes) that is still on the board and isn't a follow tile, the free slot beside the newest such tile, by the same rules with sides ordered below, right, left, above, is taken if it touches that tile 24 pt below or right of it and is no less in view (wholly, partly, not at all, against the viewport inset 24 pt) than the slot beside the caller; otherwise the caller rule applies. Follow tiles, pins, links, and the user's objects never stack. Free means 24 pt clear of every tile and group, other agents' included; drawings and arrows never block. While the caller's tile (or the ideal spot) is on screen, a slot wholly inside the viewport (`Board.viewport`: the part of the window clear of the toolbar and tray, inset 24 pt) wins over a nearer one outside it, and when none fits, a slot partly in it wins over one wholly outside, one whose top edge (a tile's title bar) is in view first: a terminal an API call made without a frame used to land above the one filling the view, its title bar under the toolbar. A new follow tile (`place(width:height:near:shrinkingTo:)` with `Board.followMinimumSize`, 400×300, about 45 columns of code) may also be cut down to the part of such a slot that is in view: when no full-size slot fits wholly in view, a smaller one that does beats one partly outside (beside a default 1000-pt terminal in a 1976-pt view: 440×446 on its right, not 640×446 partly off-screen); a narrower sliver (198 pt in a 1492-pt view) keeps the full-size slot, since code wrapped at 18 columns is unreadable. The view never moves for it. Origins are whole points. The app places the user's own new objects by the same rule (`CanvasView.openForUser`: File › Open File, New Note, New Browser Tile, New HTML Tile, ⌘T, Go to's file rows at the viewport center; Edit Here's terminal beside its code tile), then pans the least that shows the object (`Layout.reveal`), selects it, and gives it the keyboard. API creates without a caller use the viewport center and never move the viewport.

## Layout

`object.measure`, `size: "fit"`, `layout.place`/`stack`/`translate`/`grid`, `object.batch`, and `layout.check` live in CanvasCore (`ObjectMeasure`, `Layout`, `Board.atomically`). Measured sizes are whole object frames, tile title bar included: code follows `CodeMetrics` (`ObjectMeasure.code`: as wide as the range's longest line up to the max width, `width` or `CodeMetrics.defaultFitWidth` = 1546 pt, 200 columns (`CodeMetrics.autoColumns`) beside a 4-digit gutter; longer lines wrap and count in the height; `layout.check` measures code at its frame's width; a code tile created without a frame, by the API or the user, other than a follow tile, takes `Board.newCodeSize`: 446 tall and as wide as the working-tree file's longest line needs at its zoom, by `SideText`'s lines and `WrapText`'s columns, from 640 up to `defaultFitWidth` of content, 640 for a tile shown from git or a file it can't read within 1 MiB; easld's `Board.NewCodeSize` matches it, decoding malformed UTF-8 as Swift does), images (`LocalImage`: the picture at one point per pixel, at most `width` wide, default 960, plus the caption strip; an image created without a frame height is fitted like a note), notes (an `object.create` of a note without a frame height is fitted like `size: "fit"`, at `frame.w` or `ObjectMeasure.defaultNoteWidth`; `title` only names the tile) lay out `NoteRenderer` output with TextKit 2 at the note tile's own insets, its tables' columns fitted and their cells wrapped to that width (`ObjectMeasure.note`, `noteInset`; `NoteRenderer`, `NoteLayout`, and `DrawingStyle` are in CanvasCore for this), text shapes use `DrawingStyle`'s font, and HTML pages are laid out by the app's WebKit (`ObjectMeasure.html`, set by the app to `HtmlTile.measure`: the page loads offscreen exactly as `view.render` loads it, in a throwaway tile 1 pt tall at the width, and its document scroll size once the kit reports `view.rendered`, at most 3 pages at once, 10 s each; `size: "fit"` gives `frame.w` or 640 and the title bar plus the document height, capped at `ObjectMeasure.maxHtmlFitHeight` = 4000; `layout.check` measures each HTML tile at its frame width, uncapped; CanvasCore alone reports HTML `unsupported`). Measuring reads files, so `object.measure`, a `size: "fit"` create/update, `object.batch`, and `layout.check` are resolved asynchronously; a batch measures every op first, then applies all of them synchronously inside `Board.atomically`, so no other request interleaves with its writes. `Board.atomically { }` is one undo step and one board revision; when its body throws, the changes it made are reverted (announced as normal changes, not recorded) and the error is rethrown. Layout ops move objects through one private `Board.shift` (groups by their leaf members, each object once) inside `Board.deferringRefits { }`, which holds group re-fits until the op's end and then re-fits each affected group once; group frames are stale only inside that scope. `size: "fit"` on an `object.update` without `frame.x`/`y` takes `Board.refitFrame`: grown from its top-left corner when that overlaps nothing it didn't already, else from the first other corner that doesn't (`Layout.refit`: top-right, bottom-left, bottom-right), else the free slot nearest the top-left-grown frame among those whose origin is within the frame's longer side of it (`place(_:)`'s rule, in view first, the object and its groups not blocking; `freeSlot(within:)`), else top-left anyway. Fitted results (and fitted batch ops, after the whole batch) carry `overlaps`, `Board.overlaps(of:)` by `layout.check`'s overlap rule, when not empty. Batch side effects stay per revision, not per op, in the app too: `avoid` arrows, whose routes depend on every tile, re-route once after a burst of changes (`ShapeLayer.rerouteAvoiding`: next main-queue turn or before the layer draws or renders), keeping the drawn route until then.

`layout.check` judges what is drawn: tile frames are whole tiles; arrows route with `BoardGeometry.routing(rows:)` (a value snapshot of the board taken when the call arrives, computed off the main actor) (line-bound ends by the model scroll rule, over each bound code tile's rows as it wraps them at its frame width: `CodeRows(file:width:)`), routed on from the drawing layer's last routing (`Board.settledRouting`): `ConnectorRouter.route(previous:)` keeps every `avoid` route nothing has touched since, so on a settled board the check computes exactly the routes, tracks and labels on screen, and after a change it computes what the layer will draw when it settles. Labels are placed as the drawing layer places them (`DrawingStyle.arrowLabel` for the chip size, `ConnectorRouter.placeLabels` for every arrow on the board together, against `BoardGeometry.blocksRoutes` objects, group title bands, other arrows' lines and each other) and reported as `labelOverlaps` when they lie on a blocking object (their own ends included), a group's title (the group id), another label (that arrow's id), or another arrow's line (`lines`), each with the caption and the chip's frame (an arrow's own frame leaves its label out). `arrowOverlaps` are pairs of arrows collinear within `ConnectorRouter.overlapTolerance` (3 pt) for at least 2 pt (`length` in points, `at` the middle of the first shared run); `arrowIntersections` are pairs whose lines cross (`count`, `at` the first crossing); both come from `ConnectorRouter.overlaps`/`intersections` over the same routes. The drawing layer routes the whole board again (incrementally) whenever a tile, blocking shape, or group comes, goes, or changes frame, blocking or flow, and whenever an arrow changes (`ShapeLayer.scheduleRouting`), so a label never stays under a tile that arrived after it and the check and the picture agree; while a tile is dragged or a code tile scrolls, only the arrows bound to it re-route (each alone), and the board routes once the change pauses (`ShapeLayer.routingPause`, 0.25 s) or ends. With `ids` or `rect`, a crossing or label overlap counts when the arrow or anything it crosses or lies on is in scope (a new tile checked by its id reports the labels it covers); line-bound arrows whose ends lie within 300 pt of a scoped object have their tiles' rows read for it. Unfilled rects and ellipses are annotations (a box drawn around or across things): like ink and arrows they never take part in `overlaps`. A code tile's range compares its rows (`ObjectMeasure.codeRows`, wrapped at the frame's natural width in whole points, so a zoomed fit tile's 611.99… pt is still its 612) with the frame and a taller range is `scrolls`, never `overflow`: code wraps at its width and scrolls to its range, so only its height can be short, and a fixed-height viewer usually means to scroll; a caption wider than the frame (`ObjectMeasure.captionWidth`, the header's own `CodeCaption.string` and `CodeMetrics.captionInset`) is `truncated`, not overflow; so is a note whose table doesn't fit its frame's width even with its cells wrapped and words broken (`NoteRenderer.tableShortfall`, via `ObjectMeasure.note`: `what: "table"`, `x` the points of width it lacks); follow tiles (`followOf`) are fixed-size viewers and are skipped for both.

### Archived geometry audit

`CanvasObject.isHidden` on the Mac and `model.Object.Hidden()` in easld share the canvas visibility rule: a question with boolean `props.archived: true` is hidden. No other object type currently defines an archived or hidden state. Unknown props named `archived` or `hidden` on other types do not hide them.

Hidden objects retain their stored frame, status, answer, and bindings, but occupy no layout space. The geometry audit covers both hosts:

| Consumer | Previous behavior | Current behavior |
| --- | --- | --- |
| `layout.check` | Archived questions counted as overlaps, arrow crossings, and label obstacles. | `countsForOverlaps` and `blocksRoutes`, and their Go equivalents, exclude hidden objects. Board, ID, and rectangle scopes follow the same rule. Undrawn arrows do not produce label-color hints. |
| Frameless `object.create` placement | Free-slot searches avoided archived frames. Recent archived answers could anchor later answers. | Free slots, caller anchors, and answer stacking ignore hidden questions. Shapes and arrows retain their existing placement rules. |
| `size: "fit"` and content-growth avoidance | Archived frames could force a different growth corner or nearby slot. | The shared overlap predicate excludes hidden objects and collapsed groups from avoidance. Explicitly addressed objects can still be resized or moved. |
| `object.get as: "graph"` | Stored hidden frames produced `encloses`, `enclosedBy`, and `overlaps` edges. | Hidden objects have no spatial edges as source or target. Stored semantic `arrowsIn` and `arrowsOut` relationships remain readable. |
| Drawing mention context | A shape could describe archived questions as enclosed, underneath it, or connected by an inner arrow. | Enclosure, inner-arrow, and drawn-on context skip hidden questions on both hosts. Direct mentions of retained questions remain readable. |
| Group bounds and auto-fit | Hidden members enlarged groups. Archiving without a frame change left parent bounds unchanged. | Bounds use visible geometric members. Archive and unarchive refit parents, including nested groups. A group with extant hidden members but no visible geometric members collapses to zero size at its previous origin. Unarchive restores fitted bounds. Genuinely empty, missing-only, and arrow-only groups retain their existing no-fit behavior. |
| `ConnectorRouter` obstacles and regions | Archived questions remained obstacles; arrows could attach to invisible tiles. | Hidden questions are not obstacles. Collapsed groups contribute no region. Arrows attached to hidden questions have no drawn route or label until unarchive; their bindings remain stored. Obstacle removal invalidates settled routes through the existing router change tracking. Deleting a hidden endpoint still detaches its bindings. |
| Zoom to Fit and Go to | Question tiles were already absent from selection and fit, but fallback document bounds could expose hidden objects and their bound arrows. | Shared visibility-aware document bounds exclude hidden questions, collapsed groups, and suppressed arrows. Go to rows and Zoom to Fit use those bounds. |
| `view.render` board-wide bounds | Target unions could include the stored frame of an archived question. | Rendering all board IDs excludes hidden outlines and suppressed arrows from the union. Explicit rectangle targets keep the requested rectangle. easld delegates drawing and bounds to the Mac client. |
| `board.stale` | Listed retained objects by ownership, expiry, last update, and terminal lifecycle. | Unchanged. This cleanup inventory is not a geometry query and can include archived questions. |
| `object.find`, `object.get`, and `easl ask get/list` | Returned archived records with their status and answer. | Unchanged. Key, prefix, type, and status searches retain archived questions. `easl ask list --open` still filters by open status. |

Explicit layout operations retain group membership and move named archived members with their groups, so unarchive preserves relative positions. The `archived-layout` conformance scenario checks invisible geometry and retained reads against both hosts.

## Swift tile protocol

Every tile's content view conforms to `TileContent` (`Sources/CanvasApp/TileContent.swift`); `TileFrameView` supplies the shared chrome (title bar, content zoom control and the body at its zoom, drag, corner resize and ⌥-drag proportional resize, lifecycle badge, zoomed-out card) and `TileFactory` maps an object type to its content view.

```swift
@MainActor
protocol TileContent: NSView {
    func setLive(_ live: Bool)                                  // false: detach heavy resources, show the card
    var liveZoom: CGFloat { get }                                // below this zoom the tile is its card (default 0.3; terminals 0.15)
    func render(_ request: TileRenderRequest) async -> TileRender   // offscreen image for view.render
    func cardSnapshot() async -> NSImage?                       // default: render at card scale
    func whenLiveReady(_ ready: @escaping @MainActor () -> Void)  // just made live: call once the live view is drawn (default: at once)
    func showSnapshot(_ show: Bool)                              // view.snapshot: cover Metal/WebKit content
    func mentionTarget(at point: NSPoint) -> MentionTarget?      // what a Hyper-click here mentions (element level)
    func outline(for target: MentionTarget) -> NSRect?           // hover highlight, in this view's coordinates
    var takesKeyboardFocus: Bool { get }                         // terminal, browser: true; code, note, HTML: false
    var surfaceLuminance: Double? { get }                        // what default-ink drawings over it contrast with (page background, image, terminal theme); nil: the app's own (default); post .tileSurfaceChanged on change
    var accessibleText: AccessibleTextElement? { get }           // VoiceOver's read-only text area while live: code lines (numbered), a terminal's screen; built only when asked (default nil)
    func update(_ object: CanvasObject)                          // a new revision of the backing object
}
```

`TileFrameView` owns each card task. Replacing a request, changing liveness or host-board availability, or detaching the frame cancels that task and invalidates its result. Deferred cards check cancellation before rendering. Closed Note and Changes renders use their retained models without file or Git reads. An availability generation rejects results that cross closure, including a close followed by a reopen, before they can replace retained models.

`render` draws the content offscreen for `view.render`, independent of liveness, window, Space, and viewport: from the tile's model (or an AppKit view that draws itself anywhere, like a code tile's header, drawn offscreen), never by capturing what is on screen. `TileRenderRequest` = `size` (the body in the content's points: the frame below the title bar, ÷ the tile's zoom), `scale` (pixels per point, the render's × the tile's zoom), `full` (the whole content, not the frame's window), `appearance` (resolve colors under it). `TileRender` = `image` (points, top-left at the body; `max(size, contentSize)` when full), `contentSize` (the content's extent at that width; overflow = content − size; a code tile's is its range, `CodeDocument.content`, which is what `size: "fit"` sizes), `state` (`rendered`, or `placeholder`/`failed` with a `reason`; never `rendered` with a blank image). The renderer cancels a render at the request's deadline (tiles should return what they have when cancelled) and reports a tile that still hasn't answered a second later as a placeholder. Tile chrome (title bar at 1×, with the content zoom's % when not 100%, and border) is drawn around the image by the renderer, the image at the tile's zoom inside the frame; app chrome never is.

Zooming never redraws the scene: everything in the document (tiles, groups with their titles and borders, drawings, selection rings) is drawn in document coordinates and scales with the board, so its size relative to everything else never changes. Only window chrome (toolbar, tray, pills, edge pills), the dot grid, shape resize handles, selected tiles' resize handles, and attention markers stay screen-sized. A selected tile's handle (`TileHandles`) is a window-space view above `AttentionLayer`, so a marker ring never hides it; it takes no clicks: `TileFrameView`'s corner grip reaches under it, `TileHandles.reach` screen points past the corner, for every tile in a group or not. A marker's ring is its own view (`MarkerRing`) that pulses three times when the marker appears or its message changes; the bubble never fades. Bubbles keep off their object's header: `PillLayout.Marker.header` is the title bar plus `TileContent.headerHeight` (a browser's address bar, a code tile's header). Markers (`AttentionMarker`) live in `AttentionLayer`, a window-space view over the scroll view that passes clicks through except on a bubble; `CanvasView.layoutPills` places each around its object's on-screen rect, with the edge pills (`AttentionEdgeView`), on every bounds change (each pan and live-pinch step), so a marker tracks the zoom continuously and keeps its fixed size. Edge pills cover no tile (`PillLayout.place(... bands:)`): the nearest stretch of their edge clear of every on-screen tile, pill and prompt, else a chip in `CanvasView.chromeBands` covering the least tile area there, then nearest the ideal spot (the window controller's free parts of the toolbar row, left and right of the drawing toolbar, in window coordinates; none while the toolbar is hidden), else the earlier compromise on the edge. While `CanvasView.chromeHidden` (View › Hide Board Chrome) marker views are hidden and left out of placement; blocked terminals' are not. Cards are what the live tile shows: code cards draw the tile's own header view offscreen (`CodeHeaderBar.prepareForSnapshot`, its real controls) above rows drawn from the model at the tile's scroll; HTML cards are the live page's last capture. Going live, `TileFrameView` keeps the card over the content, which renders beneath it, until `whenLiveReady` fires (HTML: the page's first `view.rendered` after it attaches, once WebKit has presented that frame, `WebStage.afterNextPresentationUpdate`; browser: the page loaded and presented), at most `TileFrameView.revealLimit` (2 s).

Arrows, shapes, and groups have no tile; the board draws them.

Tiles never read or write the board store directly; they go through the board model on the main actor, which persists and broadcasts events.

### Code navigation

Code views get language features by conforming to `CodeNavigationHost` (`Sources/CanvasApp/CodeNavigation.swift`) and attaching a `CodeNavigation(host:board:tile:accessories:reservedWidth:languages:)`. The injected `LanguageService` belongs to the machine that owns the file.

```swift
@MainActor
protocol CodeNavigationHost: AnyObject {
    var navigationPath: String { get }                           // board-relative path of the file shown
    var navigationView: NSView { get }                           // the view showing rows; its coordinates are the host's document coordinates
    var navigationUnavailableReason: String? { get }
    var navigationText: SideText? { get }
    var navigationLineHeight: CGFloat { get }                    // row height, so panels open below the hovered line
    func sourcePosition(atViewPoint point: NSPoint) -> (line: Int, character: Int)?  // point in navigationView; 1-based line, 0-based UTF-16 column (a wrapped line's continuation rows map past the break); nil on peeked base rows/gutters
    func reveal(line: Int)                                       // scroll a 1-based line into view
    func webLink(atViewPoint point: NSPoint) -> URL?
}
```

The controller adds a hover tracking area to the view only while `setActive(true)` (hosts deactivate it when the tile goes not live: tracking areas on hidden tiles are rebuilt on every frame of a pan), handles ⌘/⌥⌘-click and right-click on it through an app-level event monitor (Hyper stays with `HyperMonitor`), extends the view's own `menu(for:)` rather than replacing it, and places an Outline button in the host's header (`accessories:`), inside the trailing `reservedWidth` points the host keeps free (`CodeHeaderBar.reservedTrailing`). Hosts call `contentChanged()` when they scroll or show new content, which dismisses hover and panels.

- **Outline** lists `LSPSymbol.outline`: every top-level symbol and the members of modules, namespaces, classes, enums, interfaces, structs and objects, never what a function or method holds (its locals). Its panel (`NavigationPanel.filterList`, shared with Find References and a list of several definitions) takes the keyboard, because the user asked for it: a filter field narrows the rows to names containing the text, ↑/↓ move the highlight, Return reveals it, Esc closes; closing gives the keyboard back to whoever had it (a terminal through its own focus path, `CanvasView.returnKeyboard`) unless something else took it. Hover panels never take it.
- **From the keyboard** (Code ▸ Go to Definition ⌃⌘J, Open Definition in New Tile ⌃⌥⌘J, Find References ⌃⌘R, Outline ⌃⌘O, on the focused code tile, else the one selected, else the one last clicked (`KeyboardFocus.codeTarget`), and with none a notice says there is no code tile to act on; `CodeTile.navigate`): no pointer names a symbol, so they act at the rows' selection, else at the first name that isn't a declaration keyword from the tile's first range line (else its top row) down through its range and the rows in view (`CodeSubject.first`: `write_usage` in `    def write_usage(self, …):`; a tile aimed at a closing brace, a comment or `@MainActor` means the next line's name). With no name there, a message in the tile says to select one; the commands never do nothing silently.
- **Find References** lists the references, each line once (servers list a line twice, e.g. a re-export's two names), in a filter list like Outline's that takes the keyboard (↑/↓, Return, Esc; ⌘↩ is Open All); a row opens that one (`Board.openForNavigation`, see Navigating to code). The list's **Open All** lays out every reference as a code tile (`Board.openExcerpts`): the reference line with 3 lines of context either side (clamped to the file), captioned "Reference N of M to `name` · L…", measured like `size: "fit"`, stacked top to bottom (a new column past 2400 pt) in a group titled "M references to name" in the free slot nearest the tile (`Board.place(near:)`); one undo step; the board pans the least that shows the first reference.
- **Without a language server** (`CodeNavigation.textFallback`: `LSPError.unavailable`, `unsupportedLanguage`, `startFailed`, `serverExited`; a timeout or the server's own error is shown as it is): Go to Definition, Find References and Outline answer from text (`TextNavigation`, CanvasCore). The search root is the board root for a file under it, else the repository holding the file (`searchRoot`). References: `git grep -n -z --column -w -I -F --max-count 60 --untracked -e <name>` (`--no-index --exclude-standard` outside a repository) through `GitRunner`, at most 200 matches (`truncated` says there were more). Definition: the same word matches filtered to lines that declare the name (`declarations(inLine:pathExtension:)`), ranked this file, then its language family, then the rest (`rankDeclarations`). Outline: `TextNavigation.outline` (tree-sitter `SyntaxSymbol`s with their `kind`, minus anything nested in a function, plus unindented pattern declarations on lines no symbol starts on). Every such list is titled as text search ("no language server") and carries the server's error as its one-line `note` (`NavigationPanel.filterList(note:)`).
- **Workspace symbols** (`LanguageService.workspaceSymbols`, `workspace/symbol`): one request per language and project root among the given files, starting servers as needed; a project whose server is missing or fails adds nothing. Go to asks with the files the board's code tiles show, else the first file of the language most listed files are in.
- **Call hierarchy and type definitions** (`LanguageService.prepareCallHierarchy`, `incomingCalls`, `outgoingCalls`, `typeDefinition`; LSP `textDocument/prepareCallHierarchy`, `callHierarchy/incomingCalls`/`outgoingCalls`, `textDocument/typeDefinition`): the client offers both capabilities at `initialize`, and each request first checks the server's answer (`callHierarchyProvider`, `typeDefinitionProvider`): a server without it throws `LSPError.unsupportedRequest` naming the command and the capability (sourcekit-lsp 6.3 has no type definitions) instead of an empty answer. Items go back to the server verbatim (`LSPCallHierarchyItem.json`, its `data`); incoming and outgoing calls are asked of the server of the item's file, with that file open for the request.
- **Projects**: a file is read by the server of its language and project: the nearest directory with one of the language's root markers (`Package.swift`, `package.json`, …) within the board root, or, for a file in another worktree of the board's repository, within the board root's place in that worktree (`GitWorktree.counterpart`), so a worktree's files are that checkout's project with its own build index; anything else, its directory.
- **Paths** are real paths (`GitDiffEngine.realPath`, realpath(3)), never `resolvingSymlinksInPath`/`standardizedFileURL`, which turn `/private/tmp` and `/private/var` back into `/tmp` and `/var`: a project root spelled that way is one sourcekit-lsp can't match to its package's files, so it answers from fallback settings (no index answers; its semantic AST builds can crash sourcekitd).

Remote language services use host-resolved project roots, server binaries, paths, and root spellings. `LanguageService.relativePath` formats returned locations without resolving host paths on the viewer. Local text fallback does not run for host files.

### Navigating to code

`Board.openForNavigation(_ aim: CodeAim, from source:, preview:, extra:)` (CanvasCore, `CodeNavigationTarget.swift`) is the one rule for every user navigation to code except a terminal's ⌘-click (`Board.openReference`: `Board.openCode`, its own preview, or a page): Go to's file/symbol/Recent rows (source nil), definitions (the code tile), changes-tile lines (`preview: true`, `extra: diffBase`), an HTML page's `code.open` and a note's `path:line` link. In order: the tile `Board.tileShowing(aim, near: source's frame)` finds anywhere on the board (a code tile, any author, not a follow tile, showing `aim.path` at exactly `aim.range`, else a captioned one whose range contains it; exact first, then in view, then nearest, then topmost): nothing changes and `CodeOpened.existing` is true, and the board goes to it (`CanvasView.goToShown`: selected, `Layout.present`; a definition inside the clicked tile scrolls it instead). A terminal's ⌘-click (`Board.openCode`) asks `tileShowing` first too; with `preview`, the tile this source created last (`codePreviews[source]`) while its `rev` is unchanged and it is still `isNavigationSurface`; a navigation-surface tile in view showing `aim.path`, nearest the source's center (the viewport's without a source); else a new code tile (`place(near: source, shrinkingTo: followMinimumSize)`, or at the viewport center), which becomes the source's preview with `preview`. `isNavigationSurface`: a code tile the user created whose last writer is the user, with no caption, no `parent`, no group listing it, no `followOf`. Re-aims (`Board.reaimForNavigation`, also a terminal's ⌘-click preview and a follow tile's history strip) are `Board.unrecorded` updates credited to the user (logged, never an undo step); the answer (`CodeOpened`) carries the `CodeReaim` (tile, `before`, `after` aims). Without a viewport (no window) every tile counts as in view.

Back/Forward (`NavigationHistory`, per `CanvasView`): `CanvasView.navigating(landing:_:)` wraps a navigation, recording `Entry(from:, to:, reaim:)` with the viewport before and after (nested navigations are one entry; one that neither moved the view, re-aimed nor changed a step's selection is dropped; 100 entries). An ⌥⌘-arrow step (`CanvasView.moveToNeighbor`) records its entry directly with `selectedBefore`/`selectedAfter`, and `Move.selection` selects that object again on Back/Forward and visiting `landing` in `RecentLocations` (20, newest first, one per path and start line; Go to shows 5). Back pops an entry onto Forward and shows `from`, re-aiming `reaim.tile` from `after` to `before` only while `Board.restoreAim` finds it still navigation surface showing `after`; Forward the reverse. A new entry clears Forward. The window takes ⌘[ / ⌘] ahead of the focused view (`CanvasWindowController.navigationAction`); with a browser page (not its address field) holding the keyboard they go to the page's `goBack`/`goForward`.

### Code tiles

One view per tile, no modes: the whole file (the base version for a deleted file), scrolled to `props.range`, the range tinted only while the tile shows rows outside it (`CodeMetrics.tintsRange`: a tile fitted to its range, or a whole-file range, shows no tint; live, cards, and renders alike). Geometry is `CodeMetrics` (CanvasCore): fixed 16 pt rows, the 12 pt system monospaced font (every column `charAdvance` wide, tabs to 4 columns, East Asian wide characters and surrogate pairs 2), a gutter of line numbers plus a sign column, and header/caption/history strip heights; `object.measure` uses the same numbers. Rows soft-wrap at the tile's text width (`CodeMetrics.textColumns`, `CodeMetrics.wrap`): a line wider than the text column continues on rows with no line number (a faint ↪ instead), its gitsign continuing down the gutter, and its text indented by the line's own indentation plus 2 columns (at most half the row); tabs expand against the unwrapped line and breaks never split a surrogate pair. Nothing scrolls sideways. A resize by the user rewraps live, keeping the top line in place; any other change of the tile's natural size (an agent's `object.update` frame or `size: "fit"`, undo) re-aims the scroll at the range by `CodeMetrics.scrollOffset` (`CodeTile.resizedElsewhere`, called by `CanvasView` when the content's size changed under it), so a fitted tile shows exactly its range. The model is CanvasCore's `CodeDocument` (built off the main thread from `GitDiffEngine`'s `FileDiff`): `GitSign`s from the diff's change records (added bar, modified bar, deleted wedge on the top edge of the line after the deletion, `lineCount + 1` at the end of the file), per-line highlight runs (`SyntaxLines`) for both sides, and the header's status and warning (`noBase`: no commits yet / no default branch / no merge-base, `diffTooLarge`, deleted). A file not in the base is `added` (every line an added bar; `untracked` when git doesn't track it yet: "new file, not tracked by git yet"), unless git ignores it (`git status --porcelain --ignored=matching` says `!!`, e.g. a node_modules frame): `ignored`, plain source with a quiet "ignored by git". The base picker names the base as the changes tile's does (`ChangesBaseChoice.title`: Uncommitted changes, Branch vs origin/main, vs <commit>); the status adds the base's commit unless the picker shows it (a commit typed as its sha), and `CodeDocument.baseDescription` (`against merge-base with origin/main b57db4f`) is the picker's and status's tooltip. `CodeRows` inserts peeked base lines above the lines that replaced them (entries: logical rows) and maps entries to visual rows (wrapped entries take several): `row(_:)`/`segment(_:)` give a visual row's logical line and slice, `index(ofLine:)` a line's first visual row, `rows(ofLine:)` all of them; `WrapText` measures each line's columns once per load so rewrapping skips lines that fit. Selections are `CodeRows.Position`s (entry + UTF-16 offset), so they survive rewraps and ⌘C copies logical lines; mentions, LSP positions, range tint, edit flash, peeks, hunk jumps, `reveal`, and `aim` all go through the same mapping, and cards, `render`, and the live view draw through one `CodePainter`. `CodeEdits.changes` diffs the texts of consecutive loads of the same file: those rows flash for 3 s (a follow tile also jumps to the first). A tile with `pinnedCommit` shows the file as of that commit instead (`GitDiffEngine.pinned`: `rev-parse` then `cat-file blob`, `FileDiff.State.pinned`, or `.pinUnavailable` with the reason as its notice): no signs, no base picker or change stepping, no Edit Here, header status `pinned at <sha7> (<revision>) · read-only`, and its mentions carry the commit (no side), so they quote those lines; `object.measure`, `layout.check`, and line anchors read the same text (`NoteSource.read` with the commit). `FollowLock` holds a follow tile's re-aims for 10 s after the user scrolls, clicks, or selects in it, counting them ("N new ▸"), then shows the newest.

Ranges stay on their code (`CodeAnchor`, `NoteAnchor.resolve`): a code tile with a `range` that isn't a follow tile or pinned to a commit re-finds its range whenever it installs a new text of the file (live reloads, and the reload before a render or card) or its `range`/`anchor` change: by the text the range held when the tile last found it (in memory), else `props.anchor` (the range's first line, trimmed). A range found elsewhere, or longer or shorter by lines inserted or removed inside it, is written back with its first line as `anchor` by `Board.reanchor`: bookkeeping like `writeBookkeeping` (no `rev`, undo step, or log; a board revision and `object.updated`), so agents, `layout.check`, measure and renders see the moved range and an agent's `object.update rev:` still holds. Undo restores `range` and `anchor` together, and the tile re-finds the range from there. A range whose code is gone keeps its lines, loses its tint, and the header shows "⚠︎ stale: …" before the status. An `object.update` (or any re-aim) that changes `range` or `path` without an `anchor` drops the old `anchor` (it named another line); an agent may pass `anchor` itself. `object.get` on such a tile adds `rangeStatus` (`AnchorStatus`): the tile reloads the file unless it is current (re-anchoring as above, and the returned `object` carries the result) and resolves the range with the text it last found there (`ApiRouter.codeRangeStatus`), so a first line repeated elsewhere never passes for it; without a tile, by `props.anchor` alone. Links are positions: `<canvas-link line=>`, `<canvas-code lines=>` and a note's `path:line` don't move with the code (`<canvas-code>` shows a stale badge when its `symbol` is lost); only ranges that anchor do.

Automatic code-anchor metadata stays within the board's file policy on both hosts. `Board.reanchor` on the Mac reads through `BoardAreas`; easld's `measure.Reanchor` uses the same authorized reader as note metadata. The canonical board root grants access, not the resolved ref root. Outside paths, escaping symlinks, and committed symlink blobs produce no automatic `props.anchor` or range writeback. On host load, persisted `props.anchor` is host-generated metadata and is removed when its path fails the same policy, including explicitly supplied values. Allowed anchors remain unchanged, including anchors for missing inside files. The host persists changed snapshots without changing revisions, timestamps, undo history, activity, or events. A second load performs no scrub save. Local tiles still display and relocate outside files in memory, including their scroll position, keyboard mentions, and navigation targets. Changing the diff base preserves that capture because it changes the comparison, not the current file. Code update events precede the automatic anchor bookkeeping event.

The view draws only visible rows (a CTLine per visible row, cached only while visible) and scrolls itself, with no NSScrollView; not live, it keeps no line cache, layer contents, tracking areas, or views in the window, and cards, `snapshot()`, and `render(_:)` draw rows straight from the model.

Mentions: a row is the line on the side it shows; a sign in the gutter is the whole change (a deletion: its base lines, `side: old`); a peeked row is a base line (`side: old`, `commit` = the base). While a tile shows changes against a base, its new-side mentions carry `side: new` and that base's commit.

Follow tiles (`props.followOf`): `Board.follow` (`follow.report`) re-aims the terminal's one follow tile (at `range`, else at the hunk of `changes` spanning the most lines, the last of equals: `Board.followAim`; `changes` is kept as `props.lastChanges`, which the tile flashes when it loads the file fresh, and a re-load of the file it shows flashes whatever changed), creating it with `Board.place` beside the terminal (shrunk to stay wholly in view when the terminal is on screen, see Placement). Reports are ignored while the terminal's `props.follow` is `false`, and for paths `FollowFilter.follows` rejects: outside the board root, the terminal's cwd, and every other worktree of their repositories (`GitWorktree`: directories whose `.git` leads to the same common git directory, read from the filesystem, no git process; such a file keeps its absolute path, so the tile diffs it in its own worktree); under the temp directory (`NSTemporaryDirectory()`, `/tmp`, `/var/tmp`) unless the project containing it is there too; missing, a directory, larger than the code tile's limit (`GitDiffEngine.maxFileSize`, 4 MiB, by its size, unread), a binary extension (images incl. svg, pdf, archives, objects, media, fonts), or a NUL byte in the first 8000 bytes. The tile keeps its last accepted file. Deleting a follow tile other than by undo/redo sets its terminal's `props.follow` to `false` in the same undo step; `Board.setFollowing` (the terminal's "Follow Files" menu item) sets it back to `true` (the next report creates the tile) or to `false` and deletes the tile, one undo step. Deleting a terminal deletes its follow tiles in the same step. The history (`props.history`, newest first, at most `Board.followHistoryLimit` = 8) records each location with its action; a location revisited moves to the front and stays `edit`/`write` once edited, and past the limit the oldest reads go first, so every edit of a parallel burst (omp lands three edits within 50 ms) stays listed. The history strip (`CodeHeaderBar.fitStrip`) marks edit and write chips with a pencil in orange, always shows the current location, then the edits, then as many of the newest reads as fit whole, in history order; the oldest reads drop off a narrow tile first instead of the strip clipping or squeezing the current one. A re-aim to another file and back before the other file loaded (two reports a millisecond apart) still scrolls to the newest range when the load installs the same file (`CodeTile.rangePending`). A code tile whose file is on neither the disk nor its diff base (`FileDiff.State.missing`, checked again 0.6 s later so a delete-and-recreate save doesn't count) calls `Board.codeFileVanished` with the history paths found on disk: a follow tile steps back to the newest `history` entry still there (its `path`, `range` and `action` as `lastAction`, no edit flash) and drops the entries that are gone; with none left, or for a ⌘-click preview in `codePreviews`, the tile is deleted as a replay would (no undo step, and a closed follow tile doesn't turn its terminal's `follow` off); the activity log credits `system`. Other tiles are kept.

### Branch-anchored tiles (`ref`)

Code, note, and HTML tiles take `props.ref`, a branch (or any ref), instead of one checkout (`RefSource`, `GitRefs`, CanvasCore). Paths keep their meaning: relative to the board root's place in the repository, and an absolute path in any worktree of the repository names the same repo path (`RefSource.url(for:)`). Each resolve (`GitRefs.resolve(repo:ref:lastKnownSha:)`) picks one state, which the code tile's header leads its status with (`RefSource.label`):

- **live** (`live in <worktree>`): a worktree of the repository (the common git dir, found from the filesystem, `GitRefs.liveWorktree`) has the branch checked out. The tile reads that working tree: a code tile diffs against its `diffBase` there (default its merge-base), shows the base picker, reloads on edits, and its mentions, Edit Here, and language features name the file in that worktree.
- **objects** (`<ref> @ <sha>`): the ref resolves but no worktree has it. The tile reads git objects at its commit, read-only like `pinnedCommit`; mentions carry the commit.
- **merged** (`merged in <sha>`): the ref no longer resolves and the default branch (origin/HEAD's target, else `main`, else `master`) contains the last SHA. The tile reads the commit that brought it in: the earliest commit on the default branch's first-parent line descending from it (the merge; the SHA itself when it was fast-forwarded).
- **missing** (`branch gone, showing <sha>`): the ref no longer resolves and the default branch doesn't contain the last SHA (a squash merge, or a branch deleted unmerged). The tile reads that SHA's objects while they exist; once they are gone (gc), it says `unknown ref <ref>`.

Every resolve records the SHA it settled on (the live worktree's HEAD, or the ref's commit; never the merge commit) as `props.refSha` (`Board.recordRefSha`: bookkeeping, no rev, no undo step, and only while `props.ref` is still that ref), which is the last SHA the merged and missing states fall back to. `object.create`/`object.update` (single or in a batch) resolve a new `ref` before writing it and add `refSha`; a ref that resolves to nothing, with no `refSha` whose objects remain, is `not_found`, one that isn't a ref name `invalid_params`, and clearing `ref` clears `refSha`. A tile re-resolves on every load: code tiles whenever HEAD, a ref, or a worktree of the repository they hold moves (`.gitRefsMoved` from `GitDiffEngine`'s repository stream), notes on the same paths through their own file events. `object.measure`, `size: "fit"`, `layout.check` line rows, `rangeStatus`, and `agent.prompt` mentions read the same place (the prompt, synchronous, uses the live worktree or else `refSha`).

Precedence: a code tile's `pinnedCommit` wins over `ref` (the ref is neither read nor resolved). A note's or HTML tile's `ref` wins over its `root`. Ranges re-anchor under a ref as on the working tree (`CodeAnchor`), so a range follows its code as the branch moves.

Notes and pages keep their body inline; `ref` sets where the files they name are read: the note's link root and excerpt fences (a fence's own `@<sha>` still wins; `LinkReading.fences`), `path:line` links (the code tile they open carries the same `ref`), and a page's `code.excerpt`/`code.open`. Images and other page files load from the live worktree, else from the board's checkout; a symbol-only fence searches the live worktree, else the board's checkout.

### Changes tiles

`ChangesTile` (`Sources/CanvasApp/Changes/`) draws a `ChangeSet` (CanvasCore) through `ChangesPainter`, live, as its card, and for `view.render`, with `ChangesMetrics`/`ChangeRows` geometry (header strip, the file list with more than one file, file rows, hunk rows, `CodeMetrics` line rows soft-wrapped at the tile's text width by `CodeMetrics.wrap` with the code tile's hanging indent and a faint ↪ in the gutter), which `object.measure` and `size: "fit"` use too (the file list open, deleted and viewed files folded, lines wrapped at the fitted width). The header of the file under the top of the rows stays pinned there while its hunks scroll (`ChangeRows.stickyFile`), pushed up by the next file's, and drawn over the rest of the file's last row when only a sliver of it shows above the next file. The header strip (`ChangesPainter.headerLayout`) holds the summary (`ChangeSet.lead`, drawn with ▾, then `counts`: `Uncommitted changes · 3 files · +40 −12`, `pr-1041 vs origin/main · 6 files · +62 −0`: the reviewed worktree's branch, or `HEAD` detached, against `baseName`), the keys when they fit beside all of the summary (`ChangesMetrics.hint`), and a filter field (an `NSSearchField` while live, drawn text in cards) that limits the list and the sections to files whose board path contains its text. A click on the lead opens the base picker (`ChangesBaseChoice`: `HEAD`, `merge-base` titled `Branch vs <GitWorktree.defaultBranch>`, the typed revision when current, and Commit or Ref…, a popover field); a pick is `object.update` of `props.base` by the user, one undo step.

Listing (`ChangeSet.load`, all through `GitRunner`, off the main thread): the reviewed directory is the board root, or `ChangesSpec.root` resolved against it when that lies in a worktree sharing the board repository's common git directory (`GitWorktree.sameRepository`, from the filesystem); any other `root` is refused (`notice`, nothing listed). `rev-parse --show-toplevel` from that directory; the base resolved as code tiles resolve theirs (`ChangesSpec`: `base` default `HEAD`); `paths` (default the reviewed directory) turned into repository-relative literal pathspecs, and anything resolving outside that worktree refused; `git diff --raw -z -M <base>` plus `git ls-files --others --exclude-standard` (untracked = added), at most 300 files (`omitted` counts the rest); each file's texts and hunks from `GitDiffEngine.diff` (a rename: the base text of its old path and `git diff -M -U0` between the two paths); hunk status from `git diff -U0` (index → working tree), `git diff --cached -U0` (HEAD → index) and, for a base older than HEAD, `git diff -U0 HEAD` (`ChangeHunk.status`: `partial` where the index differs from both the working tree and HEAD over the hunk, i.e. staged and edited again). Board paths are relative to the board root when under it, else absolute (another worktree's files). Hunk ids (`ChangeHunk.id`) hash the path and the unified lines (FNV-1a), so they survive line shifts elsewhere; a file's `fingerprint` hashes its hunk ids, status, and notice. The live tile reloads on `FileEvents` (FSEvents) under the repository's top level, and the worktree's own git directory when it lies elsewhere (a linked worktree's `<common>/worktrees/<name>`), ignoring the git directory except `index`, `HEAD`, `packed-refs`, and `refs/`, and on `.gitDiffBaseChanged` and `.reviewPatchApplied`.

Two commits (`ChangeSet.loadCommits`, `CommitChanges.swift`): with `ChangesSpec.head` (any commit or ref) the tile compares commits instead of a worktree, from git objects alone, never touching a working tree or the index: `head` is resolved with `rev-parse --verify <head>^{commit}`, the base as written (`merge-base`, the default with `head` or `ref`: the default branch; `HEAD` with a `ref`: the ref itself), and the diff's base is their `git merge-base` (`base...head`, a pull request's view, so commits the base gained since the fork never show reversed; a ref gone and merged, `GitRefs` `.merged`, takes the merge's first parent once the base holds the head). `git diff --raw -z -M --no-abbrev <merge-base> <head>` lists the files with both blob ids; `git cat-file --batch-check` then `--batch` reads the blobs, at most `GitDiffEngine.maxFileSize` each (larger: `too large to show`; a NUL in the first 8000 bytes: `binary file`; mode 160000: `submodule`); one `-U0` `git diff <merge-base> <head> -- <paths>` gives the hunks of files at the same path, a renamed file's two blobs are diffed on their own, an added or deleted file is all one hunk. Every hunk is `committed` and every file `ChangedFile.readOnly` (`blobs` set): no Stage, Unstage, or Discard buttons, `s`/`u`/`r` and every `ReviewPatch` builder refuse with `ChangesFailure.readOnly`, and the header offers reading keys only. The header's lead is `<head> vs <base> · <merge-base>..<head>` (short SHAs; `(merged in <sha>)` or `(branch gone)` after the head for a gone `ref`). Viewed fingerprints hash the path, status, notice, old path and both blob ids, so a mark holds while neither side of that file changes, wherever the head moves. A live tile watches only the common git directory's refs (`refs/…`, `packed-refs`). A click on a line opens a code tile pinned (`pinnedCommit`) to its side's commit: the merge-base for a removed line (at the file's old name), else the head (`CodeAim.pinnedCommit`, and `ref`: navigation re-aims or reuses only tiles showing that same version); a mention of a new-side line names the head commit (`· at <sha>`). A commit or ref the repository lacks lists nothing: the notice is `no commit <ref> here; fetch it: <command>` (`ChangeSet.fetchCommand`: `pull/N/head` → `git fetch origin pull/N/head:refs/pull/N/head`, `<remote>/<branch>` → `git fetch <remote> <branch>`, a commit id as it is, any other name into that local branch). easl never fetches: every git process runs with `GIT_NO_LAZY_FETCH=1`, so a partial clone's missing blob is missing, not fetched.

`ChangesSpec.ref` (a branch, instead of `root`) is resolved by `GitRefs.resolve` with `props.refSha` as the last known commit: `.live` reviews the worktree that has it checked out (the board root when that is the board's own checkout) exactly as a `root` tile would; `.objects`, `.merged`, and `.missing` compare that commit with the base as above, read-only. The tile writes the commit it read back to `props.refSha` (`Board.recordRefSha`: credited to the system, no undo step, only while `props.ref` is still that ref), which is what it keeps reading once the branch and its worktree are deleted; `object.create`/`object.update` resolve a changes tile's `ref` as they do a code tile's (`ApiRouter.referenced`), their `not_found` naming the `git fetch` that brings it (`ChangeSet.missing`). `head` with `ref`, or `ref` with `root`, lists nothing and says which to drop.

Actions (`ReviewPatch`, `ReviewGit`): every Stage and Discard is one unified patch, applied with `git apply --whitespace=nowarn -` in the repository's top level (the reviewed worktree's), and its undo is the same patch applied the other way round (`-R` toggled). Patches only name repository-relative paths (no `..`, no `.git`, `ReviewPatch.checkPath`) of files the listing found, and never carry mode changes except a created or deleted file's own.

| Action | Patch | Applied | Undo |
| --- | --- | --- | --- |
| Discard hunk / file, base HEAD | base → working tree over the hunk's changes (all of a file's; a created file is its deletion, a deleted file its re-creation from the base; a renamed file keeps its name), 3 lines of context, from the texts the tile shows | `git apply -R` to the working tree (the index is untouched) | `git apply` of the same patch: the hunk comes back exactly |
| Discard hunk / file, base older than HEAD (`ChangeSet.includesCommits`) | HEAD → working tree changes (`git diff -U0 HEAD`, read at the moment and checked against HEAD's text and the working tree the tile showed) that touch the hunk's working-tree lines, or all of the file's; an untracked file is its deletion, a file deleted since HEAD its re-creation; committed hunks refused (`ReviewPatch.discardUncommitted`) | `git apply -R` to the working tree | `git apply` of the same patch |
| Unstage hunk / file | HEAD → index changes (`git diff --cached -U0`, checked against both texts) that touch the hunk's lines in the index (`ChangeHunk.indexSpan` through the index → working tree changes), or all of the file's; a file new in the index is its creation, a staged deletion its removal (`ReviewPatch.unstage`) | `git apply --cached -R` | `git apply --cached`: staged again |
| Stage hunk / file | index → working tree changes (`git diff -U0`, read at the moment of staging and checked against both texts) that touch the hunk's working-tree lines, or all of the file's; an untracked file is added whole, a file deleted from the working tree removed | `git apply --cached` | `git apply --cached -R`: the index is as it was (an added file is untracked again) |
| Discard / Stage / Unstage selected lines | the hunk's patch as above with only the selected changed lines (`ReviewPatch.LinePick`; a patch not built from the tile's own texts finds a selected line in the other version by its text in the change there, `ReviewPatch.matching`). Within a change the n-th removed and n-th added line stay paired. Forward (stage): unselected `+` dropped, unselected `-` turned into context; reversed (discard): unselected `-` dropped, unselected `+` turned into context; headers recounted | as the hunk | as the hunk |

A patch that doesn't apply (the lines changed since the tile read them, the index is locked by another git) changes nothing and the tile says so in its header (`ChangesFailure`); staging a hunk the index already holds is refused as `already staged`, unstaging one it doesn't as `not staged`, and discarding a committed hunk (`HunkStatus.discardable`; a file whose hunks are all committed, `ChangedFile.discardable`) as `committed: Discard only puts back work not committed yet`: the tile shows no Discard button there. Discard asks first, by key or click alike (`DiscardQuestion`, one pending question naming the file, hunk id and picked lines, with the header's hint: the button's red "Discard?" and the hint are painted from it together): `r` asks and only ⌘⌫ answers (`DiscardByKey`; a second `r` never discards, so text typed into the tile can't), a click on a Discard button turns it into "Discard?" that a second click on it confirms (the header says how to go on). The question never times out; any other press or key in the tile, the keyboard leaving it, or anything else the header says drops it; once applied, the board's notice says `Discarded <path>, lines 13–20 from your files · ⌘Z undoes` (`ReviewPatch.discardNotice`, undo's own naming). Unstage takes Stage's button once all of a hunk (or file) is staged; `u` unstages the selection or the current hunk. `ReviewGit` applies patches one at a time in the order asked, so an undo right after its action waits for it. `Board.recordReview` records an applied action as one undo step: the tile's `props.reviewed` entry (`ReviewPatch.entry`: action `stage`, `unstage`, or `revert`, path, scope `file`/`hunk`/`lines`, the hunk's `id`, `header`, `label`, counts, and the patch text, at most 200 lines; at most 100 entries, oldest first) and an `UndoEffect` named for it (`ReviewPatch.name`: `Stage of src/a.rs`, `Discard of src/a.rs, lines 15–46`, `Unstage of 2 lines of src/a.rs`) whose undo and redo apply the patch reversed and forward; one whose patch no longer applies is reported to the tile (`.reviewPatchFailed`) and leaves the files alone.

Viewed: the file header's check writes `props.viewed[boardPath] = fingerprint` (one undo step, dropping entries whose diff changed since) and folds the file; an entry counts only while the fingerprint matches (`ChangedFile.isViewed`), so a changed file unfolds on the next listing. Fitted tiles (`ChangesMetrics.grown`): after a reload, a tile whose natural height equals `ChangesMetrics.fit` of the previous listing (at its width) grows toward the new fit when that is taller (`Board.growFitted`: into free space only, `Board.grownFrame`, never over a neighbour, the rest scrolls; credited to the system, never an undo step); one sized for an empty listing (or none yet, after a relaunch) grows wider too, a tile the user made (Review Changes: a compact "No changes" when it first lists nothing) to at most the default 820×620. Review Changes (the board menu's per-worktree Uncommitted changes and Branch vs <default branch>, File › Review Changes and Review Branch) lists first (`ChangeSet.load`) and then creates the tile, compact when nothing is listed. `object.create` of a changes tile by an agent (`caller`) that already made one on that board for the same `root` (resolved), `base`, and `paths` is `object.update` of that tile with the call's other props, `frame`, and `size`, and answers `reused: true` (`ApiRouter.reusableChanges`; not in batches).

Scrolling: a trackpad gesture belongs to whoever its first movement picks (the tile when it can scroll and the movement is mostly vertical, else the board) until it ends, momentum included. A gesture the tile did not see begin stays with the board, even if the tile also missed the previous gesture's end. `CanvasWindow.sendEvent` counts gesture starts for `ScrollGesture`, including starts outside the tile. A gesture's first event without movement never reaches the board while the tile can scroll, so the board cannot start tracking a gesture that turns out to be the tile's. Wheel notches and phaseless steps go one by one, as in code tiles. A horizontal-dominant step or a non-precise ⇧-wheel step goes to the board (`CanvasWheel.sideways`). j/k, J/K, ]/[, s/r scroll the current hunk into the tile's view below the pinned file header (`reveal`), never the board.

Opening code: a click on a line opens it by `Board.openForNavigation` with `preview: true` (the tile's own preview, else a plain code tile in view showing the file, else a new one beside the tile, shrunk down to a follow tile's minimum to land wholly in view; see Navigating to code), one step of Navigate Back; then the board pans the least that shows it together with what showed of the changes tile (`Layout.reveal(_:keeping:…)`, the padding cut to the room left when both just fit), or the code tile alone when both can't fit.

Mentions: a diff line is a `code` mention of its side's line (`side: new` for context and added lines, `side: old` with the base's name of the file for removed ones) with `commit` = the base and `diff` = what it is (`ChangeSet.mentionDetail`: `added|removed|context line · unstaged|partly staged|staged|committed hunk`); the prompt names the side either way (`, new side (working tree)`, `, old side (base)`). A hunk header mentions the whole hunk (`ChangeHunk.mentionLines`, `diff`: `whole hunk +a −r · unstaged|partly staged|staged|committed`); a file header mentions the tile. The header's hints (`ChangesMetrics.hints`) leave out staging and Discard for a listing with nothing to stage, unstage or discard (`ChangeSet.actionable`: a branch's commits only). The tile's keys (`ChangesTile.key`) act only once it has the keyboard; pressed while it is only the selection, `keyWhileSelected` says "press ↩ first to use the tile's keys" in its header, and the drawing layer leaves them alone (`ChangesTile.isOwnKey`: `r` there never picks the rectangle tool).

### Image tiles

`ImageTile` shows `props.path` (board-relative, absolute, `~/…`, or a `file://` URL: `LocalImage.tileFile`; any file the agent or user names, unlike notes and pages) decoded by `NSImage` (bitmaps, SVG, a PDF's first page), read off the main thread, aspect-fit and never scaled past its natural size above the optional one-line `caption` strip (`LocalImage.captionHeight`). While live it watches the file's directory (`FileEvents`) and reloads on any change to the file, so a chart re-saved in place, or one written after the tile was created, shows; not live, it reloads when it is again. `view.render` and cards draw from the loaded picture. Natural size is one point per pixel for bitmaps (`LocalImage.naturalSize`, from the header only), the document size for SVG and PDF; `object.measure`, `size: "fit"`, and a create without a frame height give the picture at most `width` (default `LocalImage.defaultMaxWidth`, 960) wide plus the title bar and caption. A Hyper-click on the picture mentions `.image(object, path, x, y)` in image pixels; elsewhere the tile.

GIF image tiles animate while live in a window, locally and remotely. ImageIO decodes the next frame off the main actor, with a 4096-pixel decode bound and the source's frame delay. Delays below 11 ms use 100 ms. A missing loop extension plays once, zero repeats forever, and a positive count adds that many repeats. Finite animations retain their last frame. The timer stops when parked or detached. Cards and offscreen renders use the first frame rather than running an animation offscreen.

### Video tiles

`type: "video"` uses `VideoProps`: required nonempty `path`; optional `poster`, `title`, `loop`, `muted`, `autoplay`, `startTime`, and `key`. Playback flags default to false; `startTime` is finite, nonnegative seconds, default zero. Paths are board-relative or absolute within the board's permitted areas, including registered worktree counterparts. Poster paths use the same policy. Escaping symlinks and outside paths are refused on the machine holding the file.

`VideoTile` uses AVKit's native controls and aspect-fit rendering. An `AVAssetResourceLoader` serves an opaque URL in the existing `canvas-kit` scheme through `HostFiles`, or the same no-follow local reader; it never supplies a file URL to AVFoundation or adds another WebKit scheme handler. Each descriptor read is at most 1 MiB, with at most four encoded read-ahead blocks per asset. AVFoundation's playback buffers and decoded frames also remain in viewer memory. External playback and external asset references are disabled. Parking releases the player item and preserves playback position and intent. Cards and snapshot covers use decoded pixel buffers, with asynchronous frame generation when no decoded frame is available. Closing a remote board cancels live playback and outstanding frame generation and retains only cached presentation state.

Before attachment to AVKit, video metadata loads asynchronously and the visual player receives an audio-free composition preserving the source's video and legible tracks. Muted playback creates no audio output. Unmuting reads the container's first enabled audio track through `AVAssetReader` and sends compressed samples to `AVSampleBufferAudioRenderer` with `AVSampleBufferRenderSynchronizer`, entirely on a tile-owned worker. Audio deliberately has no `AVPlayer` or `AVPlayerItem`: their internal main-queue callbacks can synchronously query stalled audio state even if construction and playback calls run elsewhere. Native mute, volume, pause, seek, and buffering state drive the isolated renderer. Audio preparation shows a status on the tile; if output has not started within eight seconds, the tile reports unavailable audio without blocking video controls or the rest of the app. Muting, parking, or closing cancels pending audio work; a stalled system call cannot block another tile's audio controls.

The visual player keeps `AVPlayer.automaticallyWaitsToMinimizeStalling` at its default so AVFoundation buffers and resumes playback after starvation. Audio follows only while the visual player is playing. A two-second timestamp horizon bounds queued compressed samples, with one pending sample at the admission boundary. Clock drift over 100 ms is realigned to the visual timeline; native seeks restart the audio reader. Concurrent requests for the same encoded block share one host read. Cancelling a request releases its interest in that read. The read is cancelled when its last reader leaves, and a cancelled asset cannot refill its encoded cache.

Creation without `size:"fit"` uses a 640 by 386 point frame. `object.measure` and fitted writes read bounded MP4/MOV track headers on either host, including the display transform, and add the 26 point title bar. Unsupported or unreadable metadata returns `unavailable`; it does not invent an exact size or require an attached Mac on easld. The default fit width is the image fit width, 960 points. Video does not apply content zoom.

### Diagram tiles

A diagram tile (`type: diagram`, `DiagramProps`) is computed from the code, not drawn. `kind: calls` (the only kind so far; the model is kind-neutral so type/ER graphs and pipelines can add kinds with their own builder) is a function's call hierarchy: `CallGraphBuilder` (CanvasCore) resolves the root by its symbol (`symbol`, `Type.member` or a bare name matched against the file's document symbols, without `path`, the file found by `NoteSource.locate` when that file's document symbols declare it, else by `workspace/symbol` for the name, asked of the projects (at most 3) of the tracked files mentioning it (`git grep -w`, at most 40, declaration-like lines first), each answer in the board's files checked against its file's document symbols for the container (typescript-language-server names none): an answer counts once the next one (1.5 s later) finds the same declarations, since a server still reading the project answers with part of it (tsserver just started: the opened file's only); one declaration left is the root's file, several are an `error` listing them as `path:line (Container.name)`; or the document symbol at or around `line`), asks `prepareCallHierarchy` at its name, then walks `incomingCalls`/`outgoingCalls` breadth-first `depth` levels each side and one more level under each node in `expanded`. The graph is of one checkout (`DiagramRefresh.scope`): the one the root's file lies in (`path`, else the root node it last found; a file in another worktree of the board's repository means the board root's place in that worktree, `Board.checkoutRoot`), else the checkout of the agent that created it (`Board.callerCheckout`), else the one the user opened the board from (`Board.workingRoot`); the bare symbol is looked for there and paths are written as the board stores them. Only items in that checkout's files are nodes (the SDK's, generated interfaces and compiler-made `$…` thunks are dropped); at most 60 nodes (`omitted` counts the rest). Node ids are `path#Container.name` (`@line` on a same-named second symbol), so moving code keeps a node's id, expansion and arrows. A node is placed at its document symbol in the file's current text (at the item's position, else the one of its name nearest to it): sourcekit-lsp places items and calls where the last build's index saw them, so code moved since shows where it is now, its calls shifted with it. A node's `lines` are its document symbol's range; its excerpt is the lines of its calls toward the root for a caller, else its signature up to the line opening its body (at most 3 lines).

The graph lives in `props.graph` (`DiagramGraph`), bookkeeping (`UndoHistory.bookkeeping`, `Board.writeBookkeeping`: no rev, no undo step), written by `DiagramRefresh.run` only while the props it was computed for are still the tile's. Freshness: a build is merged with the previous graph of the same aim (`DiagramGraph.merged`): a previous node missing from the new graph whose symbol is no longer declared in its file (or whose file is gone) stays, `stale: true`, with its edges to what remains (`stale` edges); one whose symbol still exists (it stopped calling, was collapsed, is past a smaller depth) is dropped. A root whose symbol is gone keeps the whole previous graph with the root stale and `error` saying so (`DiagramGraph.stalled`); any other failure keeps the previous graph with `error`. Changing `kind`, `path`, `symbol`, `line` or `direction` starts over; `depth` and `expanded` don't.

`DiagramTile` (CanvasApp) draws the graph with `DiagramLayout` (CanvasCore; deterministic from the graph, so the tile, `object.measure` and arrow ends agree): one column per level, callers left of the root and callees right, each column ordered by its neighbours toward the root and centred on the tallest, a status strip above, scaled down (never up) to fit the body and centred. It recomputes on creation, when re-aimed, on a debounced (0.6 s) change of any file it shows while live (`FileEvents`; not live, when it is again), after a launch once it shows, and on `object.reload` (`ApiRouter.refreshDiagram`: the tile's own refresh; a board without a window computes directly). The router waits up to `timeoutMs`, default 60 s (`ApiRouter.computeDiagram`), and then answers `loaded: false` with the graph the tile has while the computation goes on: a language server that doesn't answer never holds the request longer. `object.create` (or an upsert that creates) with `size: "fit"` and no `props.graph` creates the tile at its default size (at the given `x`, `y`), computes it the same way with the 60 s default, then fits it to the measured graph where it is then (moved meanwhile, it stays moved; deleted meanwhile, the create still succeeds, with a warning) as a system write (not an undo step: one ⌘Z removes the tile); the result adds `diagram`, that summary, and a graph not there when the wait ends leaves the default size with a warning (`ApiRouter.createFittedDiagram`). In a batch, sizes are measured before anything changes, so a diagram there fits only once it has a graph. A click on a node with + (or −) toggles its id in `props.expanded` (an undo step); a click on its `path:line` opens the code (`Board.openForNavigation`). A Hyper-click mentions the node as a code mention (`DiagramNode.mention`): its declaration's lines, or the excerpt line under the pointer, `symbol` the node's `Container.name`. A tile still at the default size is sized to its first graph, and a tile whose graph gains nodes (a node opened) grows to show them, never shrinking (at most 1600 × 1100 body; unrecorded writes). Growth never covers another object and never relocates the tile (`Board.grownFrame`): the whole size from a corner with room (`Layout.refit`: it may grow up or left, keeping its other edges), else from its top-left as far as the free space right and below allows, `placementGap` short of neighbours; the graph is drawn scaled to what it got. After the user's own click opens a node (not an agent's `expanded` update, which follows `view.follow` rules), the board pans, animated and never zooming (`Layout.revealGrown`): the least pan that shows the whole grown tile when it fits in view; else the added nodes with the clicked one when those fit; else toward the added nodes' left and top edges, cut short where the clicked node would leave the view. Moving it to a free slot (`refitFrame`) would take the node just clicked from under the pointer, and scrolling inside the tile would make node boxes, and arrows bound to them, depend on per-view state the model can't see.

## Export

The object menu's Copy as Image and Save as PNG… draw the selection with `view.render` (`CanvasView.render`, `.objects(selection)` plus every group whose members are all selected, `SelectionScope.export`, at 2 px/pt: tiles, drawings and groups under it, no app chrome) with `RenderRequest.chrome` false: as View › Hide Board Chrome shows the board, without author marks, close glyphs or the dot grid (a plain board background; `view.render` itself keeps them). ## Remote boards

A remote board's window (docs/design.md "Client mode") speaks the host's API over two board-level `EaslConnection`s. The main connection carries `events.subscribe`, reads, writes, prompts and delegated calls, including render requests; the other carries diagram reloads. Each live streamed browser has an additional dedicated connection to the board host over the existing SSH transport, whether the page comes directly from a Mac host or is relayed through easld.

When the host is easld, the viewer sends `client.attach` with its persistent `identity` on the mirror's main connection. It serves `agent.prompt`, `agent.read`, `view.get`, `text.measure`, `view.render`, HTML `object.measure`, `object.reload` and `browser.call`. Terminal methods read or type through the attached surface. Drawing and HTML layout use the viewer's actual tiles and WebKit, never a delegated call back to easld. Diagram reload runs the Swift builder against host files and language servers, then returns its result for easld to validate and persist. Browser commands and reload use the real page on the named drawing Mac, including its retained background canvas. HTML re-renders on prop changes rather than accepting reload. `view.snapshot` stays unsupported. An app host receives no attach. A refused attach leaves board reads and edits working, without an attach retry loop.

Before creating a Mac-hosted board's window, the viewer identifies its server with `client.list` on the loaded board's connection. Easld returns a clients list; the Mac app answers `unsupported`. A server predating that method answers `invalid_params` and retains the OS-based guess. A malformed success or a ten-second timeout is `unavailable`; other host errors retain their code. Identification does not change the selected socket or server home. Easld on macOS attaches viewers and keeps zmx sessions in `<home>/zmx`, rather than inheriting the installed app's launcher or session directory.

The attached viewer measures plain-text notes exactly. If any item in a `text.measure` batch needs an anchored fence or an image from the host, it returns `unavailable` and easld approximates the whole batch on the host. The viewer never reads a same-named local path for a host file.

An attached viewer measures HTML pages exactly for `object.measure` and every `size:"fit"` path, including updates, upserts and batch references. Page files and excerpts resolve through the host's file reader using the candidate page's `root`, `ref` and `refSha`, even before a tile exists. Exact replies omit `approximate`. A client answer marked `approximate:true` keeps that marker. Without a capable client, HTML measurement remains `unavailable`; easld has no fallback HTML layout engine.

Failure to read WebKit's document dimensions is `unavailable`, never an invented exact size.

easl › Keep Remote Boards Attached is on by default. Closing an easld board's sole-tab window keeps its controller, tiles and attachment alive without a visible window. A manually closed tab beside other tabs and `board.close` detach and remove its reopen entry. Turning the setting off ends hidden attachments and pending background loads immediately, but leaves visible boards attached and keeps the reopen addresses. Turning it on or launching easl attaches listed boards offscreen. Quitting closes every attachment. `client.list` on easld reports each attachment's `id`, optional `app` and `host`, sorted `boards` and `serves`, and optional last `focused` board. The Mac app answers `unsupported`.

AppKit decides whether to quit when the last window closes. Once background attachments or loads keep easl running, a later detach, setting change or load failure does not automatically quit the app. Reopen restores a window; Quit ends the process and every remaining link.

For delegated `view.render`, easld requests inline bytes and strips `out` before sending the call. The viewer refuses file delivery and returns no path. If the caller asked for a file, easld writes it on its own machine; an inline caller receives the bytes unchanged. A browser ID or singleton browser-ID list selects its persisted drawing identity and renders that Mac's real page. Multi-object lists and rectangles use the selected viewer's native providers, including current browser stream images. Without a current stream frame, a browser requests an inline single-browser render through that same drawing-machine route on a separate connection. The nested request excludes every object type except its explicit target, so overlapping tiles cannot start recursive board compositions. The viewer crops off the returned tile title bar and uses the browser body without starting a stream, changing the viewport, or writing a file. Each capture shares the outer render's remaining deadline and closes its connection on completion or cancellation. A delegated single-browser render fails if the selected viewer no longer owns the page. Offline drawing Macs and changed drawing identities fail rather than exporting retained stream frames as fresh. Viewer replies above easld's 64 MiB inbound line limit fail before transmission. An inline caller's complete response must also fit the daemon's 32 MiB output budget, including JSON escaping and metadata; otherwise the call returns `invalid_params` directing the caller to file output instead of dropping its connection.

Unseen-browser snapshots share a per-host admission queue in each viewer: at most two one-shot SSH links, with interactive requests before background requests and FIFO within a priority. Queue time counts against the original render deadline. Expired and cancelled queued requests open no link; cancelling an active snapshot preserves its sibling.

The remote viewer does not serve `view.snapshot`: a viewer-local scratch image would persist host content on the wrong Mac. With no other capable client, the host returns `unavailable` without creating an image. Local-board snapshots and explicit local exports are unchanged.

Delegated `agent.read` reads the attached surface's scrollback, not zmx history on either machine. Its `since: "prompt"` mark belongs to this viewer. If the marked context is gone or ambiguous after scrollback trimming, the reply returns the available tail with `truncated: true`. Command blocks use the surface's shell-integration log and stop before a command that is still running.

Mixed app and easld versions are normal during automatic updates. The compatibility baseline is the previous published release, not a matching schema hash. Both v0.3.0 and the current app use schema version 2.

- `view.render` `inline: true` returns the image in the reply as `data` (base64, in `format`, png unless `format` says jpeg) and writes no file; `path` is absent. `inline` with `out` is `invalid_params`, checked before the target. Remote tiles draw natively rather than fetching host-rendered tile images.
- `agent.prompt` `composer: true` is the user's prompt from a composer in another app. Both hosts accept `staged: Mention[]` in token order and a `viewer` identity, retaining the full targets rather than converting them to agent `PromptMention`s. Each target terminal gets its own queue and delivery IDs; the submission whose folded text matches takes its mentions, numbered from 1, never the tray or a hand-off. Peeks retain them and drains without `prompt` cannot claim them. The viewer withdraws the original chips without an undo step and retains them in memory until `composer.submitted` or `composer.returned` names their original IDs, terminal and viewer. Events contain no captured target content. `answer: true` passes the blocked check alone and accepts no staged mentions. `mentions` with `composer`, `answer` without `composer`, `staged`/`viewer` without `composer`, and composer `caller`, `from`, `when` or `force` are `invalid_params`. Schema version 2 makes this a clean cutover; agent-to-agent `mentions` are unchanged.
  A staged mention's `stagedAt` accepts seconds since 2001-01-01 or an RFC 3339 timestamp; `label` and `edited` remain required.
  `board.get {viewer}` includes `composerReceipts` only for that viewer; an unscoped manifest omits them. The host retains the newest 2000 committed IDs-only outcomes per board. Consuming fresh request-local staged IDs makes snapshot and live outcomes idempotent, so a late outcome cannot consume a later send's private hold. Closing a board returns queued remote mentions before `board.closed`; reopening in the same host process retains those return receipts. The viewer applies matching private outcomes even while its host board is closed or a refresh holds object events. Receipts and pending queues do not survive a host restart. A definite delegated refusal withdraws its queue. A transport failure after dispatch keeps the queue and returns an unknown submission outcome; neither host nor viewer retries the physical paste.
- **Prompt submission receipts.** `agent.prompt_epoch {}` returns this router lifetime's `promptEpoch`, separately from legacy `system.ping`. `agent.prompt` accepts `submission: {id, epoch, createdAt}`: an ASCII `sub_` id of 8–80 characters, that epoch, and an RFC3339 timestamp. Both hosts reserve the id before any awaited work or delivery. Identical repeats return the original success or refusal without delivering again; changed params under the same id are `invalid_params`. Only `reconcile` is excluded from that comparison. Legacy calls without `submission` keep their existing behavior.
  `reconcile: true` is a query, never a submission. It returns the original success, `delivery: "pending"` while the first call runs, or `delivery: "not-delivered"` for a confirmed refusal (with its `error`) or cancellation. Querying a valid id the host has never seen installs a cancellation tombstone before returning `not-delivered`, so a late original cannot execute. Missing receipts with another epoch, an age over 24 hours, a clock over 5 minutes ahead, or no free receipt slot are `delivery: "unknown"`, never permission to submit again. The registry holds at most 4096 entries, reclaims completed entries older than 24 hours when full, and never evicts pending work. A full registry refuses new execution before side effects. Known matching receipts replay even after their acceptance window.
  The remote composer generates one submission per target and sends the original once. After any lost or uncertain result, `RemoteReplayQueue` reconciles that same payload on reconnect; pending receipts are polled, while unknown receipts wait for another reconnect. “Delivery unknown, checking…” stays visible and the outgoing draft and mention origins stay held. Only a successful receipt marks “Delivered”; only a definite refusal or cancellation allows draft restoration. A query failure or malformed reply is not evidence of non-delivery. A host restart deliberately leaves an old epoch unknown: the in-memory receipt cannot prove what its predecessor delivered.
  Current receipts take precedence over a previous launch's unknown-outgoing warning. Dismiss hides only that previous warning in this window; it neither restores nor discards the held text, marks it delivered, nor suppresses later receipt checks. Each refusal is reported as soon as that target refuses, even while another target remains unknown. The first confirmed target records a prompt once in recall history; later targets cannot repeat or reorder it.
  The public host owns the receipt. Easld removes `submission` and `reconcile` before asking a typing client to deliver; that client cannot reconcile the host's epoch. An in-process Mac composer has no reply transport to lose and consumes no receipt slots. The same Mac's public API still reserves and reconciles receipt-aware calls.
  On a host whose `agent.prompt_epoch` reply is exactly `invalid_params: unknown method agent.prompt_epoch`, the composer uses the legacy `agent.prompt` request without a submission receipt. Sending remains available without an update notice. A successful reply clears the draft. A lost reply keeps v0.3.0 behavior: the send reports failure and restores the draft even if execution already happened. The app never automatically resends or reconciles that legacy request. A manual retry can therefore execute it twice. Other epoch errors and malformed successes do not select legacy delivery.
- Writes are the API's own: `object.update {id, frame?, props?, z?}` (`props` with the host `rev` the edit was based on, so a crossed edit fails `conflict`), `object.delete {id}`, `object.create {board, type, props, frame, parent?}`. Optional `viewer` and positive integer `step` must appear together on create, update and delete, and are refused inside `object.batch`. A viewer groups a gesture's writes under one step. `z` is an integer on both hosts; Bring to Front and Send to Back send those updates through the same path.
- `board.undo` and `board.redo` take `board?`, `viewer` and `step`. The host captures actual successful writes and their cascades, not viewer-supplied inverses. Each frame component, `z` and top-level content prop is guarded against the value that step wrote; concurrent replacements are kept. Restoring a deletion retains its id and order, uses a fresh revision, and refuses a key now held by another object. Replies carry current `changed` objects, `deleted` and `kept` IDs, the selected `step`, and `pushed` when an opposite step exists. Repeated transitions change nothing and return current touched objects, including all-kept transitions. A new accepted edit clears only that viewer's redo. History is memory-only, bounded to 16 viewers and 200 steps each. Receipt retirement never evicts a live step. A retired transition without a live match returns `retired: true`, the requested step and no effects; the viewer drops only that local step, with a notice, without replaying its private effects. Actual history evictions reject old step IDs with `conflict`. Viewer IDs identify windows across reconnects, not authorization credentials. Schema-1 hosts retain basic CRUD; updated viewers disable undo, restacking and staged composer sends until the host is updated.
  A rejected remote note edit keeps the user's candidate in a separate private recovery step. Undo and redo restore that text through revision-guarded host updates, not synthetic local object changes; a newer host edit refuses recovery without consuming the step. After a lost reply, an already-authoritative copy of the requested text completes the transition without another write.
- `board.get` includes optional `attention`, sorted by object id, with each marker's `id`, exact `raisedAt`, optional `message` and `raisedBy`. On schema-2 hosts omission means no markers; old hosts without a snapshot retain event-derived markers. The mirror installs the snapshot on opening and reconnect before replaying held events. `view.seen {id, rev?, marker?}` acknowledges a terminal revision and/or an exact marker `{id, raisedAt}` and returns `{seen, cleared, object?}`. Only an accepted acknowledgment whose supplied revision matched returns the canonical terminal object; the mirror advances a queued prop write through that acknowledgment's own revision, never a later agent edit. A newer turn or replacement marker is untouched; working and blocked terminals cannot be marked seen. Viewer clears and automatic seen acknowledgments use this method rather than a lifecycle write. A refused acknowledgment does not make the board offline.
- Terminals attach with `RemoteHost.terminalAttachCommand(for:board:merged:)`. Without `props.host`, the destination is the board host. Discovery supplies its zmx executable and GUI `TMPDIR`; custom homes and identified easld hosts use `ZMX_DIR=<server home>/zmx`, including easld on macOS. With `props.host`, the viewer connects directly to that target using the hosted terminal layout above. Both routes require the board host's owning home, derived from its socket's parent directory. Remote and hosted attaches share `HostedTerminal.ownershipAttach`. The home and tile labels must match, and the board label must name the current board or one of `board.get`'s optional `merged` IDs. The mirror reads that metadata before creating tiles. The shared script waits through missing sessions and labels during `agent.restart`; `SHELL=/bin/false` prevents a missing session at the final attach from starting a shell. Another owner's session exits `HostedTerminal.refused`, and the viewer holds its ownership notice without retrying. Transport failures show ssh's reason and retry after 2 s; clean detaches retry after 1 s. The viewer never falls back to a different destination. A host deletion, through events or a reconnect read, removes the tile and disposes its attach loop. The viewer reads no process, `zmx history` or notification of a remote terminal. Its lifecycle, title and markers are the host's, in props and events.
- A remote terminal's ⌘-clicked file references use `HostReferences` over the existing per-host SSH master. One host invocation resolves all wrapped-reference candidates, in order, against a valid OSC 7 directory, the matching labelled zmx session's cwd, `props.cwd`, and the board root. Bare names use the host's tracked and nonignored file index, with nearest-cwd selection and ambiguity refusal. The viewer parses terminal text but never lists or checks its own files. The host permits the board root and its same place in registered worktrees, refuses outside paths even when missing, and checks resolved containment with descriptor-relative no-follow access. Accepted paths open through `Board.openCode`; missing files show a host notice. Pytest bytes are bounded and returned in that same invocation. Option or Shift requests a separate code tile. Ghostty file URLs use the same resolver. No new schema method or host upgrade is required. A terminal hosted on a third machine uses only the board host's root and index.
  A valid OSC 7 directory takes precedence without running `zmx list`. Without one, session discovery keeps its 2-second bound. If discovery throws, times out, or exits nonzero, relative references return `unavailable` and the viewer shows "Host file lookup is unavailable"; they never resolve or rank from `props.cwd` or the board root after that failure. Absolute references do not depend on session discovery. A successful listing with no matching usable session retains the `props.cwd` and board-root fallback.
  A later absolute reading in the same wrapped reference can still resolve when an earlier relative reading is unavailable.
  The terminal's preview follows its provisional object onto the host's canonical id and revision. Later references re-aim that tile; a preview the user moved or kept before the create completed is not revived by the acknowledgement.
- Remote notes use `HostFiles.note(HostNoteRequest)` for excerpt text, symbol discovery, and image bytes. Host checks bind the note's selected source to the board's permitted worktree areas; an escaping root override grants no access. Live files use descriptor-relative no-follow reads. Pinned fences read regular Git objects and do not follow the live checkout's symlinks. A fence's commit wins over the note's ref. `NoteSource.interpret` applies the same anchor and proposal rules as local notes. Captions keep authored relative paths. Images use the live source or host temporary directories, require an image extension, and decode in memory; percent escapes and file-URL hostnames resolve on the host. ### Browser drawing machines

Every browser tile carries `props.drawingMachine = {id, host}`. Routing uses only `id`, the drawing Mac's persistent `client.attach.identity`. `host` is a display label retained with the tile for offline notices. `client.list` exposes both the persistent identity and the connection's distinct `cli_…` id.

A Mac-hosted board runs browser pages on its host, stamps that identity on new and imported browsers, and rejects API assignments to another machine or `null` until machine switching is supported. Easld assigns new tiles to the eligible Mac that creates them on its attached connection, otherwise the earliest eligible Mac attached to that board. The first eligible attachment fills existing missing values without bumping object revisions. Eligibility requires a persistent identity and `browser.call` capability. Repeated attach, focus changes, disconnect and reconnect never replace an easld tile's assigned identity.

On an easld board, only the matching Mac creates a real `BrowserTile` with its own `BrowserProfile`. Other viewers use `RemoteBrowserTile` to stream that page through easld. An unavailable drawer shows `Draws on <host>, which is offline`; no assignment shows `No drawing Mac yet`. `client.changed` carries a transient full `{clients}` snapshot for the subscribed board; a `client.list` bootstrap cannot overwrite a newer snapshot. Presence is not board data.

The drawing Mac answers `browser.call` with the existing typed cmux parser and page automation. `object.reload` uses the same page's reload adapter. Before validating a delegated page target, the viewer reconciles the preceding subscribed event prefix and snapshot objects deferred until its outstanding create replies arrive. It then returns `not_found` for a deleted target without waiting for a future creation; disconnect fails admission with `unavailable`. Calls do not wait on outgoing page reports. Both methods work from the retained canvas while its window is closed and background attach is enabled. Closing the window releases its live document; background commands recreate it from the saved URL in the same drawing profile. Neither method opens or activates a window. An in-flight action is never replayed after a disconnect.

Committed URL and title metadata return through `browser.report`, accepted only from the attached drawing identity for that board. URL commits retain agent, user or system credit; page titles are bookkeeping. The reporting process must give credit explicitly; SDKs do not fill its `caller` from the environment. The drawing Mac previews these observations without changing the object's revision. Reports queue without blocking delegated replies, and the mirror reconciles authoritative metadata after its queue drains. Other remote system writes and bookkeeping remain host-owned. Child pages inherit the drawing identity and profile; canonical IDs preserve popup views and `window.opener`.

On easld, `props.url` is observed page state; host-owned `urlIntent = {url, rev, actor}` records an explicit API URL assignment or URL-restoring undo/rollback, with its causal driver. Reports and unrelated edits preserve the marker. Caller-supplied markers are discarded at creation and ignored on update. Existing remote pages navigate only when the marker changes; fresh views load the current `props.url`, and released views retain a newly received intent until their web view returns. An observation acknowledgement, failed report, frame-only edit or reconnect snapshot with unchanged intent cannot navigate the page.

The drawing Mac keeps its own browser profile, cookies, page state and network requests. Localhost and file URLs refer to that Mac, not to the board host. Easld stores ordinary URL, title and drawing-machine props, not page bodies, screenshots, cookies, page logs or profiles. Browser command results pass through memory. An offline move explicitly confirms reloading the last saved URL. A failed online read aborts; it never silently uses stale metadata. The new Mac reloads in its own profile without copying cookies, logins, or unsaved state, and old streams end. Other tiles, including child pages, keep their assignments. Mac-hosted boards show their host but do not yet support moving drawing to a viewer.

### Remote browser streams

The drawing Mac owns the existing `WKWebView`, its network requests, and its browser profile. The viewer and agents act on that same page. Cookies, credentials, storage, and profile files stay on the drawing Mac. No profile is synchronized or recreated on a streaming viewer. A Mac host serves directly; easld relays the same methods and private event envelopes to and from its exact attached drawing Mac.

The `surface.*` methods on the easl API are distinct from the cmux subset above. Their wire types and validation live in `schema/easl-api.json`.

- `surface.stream {id, scale?, format?}` opens a connection-owned stream and returns `stream`, `size` with `w` and `h`, and `scale`. Scale is at most 2. Raw clients retain full JPEG quality 0.8 by default or explicit full PNG. Native viewers request `h264`. The fastest of the first three decoded motion acknowledgements selects JPEG below 40 ms, avoiding cold-decoder bias. Otherwise motion uses predicted H.264. This choice measures the link, not whether it is direct or relayed. Decoded images remain capped at 4,000,000 pixels.
  - An H.264 payload is an `ESV1` packet inside base64 `data`. Its header contains four ASCII magic bytes, one flags byte with only bit 0 for a keyframe, the NAL-length byte `4`, and big-endian UInt16 SPS and PPS lengths. SPS and PPS precede one complete AVCC access unit. Motion packets are at most 48 KiB. Oversized unpublished motion candidates reset the encoder and retry at smaller even dimensions with a fresh keyframe. JPEG uses one quality-0.8 encode at its original dimensions. The encoder, native wire parser, and shared image decoder retain the 16 MiB full-image bound for JPEG and explicit PNG.
  - Each stream has one published video prediction chain. After one second without input or a change to more than 1% of pixels, a worker encodes one native-size high-quality H.264 refresh. Later small changes predict from that sharp reference. The initial link probe does not pay for high-quality codec setup. Consecutive capture comparisons stop once changes exceed 1%. Smaller changes do not restart the settle clock. Comparison against the refresh's frozen source capture re-arms settling once cumulative changes exceed 1%. JPEG mode does not produce idle refresh.
  - Encoders set the maximum keyframe interval to `Int32.max` and its duration limit to zero. New streams, missing references, decode recovery, size changes, and settled refreshes require IDRs. A sharp-session IDR uses `refresh:true` and the 576 KiB bound, including a size-change IDR outside the settle worker. It never retries through the 48 KiB motion-quality fallback. VideoToolbox permits earlier keyframes despite its interval setting, so this reference handling also covers an encoder-generated IDR.
  - A stream retains at most one warm motion session and pixel pool while its sharp reference is active. A large pixel change during input resumes motion without first encoding an oversized sharp candidate. The first resumed frame requires an independent IDR with minimum QP 42. Later motion retains its 2 Mbps target and minimum QP 35. Small input changes keep the sharp prediction chain. After large input settles, the worker restores a sharp reference.
  - `refresh:true` requires `format:h264` and marks one complete `ESV1` packet of at most 576 KiB. Native-size video rounds each dimension up to an even number with a minimum of 16, padding the bottom and right edges instead of resampling. The decoder crops native-size refresh and later predicted output to the original `canvas {w,h}`. Input coordinates remain page points. Ordinary H.264 packets remain bounded to 48 KiB. The real-page quality target is maximum RGB channel error at most 8 and mean at most 1. Documentation must meet it after settling and at every one of 200 caret transitions. A GitHub file view and a dense table must meet it after settling and through 30 caret transitions at actual tile dimensions. These are qualification requirements, not passing measurement claims. Saturated synthetic rasters report error numbers but do not gate quality.
  - H.264 capture fitting reserves the encoder's even dimensions and 16-pixel axis minimum within the 4,000,000-pixel budget. It preserves odd and tiny capture dimensions when coded padding fits, and reduces dimensions only at the padded budget boundary. Capped viewports therefore remain eligible for a sharp reference. JPEG and PNG retain their original capture fitting.
  - `SurfaceRefreshTransmission` sends one 16 KiB chunk and waits for its `surface.progress` receipt before sending the next. Each part carries the same sequence and metadata, plus `offset` and `total`. Offsets start at zero and increase by 16,384. Total is 1 through 589,824 bytes. Part data is exactly `min(16384,total-offset)` bytes. Normal frames omit both fields. Parts are fragments of one H.264 packet, not separate images or pixel regions.
  - `SurfaceRefreshAssembly` validates bounds, alignment, lengths, and constant metadata before retaining part bytes. It accepts ordered parts and returns no image until the entire packet is present. A newer sequence replaces an abandoned assembly only at offset zero. Input, reconnect, and close reset partial state. The viewer filters stale parts before assembly and serializes decoding off-main. It presents actual decoded H.264 pixels, without a separate sharp raster or block copying. Only the accepted stream generation and outstanding frame credit can install an image or acknowledge it.
  - `surface.progress {stream,frame,offset}` receipts a validated chunk on the opening connection. It releases at most one further chunk, never frame or decode credit. Duplicate receipts do nothing. Unsent and misaligned offsets are invalid. A receipt for a superseded refresh does nothing. Only the complete decoded and installed logical frame receives `surface.ack`; the final chunk receipt is optional.
  - Input cancels pending refresh work and retires its logical frame credit without waiting for receipts or decode. The next frame's `supersedes` names the first sequence in the consecutive canceled-refresh range ending just before that frame. Published motion frames cannot be superseded. A canceled H.264 decode may already have changed the receiver's prediction state. The viewer abandons that decoder and never acknowledges canceled work. The sender resets after canceled, oversized, or otherwise unpublished reference output, so the next video frame independently recovers with an IDR. No later motion is encoded against a pending refresh, and published refresh blocks later captures until final decode acknowledgement or input cancellation. Any other sequence gap, malformed packet, or decode failure opens a fresh stream without input replay. Unchanged images send nothing. Large pixel changes cancel stale refresh results.
  - Both drawing-Mac writers check refresh cancellation before the first write of a queued line. Easld removes only queued refresh chunks on the same board and stream within the incoming frame's `supersedes` range. It commits one line at a time. Neither hop removes a published motion reference or interrupts a partial line. One chunk plus its JSON and base64 envelope can already be committed when input arrives. The delegated drawing-Mac connection permits 32 MiB of queued work plus one legal 64 MiB delegated reply and its newline: 96 MiB plus one byte in aggregate. Easld retains its 32 MiB outbox bound.
  - An encoder rate-control drop is an uncoded capture, not a missing protocol frame. It retains credit and the last presented input fence, publishes no frame, and advances no frame sequence. An oversized refresh is refused until a large change, and its unpublished reference is reset before bounded motion continues. Large input pixel changes re-arm a delivered refresh but do not retry an oversized refresh in the same large-change epoch. A dropped decoder output remains a decode failure. Codec creation failure closes the stream without a silent fallback. Retired compression sessions complete pending frames before invalidation on a utility worker.
- The same connection subscribes to `surface.frame` on the canonical board. Frames, `surface.dialog`, and `surface.notice` are private to the owning subscribed connection, never `BoardEvent`s or broadcasts. Other connections cannot operate that stream.
- Easld records the opening viewer, exact drawer attachment, board incarnation, tile, assignment, and private-event hearing, never frame or input payloads. It forwards encoded events only from that drawer to that viewer, without decoding images, acknowledging frames, or broadcasting. Event hearing is captured at open; reopen to use subscriptions added later. A drawing change, board or tile closure, drawer replacement, or either connection ending retires the stream. A late open is stopped rather than orphaned. Reconnect opens a new stream and never replays input.
- Before forwarding, easld bounds each request's conservatively estimated slash-escaped payload to 24 MiB. Requests above that cap return `invalid_params` before reaching the drawing Mac. File answers also enforce the decoded upload budget before encoding. This is a per-request bound, not an aggregate reservation: concurrent traffic still shares the producer's 32 MiB outbox. A producer that falls behind that aggregate limit is disconnected under the ordinary socket backpressure policy; its viewers reconnect without replaying input.
- Initial outstanding frame 0 grants no capture credit. `surface.ack` for frame 0 grants the first frame and releases private setup events, so they cannot outrun the open reply or easld route registration. The drawing Mac bounds that queue to 32 events and 256 KiB; overflow ends the stream. Thereafter one active frame may remain unacknowledged and acknowledgements never accumulate credit. Input may retire an idle refinement's credit, but never motion credit. The viewer decodes off-main, installs the image, then acknowledges it; stale acknowledgements grant nothing. An acknowledgement failure closes the dedicated connection.
- `surface.input {stream, events}` accepts 1 through 128 events and validates the whole batch before mutation. Positive sequence numbers increase within a batch. Already accepted sequence numbers are ignored. The result's `accepted` counts newly queued events, not delivered events. If page relay setup fails during delivery, the drawing Mac closes the stream with a notice instead of silently discarding the batch. A pending relayed JavaScript alert, confirm or prompt is not a setup failure: its answer must remain with its viewer. Reconnection never replays accepted input.
- Input kinds are left-button `mouse`, `scroll`, `key`, `text`, `compose`, `unmark`, `focus`, `command`, and `navigate`. Commands are `copy`, `paste` with explicit text, `selectAll`, `back`, `forward`, `reload`, and `stop`. The parser supports scroll phases; the current viewer sends phaseless scrolls. Mouse-up and drag retain the mouse-down view.
- Input runs inside `NSApp`'s own event queue, including native marker callbacks. No system input events or TCC input permissions are used. Mouse and key processing SPI plus an actual presentation callback govern the frame's `input` watermark. Missing processing SPI leaves the watermark pending and sets `surface.fence.unavailable`. An unconfirmed mouse or key remains pending across batches, so a later key cannot jump over a timed-out mouse. Direct text, scroll, and commands use the app queue; there is no wheel-processing SPI.
- `surface.answer` completes a pending JavaScript alert, confirm, prompt, HTTP authentication, main-frame select, or file dialog. Without a dialog listener, the host dismisses or refuses instead of showing a host sheet. The host sends no proposed username. Authentication refusal and certificate cancellation use `cancelAuthenticationChallenge`.

Passive host scripts run without a user gesture, so they neither grant nor consume page activation. Explicit browser automation retains WebKit's forced-user-gesture execution. A drawing Mac whose WebKit lacks the activation-preserving script API returns `unsupported` for new streams, with no forced-gesture fallback.

Downloads remain on the drawing Mac and produce a notice. Streamed main-frame file inputs intercept a user-activated click before WebKit opens a native panel, then open a picker on the driving viewer. A click without active user activation cannot open the viewer picker, even if WebKit marks it trusted. Selected files travel in `surface.answer.files`, from 1 through 32 files and up to 8 MiB total decoded bytes, and become in-memory `File` objects on the exact initiating input. An accepted selection cannot be empty; zero-byte files are allowed. No file is staged on easld or the drawing Mac. Navigation, replacement of the input, or stream closure invalidates the picker. Navigation sends the owning viewer a private `surface.notice {kind:"dialogClosed", dialog}`; it marks the dialog handled before dismissing its sheet, so neither a late picker callback nor a completed file read can send its answer. Success dispatches untrusted `input` and `change`, without a native cancel; viewer cancellation dispatches untrusted `cancel` and preserves the previous selection. Direct native picker fallbacks, folder uploads, file inputs in frames, media permissions, client certificates, and external-app links remain refused. Popups become ordinary browser objects with their own streams. Main-frame select is supported; iframe select remains limited.

Page-body Copy reads selected plain text through a bounded host JavaScript helper, never the host pasteboard. Password inputs copy empty text. Its success is independent of an unavailable native input fence and does not advance an unconfirmed watermark. Without key-processing SPI, a copy immediately following queued keyboard-selection changes can observe the earlier selection. Paste sends explicit viewer text. Page-body clipboard writes are user-directed and marked `currentHostOnly`, transient, and concealed. Native address and dialog field editors retain AppKit's clipboard behavior. Rich clipboard is unsupported. There is no cut command; viewer ⌘X refuses with a copy-then-delete notice so a timed-out copy cannot silently delete text.

The viewer uses only `NSImage` and `CGImage`, with no browser `WKWebView`, profile, page network requests, or browser storage. Page, frame, and credential content is not written to viewer files or logs. Explicit clipboard and export actions remain user-directed and follow the remote board's privacy markers. Leaving the live view or closing the window ends the stream, releases held input, and closes its connection. Reconnect never replays input. Unsupported or `invalid_params` stream opens do not retry. A notice clears on subsequent substantive input. Queued sheets retain their parent for dismissal.

A connected stream keeps its host page driven even with no frame credit. Closing the last stream resumes the normal 60-second driven-page grace period and subsequent release policy. An interrupted input request closes and reopens the dedicated link, shows a notice to check the page before repeating the action, and never retries that batch.

The `browser-surfaces` conformance scenario covers direct connection ownership, initial acknowledgement credit, sequence deduplication, batch validation, and dismissal of dialogs without a listener. `client-surface-relay` covers relayed methods, frame-only hearing, private delivery, forged event sources, independent viewers, and retirement after a drawing move.

Agents open one with `board.open_remote {host, board, select?}` (the Mac app only; easld answers `unsupported`), through File › Open Remote…'s own path (`AppDelegate.openRemoteBoard(named:board:select:)`):

- **The host** is found among the picker's rows (`RemoteHost.target` over `RemoteHost.candidates`: the hosts in `remote-hosts.json` and the tailnet's online Macs): the row whose ssh target `host` is, else the one row with that name, else `host` as an ssh host typed into the picker (`RemoteHost.typed`: `user@host` goes by `host`). A name two rows have is `ambiguous`, listing their ssh targets. `host` is one word that doesn't start with `-` (ssh would take it for an option), with both parts when it has an `@`, and `board` a board id (`brd_…`), else `invalid_params` before anything runs; the clients never fill `board` from their own board (the schema's `unfilled`).
  Host targets also reject shell metacharacters and a host component starting with `-` after `@`. Hosted viewer attaches use the same boundary. This avoids hostname expansion into local shell commands through older SSH clients' configuration.
- **Already open.** Resolve the saved server address before any lookup or discovery. A window at that SSH target, server socket and board answers immediately, selected when requested. A named open with several saved homes is `ambiguous` unless the dev override selects one of them. A missing legacy home uses the dev override, otherwise the default. Without a saved board entry, use the dev override or the recent server home. This resolution does not depend on background attachment finishing first.
- **Otherwise.** Discover tools at the resolved home, remember the host, read the board through `BoardMirror.load`, and open its window through `openRemoteBoard(host:board:select:)`. With `EASL_DEV_REMOTE_HOME` set, discovery refuses the host's default server before opening a relay. Only `select` brings the tab forward; an unselected separate window is ordered behind other windows, never made key. Discovery failure is `unavailable`; an unanswered socket is `unavailable`; a server with no such board open returns `not_found`.
- **The result**: `host` (the tab's name for it), `sshTarget`, `board`, `root` (the host's), `title` (`<root's name> @ <host>`), `window` (the tab's window number) and `alreadyOpen`. `remote-hosts.json` changes on disk, as with the picker, and an easld board's `remote-boards.json` entry, with its home.

## Drawing layer

`.shape` and `.arrow` objects use individual `DrawnItemView` siblings in document coordinates, interleaved with tiles by `(z, id)`. `ShapeLayer` (`Sources/CanvasApp/Drawing/`) owns their cached geometry and routing, hit tests, tools, resize handles, and editors. Its overlay paints only gestures, handles, and editors above the object stack and below the Hyper outline. Core geometry lives in `Sources/CanvasCore/Drawing*.swift`. Selection and moves belong to the scene (see Scene seams).

- A shape's `frame` is exactly its drawn box (no title bar). Ink `points` are relative to the frame origin; the frame is the painted stroke bounds.
- An arrow's route is derived, never stored: bound ends attach to the facing edge of the bound object's current outline (a tile's frame, a shape's frame, the curve of an ellipse), so arrows follow moves and resizes without writes. An end bound to a `node` of a diagram tile attaches to that node's box as the tile draws it (`DiagramLayout.canvasRect` in the model, `DiagramTile.rect(ofNode:)` live; the tile posts `DiagramTile.laidOut` when its nodes move and the layer re-routes); a node the graph no longer has binds the whole tile. An end bound to `lines` of a code tile is a row end (`ArrowEnd.row`): it attaches to the tile's left or right edge (right unless the other end lies wholly left) at the first visual row of `lines.start` (wrapped lines above it push it down), `CodeMetrics.lineY`: live, the tile's rows as scrolled (`CodeTile.lineY`; the tile posts `CodeTile.rowsMoved` and the layer re-routes), and in the model (`BoardGeometry.routes`, `layout.check`) the tile freshly aimed by `CodeMetrics.scrollOffset`, the same rule `CodeTile` scrolls by (range start with up to 3 rows of context, fewer when the viewport can't show them and the range). A line out of view clamps to the top of the rows or the bottom of the tile. Orthogonal routes with a row end leave sideways, looping around the right edges when the two tiles overlap horizontally; `avoid` uses only the two side ports and keeps its row. `lines` on other tiles binds the whole tile. `DrawingGeometry.path` (CanvasCore) routes one arrow by `props.route`: `straight`, `orthogonal` (one jog between facing sides), or `avoid` (alone, the router below with one connector). Straight and orthogonal arrows bound to the same two objects in either direction get `parallelOffsets` (`parallelSpacing` apart, relative to each arrow's direction, so opposite arrows take opposite sides). A board's `avoid` arrows route together (`ConnectorRouter`, docs/design.md "Arrow routing"): an orthogonal grid search around every object `BoardGeometry.blocksRoutes` (tiles, text, filled shapes, keeping `avoidMargin`) that picks each end's side by the flow of its group (`GroupProps.flow`, else the way arrows between groups point), then distinct ports for arrows sharing a side, crossing-aware routes, and parallel tracks for arrows sharing a channel, off group borders and title bands. Every arrow's label (all route styles) is placed with the rest (`ConnectorRouter.placeLabels`): beside its own route where nothing else is, else on it, else a short leader away (`ConnectorRouter.Label.leader`, drawn dashed). The caption is `label`, else `relation` in the secondary color when `label` is absent; `label: ""` draws none (`DrawingStyle.arrowLabel`). The layer draws, hit-tests, and selects the routed polyline; `BoardGeometry.routing()` computes the same routes and labels from frames for `layout.check` and detaching, routed on from the layer's last routing (`Board.settledRouting`). An arrow's `frame` records its route bounds when it was drawn. Free ends (`{"point": [x, y]}`) are board coordinates. Deleting a bound object turns that end into a free point where it last attached, in the delete's undo step, so the arrow keeps its direction and its other end keeps following.
- The frame the API reports for an arrow (`board.get`, `object.get`, create/update results, `board.history` summaries; `Board.reported`) is the bounds of its routed line: as drawn (`Board.arrowPath`, supplied by the drawing layer), else routed from object frames (`BoardGeometry.routes(only:)`). The drawing layer routes the board once per burst of changes, off the main thread (a change the API made: once the API is quiet, `ApiActivity`), holding a new or changed `avoid` arrow on a provisional line until then; `Board.reported` first has it route the board when such an arrow is pending (`Board.settleArrows`), except inside a step, and `object.batch` reports its arrows' frames once its step has closed, so a create result is the route drawn, around tiles later ops of the same batch add. An arrow that only moved with its ends (a tile it binds written mid-burst) reports the line it follows them on, alone, until the burst's routing places it with the rest. The stored frame of an arrow with a bound end is a meaningless placeholder.
- When a viewer opens a saved board, its snapshot arrows initially draw attached previews while the board routes in the background. Initial reads report those currently drawn preview bounds until the final routes land. Creating or editing an arrow still settles its route before reporting it. Explicit exports also settle snapshot arrows before choosing image bounds.
- The layer never takes keyboard focus (it stays with the prompt-target terminal); tool keys V/R/O/A/T/P/Esc arrive as key equivalents and only act when no terminal or text view has the keyboard. Inline text and arrow editors take focus while open and give it back on Enter/Esc/click-away, never over a responder that took focus meanwhile. The text editor (`ShapeTextEditor`) commits on Enter, Esc, and click-away (an emptied text shape is deleted; the arrow caption editor's Esc cancels), and draws a steady caret itself in a window that isn't key. A text shape's size follows `TextShapeLayout` (CanvasCore): a frame exactly as wide as its grown text keeps growing up to `autoWidth` (320) × `textSize` as it's edited, any other width is its wrap width. An arrow end binds to the topmost overlapping shape or tile, with the shape hit tolerance applied. Otherwise it binds to the nearest shape or tile within `ShapeLayer.arrowSnap` (16 screen points), with `(z, id)` breaking equal-distance ties.
- Only strokes, text, labels, and fills (`fill: semi|solid`) take the mouse; an unfilled shape's interior passes clicks to the tiles beneath.

A board's tab shows `NeedsYou` (CanvasCore: blocked beats done, nothing for working or idle), refreshed by the window controller on terminal updates. ## Undo

On a remote board, ⌘Z and ⇧⌘Z use the host-owned, per-viewer guarded history described under Remote boards. Private tray steps remain local. Board-changing remote steps never run `Board.undo()` against the viewer's snapshot. The following describes local-board history.

`Board.history` records every create, update, and delete from any actor; ⌘Z (`Board.undo()`) reverts the latest step even when an agent made it, never silently: each step (`UndoHistory.Step`) records its author (the agent when an agent made any of it, else the user), `Step.summary` says what it did by verb and object type (`created 9 code tiles, 6 arrows; moved a note`: updates of objects the step created or deleted are part of that; a group re-fitted or an arrow re-routed is left out beside anything else), and `Step.title` names it for Edit ▸ Undo/Redo (`Undo Create 9 Code Tiles, 6 Arrows (omp)`, the author by `Board.authorName`: the terminal's `name`, else its agent's kind). Every undo or redo shows the board notice for 4 s (`Step.notice`, `CanvasView.showNotice`, also announced to VoiceOver): "Undid moved a note · ⇧⌘Z redoes", with the author for an agent's step ("Undid omp: … · ⇧⌘Z redoes") and an `UndoEffect`'s name for a change to the files or git index ("Undid Stage of src/regex_helper.rs · ⇧⌘Z redoes"); an effect's name leads `Step.summary` and `Step.title`. ⌘Z and ⇧⌘Z stay with a terminal holding the keyboard (Edit ▸ Undo/Redo disabled then). Navigation's re-aims are never steps (`Board.reaimForNavigation`: Go to and links through `Board.openForNavigation`, a terminal's ⌘-click preview through `Board.openCode`, a follow tile's history strip). Every undo or redo is a new revision, newer than any the object ever had, even across a delete and re-creation. Bookkeeping nobody chose is never an undo step and never rewound (`UndoHistory.bookkeeping`, `Board.unrecorded`, `Board.writeBookkeeping`), so ⌘Z reaches the user's last own action through an agent's work: a terminal's `lifecycle`, `agent`, and `title`; a browser's `pageTitle` (the page's own title; `title` is the creator's and stays undoable); a follow tile's `path`, `range`, `lastAction`, and `history` (every `follow.report`), and the follow tile appearing; and every update the app writes back as `system` (a note's resolved `anchor=`). An undo of an earlier step keeps them as they are now (a moved follow tile goes back, still aimed where its agent last looked), and undoing a terminal's creation takes its follow tile along. Multi-object gestures wrap their updates in `Board.transaction { }` to form one step; API writes that must succeed or fail together (`object.batch`, `layout.*`) use `Board.atomically { }`, which also rolls back on error. Repeated updates of one object within a step collapse into one recorded change (first before, last after), never across an `atomically` mark. Undoing a delete restores the object with the same id and `z`; staged mentions of it are not restored. When undo/redo removes a terminal and later brings it back, it returns with the bookkeeping it last had. History lives in memory only. A step can also carry an `UndoEffect`, a change outside the board run on undo and redo (a changes tile's `git apply`, see "Changes tiles"); its slow work runs in a task of its own, so undo itself never waits on git.

## Note fences

A note's `markdown` is plain markdown; the code fence info string selects how the tile renders a fence (parsed by `NoteFence` in CanvasCore):

| Info string | Renders |
| --- | --- |
| `ts file=src/app.ts#L10-40` (`#L10`, `#L10-L40`; no range = whole file) | Live excerpt of the file with line numbers |
| `ts symbol=restoreSnapshot` / `swift file=Sources/Board.swift symbol=Board.update` | Live excerpt of the declaration (best-effort, language-agnostic; `Outer.inner` searches inside `Outer`; without `file=`, the first tracked file that declares it) |
| `… file=src/app.ts@1a2b3c4#L10-40` | Excerpt pinned to a commit (`git show`) |
| any anchored form plus `propose` | The fence body as a diff against the resolved range |
| anything else | Free-written (authored) code; `path:line` references in it open code tiles |

Anchor resolution (`NoteAnchor.resolve`, shared with code tiles' ranges), in order: a symbol that resolves wins (`Outer.inner` searches the whole extent of `Outer`, however long; the declaration's own range stops at 400 lines; a signature's parameter list, over several lines, and braces inside it open no body, so Python's `) -> T:` line is followed by its indented body); otherwise the line range is re-found by the text the tile captured when it first resolved it (when that opens with the fence's `anchor=`, else by the `anchor="first line text"` alone), preferring the candidate whose following lines match best and the written position on ties; with the first line gone, by most of the captured text still standing together; else by the fence body (a proposal's own lines vote for where they sit). Captured text also carries the range's end: the shortest stretch from the start keeping as much of it as a generous window does, so lines inserted or removed inside the range move its end with them (lines gone from its end leave it shorter, unless a line reads like the one it replaced: the next one, or one after up to 4 lines written with it, such as comments ahead of a fix, before any blank line; the range then covers them all); with only an anchor (after a restart) the range keeps its written length. A range that moved or changed length renders with "was L…"; one that can't be found renders a **stale** badge over the last text it showed.

A `propose` fence whose body the file already reads, contiguously and overlapping the resolved range (anywhere in the file when the anchor is lost, for a body of two or more lines or one found once), is **applied** (`NoteAnchor.applied`): it renders the file's lines with a quiet "✓ applied" and no diff. Not while the range's original text (captured, else the range as written) still stands whole around it: a proposal that only drops lines reads as part of its range until it is applied.

`object.get` on a note adds `fences`: per anchored fence (fences with the same info string are one), its `info`, `markdownLines`, `path` (as found by a symbol search), `symbol`, `commit`, `propose`, and `AnchorStatus`: `state` (`live`, `relocated`, `stale`, `applied`, `missing`), the resolved `range`, the `written` range when relocated, and the stale `reason`. The note tile resolves them against disk at that moment with the text it captured (`ApiRouter.noteExcerpts`), and shows the result; without a tile they resolve from the markdown alone. A note that isn't live watches nothing, so `view.render` of it resolves every fence first too; a live note with nothing pending draws what it resolved.

The tile writes anchors back: when a line-range fence without `anchor=`, `symbol=`, or a pinned commit first resolves, it appends ` anchor="<first line>"` to the fence's info string in one `object.update`, so anchors survive restarts and agents see them. It skips first lines that can't be written (blank, or a backtick inside a backtick fence) and falls back to the in-memory capture. `commit=` must name a revision (`abc1234`, `HEAD~2`, `v1.0`); anything shaped like an option makes the fence stale.

Automatic anchor capture on API create/update and the Mac tile's write-back uses the board root and its same subdirectory in registered worktrees. A source-root override must itself lie in a permitted area. Absolute paths and traversal that leave those areas, escaping live symlinks, and committed symlink entries are refused. Live reads open a checked regular-file descriptor without following symlinks; pinned reads use the requested Git blob regardless of live symlinks. `object.get` reports a refused fence as `state: "stale"`, `reason: "path refused"`, without a resolved range. The local Mac tile may still display an explicitly named outside file, but cannot copy its text into an automatic anchor.

When loading a saved board, both hosts remove every `anchor=` attribute on a policy-refused excerpt or proposal fence. The attribute is host-generated metadata, separate from authored prose and fence bodies, which stay byte-for-byte unchanged. Saved metadata has no provenance marker, so explicitly supplied anchor attributes follow the same rule. Allowed anchors remain unchanged, including anchors for missing inside files. Scrubbing changes no object revision, timestamp, undo step, or activity. An unchanged second quiet load performs no scrub save. easld persists the cleaned snapshot before serving it and propagates a scrub-save failure without opening the board. The Mac keeps best-effort persistence.

Mac board loading is asynchronous. Disk reads and filesystem policy checks run off the main thread. The board publishes without anchor metadata requiring ref or pinned-commit Git checks, so tiles and API reads do not wait for those checks. Allowed metadata returns as bookkeeping only if its carrier is unchanged; authored edits win. Restoration advances the board cursor and emits safe object updates without changing object revisions or adding undo steps. Local and host-owned viewer undo/redo snapshots receive the same authorized metadata. Ref SHA observations wait until the anchor check settles, then persist as ordinary bookkeeping. With no other user or bookkeeping save, the load persists only the normalized original snapshot; saves and closes during the check retain recoverable stored anchors on disk, never in API replies. Late checks cannot overwrite a saved or closed replacement board.

Hyper-click on an excerpt or proposal row mentions `code` (object = the note, the row's real path and line, and `commit` for a pinned fence; an added proposal row mentions the line it would be inserted before, or the file's last line when appended at the end of the file). Any other rendered paragraph mentions the markdown block it came from (`MentionTarget.note`, found by `NoteItem.at(line:in:)` from the paragraph's `.noteMarkdownLine`): the innermost list item containing it (with its nested items), else its outermost blockquote, else a fence, table row (the delimiter row stands for the header), or paragraph; a top-level heading takes its section, up to the next heading of the same or a higher level. The target carries the block kind, its heading path (top-level headings above it, levels may skip), its lines, and its markdown as it read (common indentation removed, cut to 40 lines and 2000 characters). The title bar, margins, blank space, and thematic breaks mention the note (`object`).

Code mentions carry the commit their lines are read against (`MentionTarget.code.commit`, schema `MentionTarget`): with `side: old` or no side, the commit whose version of `path` holds the lines (peeked base rows, deleted files, pinned excerpts); with `side: new`, the base the working-tree lines were diffed against; absent, the working tree. The context line names it from the mention alone, never from what the tile shows at drain time: `· diff vs merge-base 1a2b3c4` (the kind word comes from the tile's `diffBase`), `· diff vs merge-base 1a2b3c4, old side` for peeked base rows with the excerpt read by `git cat-file blob <commit>:<path>`, and `· at 1a2b3c4` for a pinned excerpt without a side. `tray.drain` is therefore asynchronous.

Link roots (`LinkRoot.swift`; with `props.ref`, see Branch-anchored tiles): a note's relative paths (fence `file=` paths, `path:line` and markdown links, `![alt](path)` images) and an HTML tile's (`code.excerpt`, `code.open`, `<img>`) resolve against the tile's `props.root` (absolute or board-relative, like a changes tile's `root`), else the board root. `object.create`/`object.update` accept only an existing directory in the board's checkout or another worktree of its repository (inside the board root for a board outside git; `invalid_params` otherwise; empty or null clears it). An agent working in another worktree of the board's repository than the board root's (`caller` a terminal; its directory is where its foreground program, else its shell, works, else `props.cwd`) writes paths relative to its own checkout, the board root's place in that worktree (`Board.callerCheckout`, applied to `object.create`, `object.update`, `object.upsert`, batch ops and `object.measure` by `Board.inCallersCheckout`): a note or HTML tile it creates without `root` gets that checkout as `root`, so it writes `tests/x.ts:16` instead of `../wt-x/tests/x.ts:16`; a code, image or diagram tile's relative `path` is stored absolute in that checkout (not a code tile's with `ref` or `pinnedCommit`: those name the repository path); a changes tile it creates without `root`, `ref` or `head` reviews that checkout. The board's own checkout's agents, the user and calls without a caller keep board-relative paths. Anchoring, `size: "fit"` and `object.measure` use the same root. A link opened from the tile names its file as the API stores paths (board-relative under the board root, else absolute).

## Git

All git in the app runs through `GitRunner.shared` (CanvasCore), which caps concurrent git processes at two, can cap stdout (`maxOutput`) and run time (`timeout`), feeds stdin (`input`, e.g. a changes tile's patch for `git apply`), stops git when the calling task is cancelled (a request still waiting for a slot just leaves the queue), and sets `GIT_OPTIONAL_LOCKS=0` so reads never contend with agents for the index lock, and `GIT_NO_LAZY_FETCH=1` so a partial clone's missing object is never fetched: easl's git never goes to the network. The only writes are a changes tile's Stage (the index) and Revert (working-tree files), each on the user's click or key, inside the tile's repository. Git, file reads, and parsing run on GCD (`offPool`), never blocking a Swift concurrency thread. Code tiles diff through `GitDiffEngine.shared`: live tiles `retain(containing:)` their repository and `release` it when they go offscreen or away; held repositories keep resolved bases and an FSEvents stream that posts `Notification.Name.gitDiffBaseChanged` (object: the repository's top-level path) when a commit, checkout, rebase, or fetch moves a base.

## HTML tiles

- Each tile's page is `canvas-kit://html/<tileId>`, served by the tile's own scheme handler: the kit head (`resources/kit/canvas-kit.css`, `canvas-kit.js`, `vendor/tailwindcss-browser.js`) followed by `props.html`. `/kit/…` serves `resources/kit` (Mermaid loads from there only when a page has diagrams). DOM mentions of HTML tiles use that URL.
- Board assets: every non-kit path can serve a board file, independent of its extension. `fetch('data/series.json')`, CSV, script and stylesheet files, fonts, images, audio and `<video src="clips/demo.mp4">` resolve under the tile's link root. Authorized absolute paths may name permitted board areas. The handler uses `HostFiles` on remote boards and the same no-follow policy from disk locally. Temporary-directory fallback is image-only. `/kit/…` is reserved, and HTML `file:` URLs are blocked. Native video paths bypass URL-path normalization and enter the same host-file policy directly.
- GET and HEAD advertise byte ranges. Closed, open-ended and suffix ranges return exact 206 selections; unsatisfiable or malformed selections return 416. File reads are at most 1 MiB each. Media read-ahead retains at most four 1 MiB blocks per handler to avoid an SSH process for every small container-header read; a new page or changed dependency clears them.
- Video path and poster file-URI references survive caller-worktree normalization and repository-board adoption unchanged, then pass through the normal host-file authorization policy. Both rewriters share their relative-reference classification; empty and `~`-prefixed values are not turned into checkout paths. A refused file URI never becomes a relative checkout shadow.
- Non-file URLs are unsupported in video `path` and `poster`; normalization can treat those strings as relative filesystem paths. Use HTML media for allowlisted HTTP(S) resources.
- Loaded files are dependencies. A metadata change reloads the page after a short debounce, not the tile or board. A missed transport probe preserves its baseline and retries at the existing cadence rather than restarting playback. Polling is live-only and can coalesce edits; the interval excludes host latency. Code and images continue to use their existing policies and native channel.
- Export (the object menu's Save as HTML… and Open in Browser, `HtmlTile.exportDocument`): the page loads offscreen as for `view.render`, and once settled its DOM is serialized with each `<img>` inlined as a `data:` URL, the kit stylesheet inlined, and every script removed (Tailwind's generated styles, `<canvas-code>` rows and Mermaid diagrams are already in the DOM), so the file opens anywhere. Open in Browser writes it to `$TMPDIR/easl-exports/<tileId>-<title>.html` and opens it with the default browser (with `EASL_NO_ACTIVATE` it only logs the file).
- Sandbox: every tile uses a nonpersistent website data store. Local boards retain the content-rule allowlist for `http(s):`, `ws(s):` and the fixed `file:` block. `allowNetwork` accepts `host`, `host:port`, and `*.host` (including the named host); default ports match their portless URL, userinfo is refused, and malformed entries grant nothing.
- On remote boards, all authorized HTTP(S) origins, public or private, run on the board host through its existing SSH route and identity. A separately managed HTTP SSH master keeps long-lived responses out of the file-read transport. A per-web-view `HostURLMap` assigns an opaque `canvas-kit://p-…/` origin to each exact upstream origin. Relative and root-relative resources keep that origin. Remote HTTP also accepts explicitly bracketed IPv6 allowlist entries. Unknown grants refuse. No DNS lookup or HTTP request for an upstream page runs on the viewer.
- `HostFiles.http` streams GET/HEAD with Python's standard-library HTTP client, bounded 64 KiB reads and blocking stdout. It validates each same-origin redirect before following it; a scheme, host or port change is refused even when both origins are allowlisted, so a document cannot borrow its requesting grant's origin. It disables ambient proxies, and borrows no cookies, credentials or TLS exceptions. Each tile admits at most two HTTP responses; the host's dedicated HTTP queue admits one transfer at a time, independently of descriptor reads and other SSH channels. UTF-8 HTML/CSS transformation is capped at 4 MiB; binary resources stream without a whole-file buffer. Upstream embedding protections still apply. Board-file media uses the descriptor-range path, not this HTTP client.
- `allowNetwork` grants access to HTTP endpoints reachable from the board host, not just files inside its board-file policy. Authorize only trusted endpoints. The file sandbox does not constrain what an allowed server itself serves.
- Resource attributes and stylesheet URL operands are rewritten before loading. The injected helper also routes window `fetch` and dynamic `src`/`href`/`poster` attributes. Script bodies and displayed text are not rewritten. Escaped spellings, protocol-relative URLs, absolute worker requests and browser APIs not routed by the helper can fail closed. This is not a POST, authenticated-session or private WebSocket proxy. Existing public WebSocket exceptions remain viewer-side; fixed rules block private literals and local names, including shared-address `100.64.0.0/10` and benchmarking `198.18.0.0/15`. WebTransport and PeerConnection are disabled through guarded WebKit feature SPI; missing selectors or feature keys deny host grants. The main frame never navigates away and popups are refused. Remote subframes accept only the scheme and inherited-policy `about:` documents, not `data:` or `blob:` documents.
- The only native access is the `canvas` script message handler (`window.webkit.messageHandlers.canvas.postMessage(msg)` → promise). Filesystem, state and rendering messages below remain top-frame-only, strict, and capped at 64 KiB. Each tile runs at most four of those messages with 64 queued; excess work refuses, and page rerender or detach cancels it. The separate strict `network.url` operation may also come from this handler's known grant frames; it only mints an allowlisted HTTP origin and cannot read files or mutate board state.

## Agent prompts and replies

`agent.list`, `agent.prompt`, `agent.wait`, and `agent.read` describe a terminal with one entry shape (`ApiRouter.agentEntry`, schema `Agent`): `tile`, `board`, `root` (that board's root directory), `address`, `name`, `aliases`, `kind`, `protocol`, `sessionId`, `lifecycle`, and agent control's `open`, `focused`, `pid`, `draft`, `model`, `thinking` (`live` in agent.list; "Agent control" below).

A terminal tile keeps a log of the commands its shell finished since easl attached (`TerminalCommandLog`, at most 200, in memory: each OSC 133 D that `TerminalCommandTracker.finished` counts as a shell command). A block is found by its command's line in the terminal's text (Ghostty's text from the top of the scrollback to the cursor, soft-wrapped rows joined): from the input line up, each logged command's line is the last line above the newer one's that ends with it (`TerminalCommandLog.positions`), so repeated commands each keep their own block; the first command not found ends the search (its line was trimmed from the scrollback), except that one clearing the screen (`clear`/`reset` among its words) owns the text from the top. A Hyper-click names the block holding the clicked line when the output below that command's line is the one Ghostty selected; its command, exit and duration then come from the log, however far its prompt row scrolled. `agent.read` `block: -N` reads the lines below its command's line to the next command's line, less the lines a prompt shows above its input line (measured whenever a Hyper-click selects a logged block, none until then); `block: -1` (`"last"`) is Ghostty's selection of the last block while it is on screen above the prompt. In the output of a program still running (Ghostty's selection goes on to the cursor) a Hyper-click mentions the rows around it. `agent.read` `lines` joins the live screen's rows by Ghostty's own wrap flags (`TerminalTile.screenRows`, matched against the end of zmx's history) and the rows above by the guess.

`agent.prompt` refuses (`conflict`, unless `force`) a target whose agent reports a lifecycle while its terminal's foreground program (`TerminalStatus.program`, from the process table) isn't that agent (`PromptTarget.foreignProgram`: none of the program's words, extension dropped, is the agent's `kind`): an editor or a pager would take the text. For tmux it asks the client's own server (`ForegroundProgram.tmuxPane`: its binary, `-L`/`-S` and `TMUX_TMPDIR`, `display-message -c <the client's tty> '#{pane_pid}'`) what the active pane runs, and sends when that is the agent; another program there (vim, the pane's shell) is the conflict, named; when tmux doesn't answer, tmux itself is. Into a shell at its prompt (the session's shell known, nothing in the foreground) a one-line text of printable characters is typed (`ShellTyping`: Ghostty's `text:` action, one write, no bracketed-paste markers) instead of pasted: once, after 12 idle minutes, zsh ran a pasted command as `[200~clear…~`, most likely its line editor taking the paste's leading ESC apart from `[200~` (KEYTIMEOUT). Ghostty writes the start marker in one write and zmx forwards it in order (that session's zmx log shows the tile's client leader throughout), so the split happened past easl; typing leaves no ESC to split. It reads the target's session text (the last 400 lines, `TerminalTail`, each line with its position in the whole text) before it pastes, and keeps it in memory per terminal until the next prompt, the tile's deletion, or an app restart. `agent.read` `since: "prompt"` reads the last 2000 lines and returns them from the first remembered line that now reads differently (`TerminalTail.Tail.boundary(after:)`: a shell's prompt line that got the command, a TUI's input box its reply overwrote), else from where the old text ended. The scrollback's own trimming can move positions; the reply then starts earlier, never later. A terminal whose lifecycle is `unknown` gets no pending-prompt state, so `agent.wait` on it fails at once instead of waiting for a report that never comes. An agent reporting by notification (`NotifyingAgent`) goes `unknown` as the prompt is submitted (`Board.notifyingAgentSubmitted`), and `agent.wait` on it waits for its next notification, past the first-report grace.

`agent.prompt` `mentions` (`HandoffMention`, schema `PromptMention`: `object`, optional `lines` for a code tile, `point` for an image tile) become the `MentionTarget` a Hyper-click on the same place stages: a code tile's lines (its `range` when no lines are given) are `code` at the tile's `pinnedCommit`, with its `symbol` only for its own range; an image tile's point is `image`; anything else is `object`; lines or a point on another type are `invalid_params`. The objects must be on the target terminal's board, and the target must run an integrated agent (`PromptTarget.drains`: it reports a lifecycle, not `via: "notifications"`), else `unavailable`. They are queued (`Board.handOff`, duplicates of a waiting target skipped) before the text is pasted, so the drain of that very prompt finds them, and withdrawn if the paste fails.

The composer sends through the same path (`ApiRouter.composerPrompt`: in process, or `agent.prompt` `composer: true` from a remote board's viewer, Remote boards): the text to each target with every `agent.prompt` check, except that a target `blocked` on a question or approval takes the text as the user's answer (`answer`: past the blocked check only, unlike `force`) and gets no mentions. On ⌘↩ the submitted draft leaves the composer and its tokens' mentions leave the tray at once (`ComposerSend.begin`, `Board.withdraw`; not an undo step) when a target takes them; when none does (every target only gets an answer, or the text is one its integration doesn't drain for) they stay staged, with a notice, and the router refuses mentions with such a text. The skip rules are each integration's own (`PromptTarget.skipsDrain`): Claude Code, Codex and Gemini CLI skip `/…` and `!…` (hook.ts), omp `/…`, `!…` and `$…`, opencode nothing (its shell mode is only the `!` key binding, so pasted `!…` text is a prompt, and a `/command` expands into one). Only prompts that need their own drain are queued, before the text goes in (`Board.queueComposerPrompt`, `Board.composerPrompts`, per terminal in send order, in memory): a prompt with mentions, with its own copies of them (ids of their own), and an answer to Codex, which submits the answer to a question it queued as a prompt (`PromptTarget.answersAsPrompt`). A prompt without tokens, an answer a dialog takes (Claude Code's, omp's, opencode's, Codex's approvals aside) and a text its integration skips queue nothing and drain as any prompt does (omp's continue shortcuts `c` and `.` among them). **Drain semantics** (`Board.drain`, `tray.drain` `prompt`): an integration's submission drain passes the text it is about to submit (the hooks' `UserPromptSubmit`/`BeforeAgent` `prompt`, omp's `input` text, opencode's non-synthetic text parts). Both texts are compared folded (`ComposerPrompt.fold`: Unicode alphanumerics (letters, numbers and combining marks), case-folded; comparisons respect canonical grapheme boundaries), so what agents do to a prompt drops out (Claude Code's `<pasted_content>` wrapper, Codex's IDE context, omp's `:)` → 🙂, text already in the input editor ahead of the paste). The drain claims the oldest queued prompt of its caller whose folded text it contains (equals, for a folded text under `ComposerPrompt.shortest`, 3 characters): it returns that prompt's mentions numbered from 1 in a block without a header, never the tray (whether or not the caller is the prompt target), followed by what agents handed the caller (`agent.prompt` `mentions`); a prompt with mentions stays queued until `tray.commit` names them (a peek takes nothing), an answer is taken by the claiming drain. A prompt typed in the terminal or sent by `agent.prompt` doesn't contain a composer prompt's text, so its drain claims nothing, whatever is waiting ahead of it. A submission drain that claims nothing while prompts wait logs one line with lengths only, and takes the tray; so does every drain without `prompt` (Hyper-V, scripts, the CLI, an older integration), which never touches the queue. So `[n]` in each target's text is the n-th token for that target, whatever is staged, retargeted or sent meanwhile. A Codex answer the claiming drain didn't take (an approval Codex takes in its dialog) goes `ComposerPrompt.answerGrace` (2 s) after Codex reports `working` or `idle` while no longer `blocked`. Queued prompts leave undelivered when the terminal's agent is released (`agent.release`, `Board.releaseAgent`), its shell is back at the prompt (`Board.terminalProgram` nil), the terminal is deleted, or at the safety cap `ComposerPrompt.lifetime` (2 h; checked on queue and claim and every minute by the window, `Board.expireComposerPrompts`): their mentions are staged again (`Board.onComposerMentionsReturned`, which the composer announces). omp's extension stages what each submission drained and commits it as `before_agent_start` hands the context back, which omp also runs for prompts it takes mid-turn (steering) without an `agent_start`; a prompt omp never prepares stays uncommitted. A prompt the terminal never took (`submitToTerminal` false) is withdrawn. When every delivery has a definite outcome (`ComposerSend.settle`): if the text reached no terminal, the submitted draft comes back ahead of what the user typed meanwhile, its tokens staged again; if it reached terminals but none that took the mentions (only an answer went in), the tokens come back the same way. An uncertain remote delivery stays held and visibly checking until its submission receipt reconciles (Prompt submission receipts, above), without blocking other targets or the next draft. While a draft is on its way it is kept in the composer state's `outgoing` until a terminal takes its text; one left there when the app quit is quarantined with a delivery-unknown notice on the next launch, never recovered as an unsent draft. A target without an integration gets `Board.context(for:caller:)`, the same block numbered from 1, pasted ahead of the text. A drained composer mention counts as delivered (`Board.delivered`). Known gap: a typed prompt that contains a waiting composer prompt's whole folded text (the same words resent by hand) claims it.

`agent.report` `final` (only with `idle`) is the final assistant message of the turn that just ended: omp's extension takes the text parts of the last assistant message in `agent_end`'s `messages` (when it doesn't continue), the hooks take `last_assistant_message` from `Stop` (Codex, Claude Code) or `prompt_response` from Gemini CLI's `AfterAgent`; opencode sends none. `Board.finalAnswers` keeps it per terminal until the next turn starts (lifecycle to `working` from idle, done, or no state) or the tile is deleted, saved with the board (`finalAnswers`, `turnErrors`, and the staleness rule's `lifecycleSeq` in the board file; `board.export` leaves them out), so a user returning after a relaunch can still read it; stale-`seq` reports are dropped with their answer. `agent.read` `final: true` returns it as `text` (with `lines`), and fails with `unavailable` while an `agent.prompt` to the terminal hasn't started, while it is `working` or `blocked`, and when no answer is kept.

After `agent.prompt` to an agent that reports a lifecycle and isn't mid-turn, `agent.wait` ignores the state from before the prompt until the agent reports `working` or `blocked` (or exits); a prompt that starts no turn within `ApiRouter.promptStartGrace` (60 s; a `/` command or `!` escape, which the hooks don't report, or text the agent didn't take as a prompt) fails the wait with `unavailable` instead of holding it forever. A prompt that lands while its agent is `working` (`agent.prompt`, the state as the text went in) joins that turn: the router doesn't wait for a `working` that may never come, and `agent.wait` answers when that turn ends, `final` being that turn's answer. That is what both integrated agents that take a prompt mid-turn do. omp takes typed text as a steering message (follow-ups likewise) and its agent loop runs it before the run ends: one `agent_end`, and when a queued message starts a new run right after, its `agent_start` comes within the extension's 250 ms idle debounce, so no idle is reported in between. Codex 0.155 queues it ("Messages to be submitted after next tool call") and submits it after its next tool call, or right after its answer when no tool call comes, firing `UserPromptSubmit` (`working`) then, within the same turn: one `Stop`, whose `last_assistant_message` answers the latest prompt (checked with its hooks, 2026-09-27). A prompt to an agent that is `idle`, `done`, or `blocked` (forced) still waits for the agent's next `working` or `blocked` before its turn can end.

`agent.report` `error` (only with `idle`) says the turn ended on an error instead of finishing: omp's extension sends the last assistant message's `errorMessage` when its `stopReason` is `error` ("Anthropic stream error (overloaded_error)"), `interrupted` for `aborted`, and `stopped at the output token limit` for `length`, beside whatever `final` text it got. `Board.turnErrors` keeps it with the answer (cleared together); the lifecycle stays `idle` with it as the message (never `done`) and as `error` (schema `Lifecycle.error`, so every agent entry, agent.list's included, says the last turn failed without parsing the message), `agent.read` `final: true` adds `cutOff` (the error) to a text that is the answer as far as it got, and with no text fails `unavailable` naming the error. That lifecycle stays until a turn starts (`working`, which clears `turnErrors` too): a report that starts no turn (an `idle` without `error`, an `unknown`) leaves it, its message kept when the report has none, and so does agent.restart (Agent control, "A failed turn through a restart"). Seeing the tile doesn't clear it: it isn't an answer to read but why the agent stopped. Before agent.restart kept it, omp's own re-reports were what kept it shown (its extension sends the failure with every `idle` until its next turn), and a relaunched omp has none to send: its plain `idle` showed a lead that had died on an API 400 as a healthy idle agent for three days.

### Agent addresses

A terminal is addressed as `name@board`, never by host (`AgentAddress`; the `target` of agent.prompt, agent.wait and agent.read, and omp's `write agent://…`):

- `name` is the terminal's `props.name`. A name only needs to be unique within its board: two boards can each have a `reviewer`.
- `board` is the board's name: the name of its root folder (`basename` of `root`, as the window title shows it: `canvas`, `lindy`; a repository board's root is its main checkout, so its worktrees share it), or its id `brd_…`. Only open boards are looked up, and only one whose root folder still exists by name (an archived board, its folder gone, by its id alone).
- A tile id `obj_…` is an address too, on any open board; it is the `address` of a terminal without a name.
- A bare `name` is looked up on the caller's board first (`caller`, the terminal asking), then on every open board. On each board a current name wins over an alias there, and matches on more than one board are `ambiguous` (an alias on one board and a current name on another included).
- A terminal's `address` (its agent entry's, a message sender's `from.address`, a bounce's) reaches it alone among the open boards: `name@board` while the name is no other terminal's on its board and its board is the only open board found by that folder name; `name@brd_…` when the folder name is shared with another open board or the folder is gone; its tile id when it has no name or shares it on its board.
- Renaming a terminal keeps its old names as aliases (`Board.aliases`, alias → tile, saved in the board file as `aliases`) until another terminal on that board takes the name (is created or renamed with it); deleting the terminal drops them. A tile moved, resized, restarted or resumed keeps its id, so its address and aliases stay.
- Errors: no match is `not_found` ("no terminal tile named or with id X", or "no open board named B", naming the open boards); more than one match is `ambiguous`, listing each candidate as its address and tile (`name@board (obj_…)`), so the caller can name one.
- A sender is identified by its tile id (`caller`), never by environment variables; its name and address are resolved when its message is delivered, so a sender renamed meanwhile shows its new name.
- Cross-host addresses (`name@board@host`, a board on another Mac or on an offload host) are out of scope for now: a remote board's agents are reached through that host's own socket (docs/design/next.md, Remote boards).

### Peer messages

`agent.prompt` to a terminal whose integration takes messages goes out of band: it never types into the terminal, so the user's half-typed draft, an open question and an approval dialog stay as they are. Everything else still types: a terminal without such an integration, and the composer (the user's own text, `ApiRouter.composerPrompt`).

- **Capability.** Every `agent.report` says the integration's `protocol` (an integer, kept as `props.agent.protocol`, shown as `Agent.protocol`; a report without it sets 0, `agent.release` clears it, and so does the integration dying, below). `protocol` ≥ 1 means the integration takes messages through `agent.inbox`. omp's extension reports 1; the Claude Code, Codex, Gemini CLI and opencode integrations report none yet and are typed into.
- **The queue** (`Board.messages`, per terminal, oldest first, saved in the board file as `messages` and left out of `board.export`): `agent.prompt` refreshes the terminal's foreground program (a killed integration is found before anything is queued), checks the target (mentions as typing checks them, `HandoffMention`), records the terminal's tail for `since: "prompt"`, and queues `AgentMessage {id msg_…, text, from, label, when, mentions, queuedAt}` for the agent session there. None of typing's refusals apply (`blocked`, a restored `working`, another foreground program): nothing reaches the screen. The result says `delivery: "message"` and the message's id. A session that ends while the message is being sent (the terminal's text is read first; `Board.agentSession` moves on) gets nothing, and the call fails `unavailable`. Messages leave when the integration acks them, an app restart keeps them, and when their session ends first they bounce.
- **Session ends and bounces** (`Board.endAgentSession`): the agent session a message was queued for ends at `agent.release`; at its integration dying (an `idle` or `done` agent whose integration took messages, its shell back at the prompt with no release, as after a SIGKILL: `props.agent.protocol` goes, its state and answer stay, and `agent.prompt`, typed or not, and `agent.wait` fail `unavailable` until an agent reports there again); at a report of another agent kind, or without `protocol`; at `agent.report_session` with another session id; at `agent.restart`, which kills it (Agent control, below); and at the terminal's deletion, once the step that deleted it closes with it still gone (a failed `object.batch` puts back the deleted terminal's queue and aliases, and the mentions it stripped). What was still queued bounces, never dropped silently: back to a sending terminal whose integration takes messages, as a message from `easl` on the user's behalf (`undelivered to <the receiver's address>: <its first line, cut at 80 characters>…`); a script's, or one whose sender takes no messages or has closed, into the receiver's board.history as a `message` entry (the receiver's id, the same text and `(from <sender>)`). A waiting `agent.wait` on the receiver looks again.
- **Delivery** (`agent.inbox`, the integration's own terminal as `tile`): a long poll (`waitMs`, ≤ 60 s) answers the messages waiting that no open connection holds, each sender's name and address and each message's mentions resolved at that moment (the `context` block is the hand-off block a drain gives, `Board.resolveHandoffs`'s: "Attached by terminal obj_… "name" to its prompt to you (agent.prompt):", or "by a script"). The answering connection holds them until it acks them (`ack`) or closes, when they are offered again, so an integration that restarts or loses its connection mid-reply loses nothing. An integration acks a message once its agent has recorded it, never before, and dedupes by id. `ack` with `started: true` says the delivery started a new turn (the agent was idle), `false` that it joined the running one.
- **omp** (`extensions/omp/easl.ts`): one long poll per tile's root session (subagents have none); messages arriving within 250 ms of each other are delivered as one card: `pi.sendMessage` of easl's own custom message (`customType: "easl:message"`, `display: true`; not omp's `irc:incoming`, which omp's `wait` returns from its queue as a bare text result and whose leftover at a run's end wakes the agent even after Esc). The extension draws it as omp draws its own incoming IRC messages (`pi.registerMessageRenderer`: `💬 IRC ← reviewer@canvas` and its age over the quoted text, three lines until unfolded), and omp's session history and retros print it as `[easl:message] <irc> Message from …`, apart from the user's prompts. A burst is one card, so it is steered, starts a turn and is recorded as a whole. Its `details`: `id` (the message's, a burst's first), `from` (the sender's address, a script's label or a closed terminal's tile id; a burst's senders joined), `message` (the text as written; a burst's joined) and `ids` (every message it carries). Its content, what the model reads, puts each message in an `<irc>` envelope like omp's: who sent it, its text with its mentions' block after it (the `<` of an `irc`, `system-*` or `easl-guidance` tag in them escaped, as omp's `escapeHarnessTags` does for its own), how to reply (`write` with `path: "agent://reviewer@canvas"`, the name and board percent-encoded; a script, or a terminal closed since it sent: no reply address), and `(easl message msg_…)`. `attribution` is the message's (a script's in a burst makes the card the user's); omp keeps it on the card. `when: "now"`: `steer` (`deliverAs: "steer"`) while the agent streams (injected at its next step; an interruptible tool such as `wait` is cut short, a question or approval waits for its answer and the message comes after it); while it streams nothing (idle, or a turn awaiting background work) the card starts a turn (`triggerTurn`). `when: "next-turn"`: held until the running turn ends (`agent_end` without `willContinue`), then a new turn; never a steer. Each sender (tile id, or a script's label) wakes the receiver at most 20 times an hour: past that its messages join the step omp is streaming as an aside (`deliverAs: "aside"`), and while nothing streams (idle, or a turn awaiting background work) wait for the next `agent_start`. A card left in omp's queue when a run ends wakes a turn, unless the user stopped the run (Esc), as a user message's did. omp starts a turn with a card without preparing it (no `before_agent_start`), on the system prompt the last prepared turn left: none of easl's guidance in a session the user never prompted, or standing orders since changed. So every card's id is marked, and until omp next prepares a turn (a prompt of the user's, or a script's queued card, which omp prepares as one), each request of a turn omp didn't prepare gets, through omp's `context` event, an `<easl-guidance>` block just before the first marked card (first, when compaction dropped it), never recorded: the easl guidance and the board's standing orders as they are now (read once a turn), saying they supersede any in the system prompt, or that the board has none now and any in the system prompt no longer apply (nothing about them when easl doesn't answer). The standing orders a prepared system prompt carries defer to that block (Board standing orders, below). A card that starts a run (omp streaming nothing) ends whatever omp prepared before: a turn paused for background work, or a preparation the user cancelled with Esc. A message is acked once omp records it: the card's `message_end` (its `ids`), or a user message carrying its `(easl message msg_…)` line (omp puts a queued user-attributed card, a script's or a burst with one, back in the editor as its text on Esc or Alt+Up, and the user sent it). Only the messages it carries are acked: one the user deleted from a restored burst is not, and goes in again as below. Its id is saved in the session (`easl.messages` entries), so a restarted omp offered it again acks it instead of delivering it twice. One omp hasn't recorded 5 s after it was handed over, with nothing streaming or queued (omp couldn't start the turn: no model; or the user dropped it from the editor), waits for the next turn that starts and the user is told (`ctx.ui.notify`); easl keeps it meanwhile. Polls and acks share the inbox connection, which any failed or timed-out call closes, so easl offers what it held again; a burst whose follow-up fetch fails still delivers what came. On a session switch, messages arriving before easl has the new session's report are the old session's (easl bounces them) and are not delivered.
- **Attribution.** A message with a `caller` and no `from` is the agent's (`attribution: "agent"`, the sender its terminal). With `from` (a script's label: `easl tell reviewer "…" --from machine-watch`, roblox's launchd tick) or without a caller it is the user's (`attribution: "user"`), named by `from` (default `script`), with no reply address.
- **agent.wait and agent.read final keep their meaning**: while a message to the terminal is queued or held, `agent.wait` doesn't answer and `final` is `unavailable`; an ack with `started` starts the prompt grace as a typed prompt to an idle agent does (the turn must start within 60 s); an ack that joined the running turn answers when that turn ends. A typed `next-turn` prompt to a `working` target (no message integration) is `conflict`: typed text would join the turn.
- **The sender's message id** (`agent.prompt` `message`: `msg_` and 8 to 64 letters, digits, `_` or `-`, the schema's `MessageId`, which easl's own `msg_…` ids fit too): the id the message gets, the same on every attempt to send it, so a sender whose call timed out sends again without the receiver getting it twice (a hosted terminal's text is read over ssh before the message is queued, which can outlast a short timeout). With that id already queued for the terminal, `agent.prompt` answers with that message (`duplicate: true`, its own `submittedAt`) and queues nothing. The app looks before it reads the terminal's text and again just before it queues, so an attempt arriving while the first still reads finds it either way; easld queues with nothing awaited. One id sent to several terminals is a message to each: each is held by the connection that took it and acked or bounced apart (holds go by terminal and id). Once delivered, the receiving integration drops an id it recorded (omp's `easl.messages` entries). Typing ignores it.
- **Unknown agents in omp.** omp's native `write agent://<name>` knows only its own process's agents. When it fails with "Unknown agent", the extension resolves `<name>` (or `name@board`) through easl (`agent.prompt` with the session's tile as `caller`, on its own connection with a 20 s timeout: a hosted terminal's ssh read took up to 10 s) and patches the tool result to the delivery: `isError: false`, content naming the address, and `details.message.receipts` outcome `injected`, so omp's IRC card shows it delivered. A failed lookup keeps omp's error and adds easl's. Every attempt at one write sends one message id (`messages.ts` `writeMessageId`): omp runs a tool's `tool_result` handlers in turn, each seeing what the last left, so a failed attempt leaves its id in `details.easl.message`, and a handler after it (dotfiles' omp-inbox, which sends through `easl tell`) sends it again with that id, which easl queues once. Without it, a timed-out prompt that easl still queued went out a second time with a new id. A server from before message ids (easld or a remote host on an older release) refuses the param (`invalid_params`, "unknown param message; …") before it queues anything: on that refusal alone the extension sends again without the id; after a timeout or any other failure it doesn't.
- **CLI**: `easl agent.prompt --target <name>[@board] --text <t> [--from <label>] [--when next-turn] [--message <msg_id>]`, and its sugar `easl tell <name>[@board] <text> [--when next-turn] [--from <label>] [--message <msg_id>]`. Inside a terminal the CLI still sends `caller` (EASL_TILE_ID), which puts that board first for a bare name; with `--from` the message is the script's all the same.

### Agent control

What a supervisor (the machine shepherd, a board's chief of staff) needs to see and steer every agent, closed boards included (`Sources/CanvasCore/AgentControl.swift`).

- **agent.list, per agent**: `open` (its board is open), `focused` (`TerminalStatus.focused`: the terminal has keyboard focus in the key window while easl is the active app, `TerminalTile.isWatched`; the user may be typing in it), `draft` (the agent's input editor holds unsent text, `props.agent.draft`), `model` and `thinking` (`props.agent`, from `agent.report_session`), `pid` and `live`. `pid` is the agent's process: the one its integration reported (`agent.report` `pid`, `props.agent.pid`) while that process lives (`kill(pid, 0)`), else the foreground process of the tile's session (`ForegroundProgram.foregroundPid`: the job leader on the shell's terminal, a `-c` shell's child), absent at the shell's prompt or when the session is gone. `live` is whether the tile's zmx session runs: one `zmx list` per call (`ApiRouter.terminalSessions`, `Zmx.sessions`, off the main actor) finds the sessions labelled `canvas.tile=<tile>` with this instance's `canvas.home` (see zmx session names above), each with its `canvas.board` and its shell's foreground process; absent without zmx. A hosted terminal (`props.host`) runs on its host: its `live` is its host's easld's `session.list` (`ApiRouter.hostedSessions`, `TerminalHost.liveSessions`: a session labelled with this instance's `canvas.home`), asked only of a host this app is connected to and absent when it isn't or doesn't answer, never this Mac's zmx; it has no `pid` (its processes are the host's, not this Mac's: neither the app nor easl tests the pid its integration reported on their own machine, where another process may have that number). A remote board's terminals (client mode) are its host's agents: the viewer's agent.list doesn't list them, and its agent.restart doesn't reach them; the host's API does both.
- **Closed boards**: agent.list lists the open boards' terminals (boards by id, terminals by tile id), then those of every stored board that isn't open, read from its board file (`StoredTerminals`, cached per file until its modification date changes, read off the main actor): `open: false`, `focused: false`, the lifecycle as saved with a saved `working` or `blocked` marked `restored: true` (as opening the board marks it), `address` `name@<root folder>`, no title, program or last command. Their agents keep running in their sessions (`live`); what they report while the board is closed is spooled and replayed when it opens (Lifecycle authority). agent.prompt, agent.wait, agent.read and agent.restart reach open boards only.
- **Draft**: every report of omp's extension says `draft`: whether `ctx.ui.getEditorText()` holds anything but whitespace, looked at every 500 ms while its session runs and reported when it flips, so text omp puts there itself (a Ctrl+D draft it restores after `session_start`, the external editor's) counts as much as typed text. A report without `draft` (another integration, an older extension, omp without its TUI) removes it: unknown. omp's extension reports `pid` (`process.pid`) the same way.
- **Model and thinking**: omp's extension sends `model` (`<provider>/<id>` of `ctx.model`, what `omp --model=` takes) and `thinking` (the configured selector, what `omp --thinking=` takes, `auto` kept: `pi.getThinkingLevel()` is the effort auto chose, which as `--thinking` would turn auto off) with `agent.report_session` at session start and switch, and whenever either changes, looked at every 500 ms (`/model` and the thinking toggle fire no extension event), idle or not. The selector is the session branch's last `thinking_level_change` this omp recorded (`configured`, else `thinkingLevel`), else the `--thinking` omp was launched with while the session it launched with is the first the agent runs (process-wide, until a session switch: a session switched to, the launch one too, runs what it recorded), else the branch's last one; none when nothing says (a new session at omp's default before its first turn). Each check reads the branch back from its leaf only to that change or to the leaf it read last time, so checks cost the same however long the session is. The extension counts a report as acknowledged only when easl answers it, and none while one is out (it may apply unanswered); it sends one easl hasn't acknowledged again every 10 s, and again when easl comes back (`watchCanvasReturn`). A report without one keeps the last.
- **Session on disk**: omp's extension sends `sessionPath` (`getSessionFile()`, what `omp --resume=` takes) only once that file exists: before each `agent.report_session` it has omp put the session on disk (`SessionManager.ensureOnDisk`, as omp's ACP `session/new` does; skipped on an omp without it), then reads the session's id and path (writing can move it to a new id and file). A report whose session ended or changed while the file was written (a release may have gone out) isn't sent. omp writes a session lazily, once it has a reply, so the path of a session with no reply yet (just started, or after `/new`) named no file: omp 18.6 resumed it as a fresh session there, and omp 18.8 refuses it (`Session "<path>" not found.`, exit 1), so agent.restart `resume` and a reboot resume of such a tile relaunched nothing.
- **agent.restart** `{target, mode, args?, force?}`: refused (`conflict`) while another restart of the terminal runs or a prompt's paste and Enter are going into it (`ApiRouter.pasting`, a bounded step: even forced, the paste would land in the relaunched agent), and unless `force` while the agent is `working` (restored or not) or `blocked`, has a prompt whose turn hasn't started (`ApiRouter.promptPending`: one being typed, its checks and screen reads included, or one submitted, or a message its integration delivered with `started`, that its agent hasn't reported working on within `promptStartGrace`, what agent.wait waits out), has a message queued that its integration hasn't taken yet (`Board.messages`, which agent.wait waits for too; forced, it bounces), may hold a draft (`draft` true, or absent: an integration that doesn't report it may have one), or its terminal is `focused`, checked in that order. The relaunch (`AgentResume.relaunch`): the tile's `command` options when it runs that agent (`AgentResume.options`: its session selectors and prompt left out, as a reboot's resume leaves them), the recorded model and thinking replacing any the command gave (omp `--model=<m> --thinking=<t>`, omp 18.6.1 `--help`; claude `--model`, codex/gemini/opencode `-m`; only omp reports them today), then `args`. `resume` appends the agent's session selector (omp `--resume=<sessionPath>`, which takes a path or id prefix, else the id; `AgentResume.grammar`'s for the others), `unavailable` without a recorded session; `fresh` leaves it out, and a terminal with no known agent reruns its `command`. From then until the restart ends, however it ends, the terminal is reserved (`ApiRouter.restarting`): `agent.prompt` to it, typed or queued, is `conflict` ("… is restarting (agent.restart) …"), `agent.inbox` offers it nothing, and another restart is `conflict`. A typed prompt is for the agent session it found (`Board.agentSession`): one that ends while it reads the screen (released, replaced, restarted, forced or not: those reads have no deadline, so they don't hold a forced restart off) gets nothing typed, `unavailable`, as a queued message's does. The app (`ApiRouter.restartTerminal`, `TerminalTile.restart`) checks the refusals again just before the kill (`killing`; a turn, prompt, draft or focus that came meanwhile calls it off), kills the zmx session as deleting the tile does (`killArguments`: the owner guard, then zmx's log) and confirms it gone (`endSession`: zmx no longer lists it, within 3 s); a kill that can't run, a session another instance owns, or one zmx still lists (or can't list) is `unavailable`, with nothing relaunched, no session ended and no queue bounced. Once it is gone the killed agent's session ends (`Board.endAgentSession`, through `restartTerminal`'s `ended`) and the tile records the relaunch (`Board.restartedAgent`), both before the relaunch starts, so what the relaunched agent reports from then on stays; a tile closed while its session was killed is `not_found`, with nothing relaunched (its delete ended the agent session). The tile keeps its id, frame and name; its `command` becomes the relaunch without the session selector (a reboot reruns it and resumes the session the new agent records), its lifecycle is cleared (`agent.lifecycle` null) except for an unread `done` (the needs-you badge) or a turn that ended on an error, kept as below (agent.wait gives the new agent 15 s for a first report either way), and `props.agent` keeps kind, protocol, model and thinking (and the session, resumed), taken before the kill, since the old agent's `agent.release` as it exits clears it. Its prompt bookkeeping (`since: "prompt"`, the prompt grace), approval waits and the composer's undrained prompts go with the old agent. Then the surface runs `zmx attach … <shell> -l -c '<argv>; exec <shell> -l'`, which starts a new session: a configuration that differs rebuilds the surface, and one that reads as the old (a second resume of the same session, a plain command rerun) is reattached all the same; the old surface's close within 10 s is ignored (it would otherwise delete the tile as an exited terminal). A hosted terminal is restarted on its host (`TerminalHost.restart`): after the same check its easld ends the session (`session.kill` with this instance's home label), and once its `session.list` no longer lists it (≤ 3 s; else `unavailable`, before `ended`) starts the relaunch (`session.spawn`, `TerminalTile.hostedSpawnParams` with the relaunch as `command`), and the tile's attach loop starts again; `unavailable` while the host is offline, with the session left as it was. A remote board's terminal is never restarted by the viewer (`unsupported`): the host's own easl restarts it, through its API. Peer messages: in either mode what was still queued for the killed agent bounces (Session ends and bounces, above) and none of it reaches the relaunched agent; a restart refused or failed before the kill leaves the queue as it was. easld (`agent.restart` forwarded to a client) checks the call and the refusals itself (focus aside: it has no window), refuses one while it forwards a typed prompt to it (`typing`, even forced: the client's answer is due within its 10 s deadline), then holds the terminal for the restart that owns it (`restarts`) as the app does: `agent.prompt` to it is `conflict`, no inbox poll takes what is queued for it, and another restart is `conflict`; it bounces the queue once the client answered with the relaunch, and offers it again when the client refused or failed. The CLI: `easl agent.restart --target <id> --mode resume|fresh [--args '<json>'] [--force]`.
- **The killed agent's release**: the agent agent.restart kills can release its terminal (`agent.release`, omp's extension as it exits) before the relaunch is recorded, or after: zmx stops listing a session while its agent may still be shutting down. From the kill, after its re-checks pass, until it records the relaunch, a release there waits (`Board.agentRestartBegan`): the relaunch's record replaces it, and a restart that ends without one applies it (`Board.agentRestartEnded`), so the tile shows what it had throughout (no `null` lifecycle comes between; the app's notification for its answer stays). Once the relaunch is recorded, until an agent reports in the relaunched terminal (`agent.report`, `agent.report_session`, or a lifecycle notification), a release there is that one and is ignored (`Board.relaunchedAgents`, saved with the board), so the tile keeps the kind, session, model and thinking it was relaunched with, also when the relaunch never starts (agent.restart `resume` can run again); the relaunched agent's own release, once it has reported, clears the tile as any release does.
- **An unseen answer through a restart**: a tile `done` with `seen` false (the needs-you badge) as the relaunch is recorded stays so, an exception to the lifecycle the restart clears (`Board.restartedAgent`; easld's restart of an owned terminal likewise, `Board.RestartedAgent`); a tile the user saw meanwhile (`seenSinceWorking`) restarts without it. The relaunched agent's reports that start no turn leave it: an `idle` from `done` stays `done`, and so does an `unknown` (an agent without an integration starting, `bin/aider`), its message kept when the report has none; the user seeing the tile, or the relaunched agent's `working`, ends it as without a restart. A `blocked` report replaces it with the current turn's question, as without a restart. Until the relaunched agent first reports (`Board.relaunchedAgents`), agent.wait waits for that report as for a tile with no lifecycle, whatever the tile shows meanwhile (the kept `done`, or the `idle` the user's look made of it) and however its agent reports (by notification too), and fails once `firstReportGrace` passes without one (`Board.awaitsRelaunchedAgent`); the relaunched agent's `agent.report_session` counts and wakes waits already pending, as does a lifecycle notification, even one repeating the kept answer. A board saved and opened again still knows the relaunch is pending.
- **A failed turn through a restart**: a tile whose last turn ended on an error (`idle` with lifecycle `error`, agent.report `error`) as the relaunch is recorded keeps that lifecycle, seen or not (`Board.isFailedTurn`; easld's `failedTurn`): the error, not the restart, is why the agent stopped, and the relaunched agent has no failure of its own to report again. Its reports that start no turn leave it (an `idle` without `error`, an `unknown`; its message kept when the report has none), so agent.list, agent.wait and agent.restart's result keep saying `error` and the tile its message; the relaunched agent's `working` ends it, with `Board.turnErrors`, as without a restart. A `blocked` report replaces it, as it replaces a kept `done`. agent.restart doesn't refuse such a tile: an unattended caller that shouldn't restart it reads `lifecycle.error` first.
- **Spawn**: `easl agent spawn --name <n> --cwd <dir> --command '<argv>' [--board <id>] [--prompt <text>] [--wait] [--timeout <ms>]` (cli/easl.ts) is `object.create` of a terminal (`command` a JSON array or shell-like words), then with `--prompt` `agent.wait` until the agent reports `idle` (retrying the first-report `unavailable` until the timeout, default 120 s) and `agent.prompt`; `--wait` waits for that prompt's turn too (without `--prompt`, until the agent is ready).
- **Board standing orders**: each turn omp's extension reads its own board's note keyed `rules` (`object.find {board: EASL_BOARD_ID, key: "rules"}`, one call in `before_agent_start`, so an edit reaches the next turn) and appends its markdown to the system prompt after the easl guidance (`extensions/guidance.ts`), headed as the board's standing orders as of that prompt, which a later `<easl-guidance>` block giving the board's standing orders, or saying it has none, supersedes. A turn an easl message starts, which omp doesn't prepare and which keeps the last prepared system prompt, gets such a block (Peer messages). Nothing when there is no such note, it isn't a note, it's empty, or easl doesn't answer (the client's 1.5 s timeout). More than 8 KB (UTF-8) is cut at a character boundary with a notice saying so and how big the note is.

## Lifecycle authority

- The omp extension is authoritative for omp tiles (`source: "canvas-omp"`). It reports `blocked` while omp waits on its user: an approval dialog (`approve <tool>?`) or the `ask` tool (its first question). omp's `tool_approval_requested` event comes only from its registered-tool wrapper; eval preludes (the `browser` and `computer` globals inside `eval`) ask for approval with no event, so the extension wraps `select` on the session's UI context (the object behind `ctx.ui`, which tools and preludes prompt with) and treats each dialog titled `Allow tool: <name>` as an approval until it settles. It depends on that title; an omp that renames it reports no approval blocking.
- omp's extension releases its tile (`agent.release`) at `session_shutdown` unless omp got SIGHUP or SIGTERM first: killing the terminal's session (a reboot, zmx or easld stopped) hangs omp up, and a system shutdown sends SIGTERM; omp's teardown then fires the same `session_shutdown` as `/exit` (omp 18.6 and 18.8: postmortem's signal listener starts the teardown, which awaits the draft's save before the event, so the extension's own listener, added as the tile's session starts and removed at its shutdown, has run by then). Nothing is sent or spooled: the tile keeps `props.agent`, its next session resumes it, and what easl queued for it stays queued. The listener changes nothing of omp's handling or exit code. `/exit` (no signal) releases.
- The Claude Code, Codex and Gemini CLI hooks and the opencode plugin ("Agent integrations") report with `source: "canvas-claude"` / `"canvas-codex"` / `"canvas-gemini"` / `"canvas-opencode"`.
- A report with a lower `seq` than the last accepted one from the same source is ignored, across restarts too (`lifecycleSeq` is saved with the board).
- The terminals waiting for agent.restart's relaunched agent to report are saved too (`relaunchedAgents`): reopening the board neither takes the killed agent's answer as the relaunched one's nor applies its late release. The next lifecycle or session report, or a lifecycle notification, clears that wait.
- Agent report spool: a lifecycle report an integration can't deliver (`unavailable`: no socket, the app quitting or restarting; `timeout`) is written by `extensions/agent-hooks/report.ts`, which the omp extension, the hooks and the opencode plugin share, to `agent-reports/<tileId>/<seq>-<pid>-<random>.json` beside the socket (`dirname $EASL_SOCKET`), as `{seq, method: "agent.report" | "agent.release", params}`, under a hidden name and then renamed; writing never throws or blocks the agent. When the app opens a board (`BoardRegistry.open`, so at launch for the boards it reopens) it reads its terminals' spools off the main actor, applies them oldest `seq` first as if they had arrived (`Board.replay`: `agent.report` through the staleness rule; `agent.release` only when no report from the same source is newer), and deletes them. A spooled file it can't read (permissions, IO) stays for the next open; one that reads but isn't a report is deleted. So an agent that finished while easl was closed comes back `done` (unseen: ⌘J, the tab dot, a notification) with its `final`, and a report applied before the quit is dropped as stale. A report easl answered with an error is not spooled. Deleting a terminal for good deletes its spool.
- A restored `working` or `blocked` is the agent's last word until it says more (the spool, its next report). The app marks it `restored: true` as it loads the board file (`Board(snapshot:)`), and the agent's next report, live or replayed, writes a lifecycle without it: until then `agent.list` and `agent.wait` show what the agent was, not what it is (an omp extension loaded before the spool existed drops what it says while easl is closed). `agent.prompt` refuses a restored `working` (`conflict`, unless `force`): the agent may now sit in a question or approval, which the pasted text's Return would answer. Integrations that live as long as their agent say it again when easl comes back (`watchCanvasReturn` in `extensions/agent-hooks/report.ts`: a new socket file at `EASL_SOCKET`, checked every 2 s): the omp extension re-reports its current state and the opencode plugin its last report, so a restored state lasts seconds after a restart; the Claude Code, Codex and Gemini CLI hooks run per event and report again at the agent's next one (a finished tool call reports `working`). A restored `blocked` is refused like any `blocked`. An integrated agent claimed `working` or `blocked` while its terminal's foreground is the shell at its prompt (`Board.terminalProgram`, from the process table: killed, or exited while easl was away without its release) is released like an exited notifying agent: lifecycle `unknown`, `agent.wait` fails instead of hanging. An agent still running whose integration stopped reporting keeps its last state until it reports again or the next prompt.
- `done` is derived by the app: an `idle` report on a tile that has not been seen since it was last `working`. Seeing counts only once the turn has ended (`Board.markSeen` ignores a `working` or `blocked` tile): a turn that ends after the user looked away is `done` until they look again (the tile on screen for 3 s, the keyboard in it, or ⌘J there).
- An agent without an integration reports by terminal notification (`NotifyingAgent`, `Board.terminalNotified`): an OSC 9 or OSC 777 `notify`, or a bell, from a terminal whose foreground program isn't its shell and whose lifecycle no integration reports sets `lifecycle` `{state: done, message: <the notification>, seen: false, via: "notifications"}` (`idle`, `seen: true` while the user looks at the terminal) and `agent.kind` to the program's first word (`aider`). A bell within 1 s of a key the user typed in that terminal (`NotifyingAgent.bellAfterKey`: vim at Esc, less at the end) is no such signal, and at the shell's prompt a notification or bell raises an attention marker instead. Return typed into the terminal, or an `agent.prompt` to it, sets `unknown` (a notification comes only when the agent waits after model work, so Return can't mean `working`); it never reports `working` or `blocked`. `agent.report` `unknown` (`bin/aider` as aider starts) sets `via: "notifications"` too, so the tile is an agent before its first notification. The shell back at its prompt (`Board.terminalProgram`) releases it (`agent.release`'s effect); a program it runs meanwhile (its editor) doesn't. Its tile gets no attention markers from its notifications (the dot says it), and its shell's command marks stay the user's (`NotifyingAgent.integrationReports` is false).

## Questions

A question (`type: question`, schema `QuestionProps`; `QuestionSpec` and the `Board` extension in `Sources/CanvasCore/Question.swift`, `QuestionTile` in the app) is how an agent asks the user for a decision on the board. Status runs open → answered | cancelled | expired, each final. **Archive is not a status**: `archived: true` on a closed question hides its tile through `CanvasObject.isHidden`. Selection, navigation, layout, and rendering skip its geometry, as specified in the [archived geometry audit](#archived-geometry-audit). The object, its stored frame, and its answer stay readable through `object.get`, `object.find`, and `board.get`. An open question cannot be archived.

Closed question tiles archive automatically after 10 seconds. `keep: true` disables automatic archiving for that question, including after a host restart. `archiveAfter` changes its delay in seconds, from 0 through 86400. Both props can change after closure. Null removes either override. `easl ask --keep` sets `keep`; `easl ask --json` accepts `archiveAfter`. `easl ask get <id>` and `easl ask list` still return archived questions with their status and answer. `easl ask list --open` returns only open questions.

The host can set a default for new questions. On the Mac, `questionArchiveAfter` in `<EASL_HOME>/ui-settings.json` sets the startup default. easld takes `--question-archive-after <seconds>`. Both default to 10 and accept finite values from 0 through 86400. A missing or invalid Mac value falls back to 10; easld refuses an invalid flag. Restart the host after changing its setting. An explicit per-question `archiveAfter` wins. When a create omits it or gives null and the host default is not 10, the host stores that default in the new question's `archiveAfter`. Existing questions retain their stored delay or the implicit 10 seconds. Changing other Mac settings preserves this field.

- **Validation** (`QuestionSpec.problem`, run by `object.create`/`update`/`upsert` and their batch ops before the write and before the `rev` check): the rules in order, first failure as `invalid_params`: a closed question takes only `archived`, `keep`, `archiveAfter`, `key`, and `zoom`; `question` non-empty; `options` an array of `{id, label, why?}` (no other keys, ids unique, labels non-empty; it may be empty: the answer is then a note); `recommended` an option id; `context` items exactly one of `{object: Id}`, `{url}`, `{path, lines?}`; `asker` `{tile?, name?, host?}` with a tile or a name (absent on create: `{tile: caller}`, else `invalid_params`); `status` one of the four, `open` on create (written when absent); `expiresAt` RFC 3339; `answer` with `{option?, note?}` (an option id and/or a non-empty note) exactly when answered; `archived` a boolean, true only when closed; `keep` a boolean; `archiveAfter` a finite number from 0 through 86400. easld applies the same rules with the same messages (the `questions` conformance scenario). Before them, a relative `context` path from a caller terminal working in another worktree of the board's repository becomes absolute in that checkout (`Board.inCallersCheckout`, as a code tile's `path`), so the mention and the tile's link name the asker's file, not the board root's; from the board's own checkout, or without a caller, paths are stored as given.
- **Writes**: answering stamps `answer.at` (UTC, whole seconds) and `answer.by` (the caller's `Actor`; the user from the tile); closing without a `frame` in the call shrinks the frame to `QuestionSpec.size` (148 pt, + 40 with a note, at its zoom) in the same write. A frame-less create is sized by the props: 460 × (194 + 50 per option, + 30 with context). The tile's text scales with the chrome text size; content taller than the frame scrolls.
- **The question's text** is plain text, drawn as written; the tile, open or closed, makes links of the http(s) URLs in it as `WebLink.matches` finds them in prose (host and port kept, `http://twaldin-home:5199/home?studio`; trailing sentence punctuation and an unmatched closing bracket left out). A click on one opens it as a context `url` opens (`Board.openLink`: a browser tile beside the question, or the one already showing it); a drag over the text selects it, from a link too, to any caret a text view would place (inside a ligature, never inside a composed character), highlighted in the system's selected-text colors, and ⌘C or the context menu's Copy copies the selection (`TextPress`, `PaintedText`).
- **Delivery** (`Board.questionWritten`, from `Board.write` and `restore`): a question going open → answered whose `asker.tile` is a terminal on its board is handed to that terminal (`Board.handOff`, header `Your question <id> was answered (easl ask):`), so its integration's next `tray.drain` carries an object mention of the question, its options and the answer (`QuestionSpec.mentionLines`); nothing is typed into the terminal. That hand-off waits only while the question is answered and not yet drained: undoing the answer takes it back, a redo that restores the answer hands it off again (drained before or not), a failed `object.batch` (`Board.atomically`) puts every hand-off back as it was before the batch, and a drain drops one whose question is no longer answered or gone (`Board.handoffStands`). Every subscriber gets `object.updated`; `easl ask --wait` and `easl ask wait <id>` wait on it (exit 0 with the answer JSON; 2 when cancelled, expired or deleted; `ask wait` on an id `object.get` answers `not_found` for is the deleted outcome). No hook command is stored in a question.
- **Host lifecycle**: one timer per board covers the earliest open `expiresAt` and the earliest closed archive deadline, at most a day out before re-checking. Opening the board and committing a question reschedule it. Due expiry and archive writes run on the next turn, never inside the request that made them due. They create no undo step, record system activity, and broadcast `object.updated`. Remote viewers only apply the host's updates.
- **Archive timing**: a closed question's deadline is its `updatedAt` plus `archiveAfter`, or 10 seconds without an override. A successful write or undo restore restarts its grace period. Open, kept, and already archived questions have no archive deadline. Explicit archiving still works for a kept question. To restore a closed tile indefinitely, update it with `{archived: false, keep: true}`.
- **Load cleanup**: before constructing a live board, the host archives saved closed questions whose deadlines have passed. It saves only a changed snapshot, preserving board revision, object revisions, timestamps, status, and answer, without adding an undo step. Recent closed questions retain their remaining delay. Kept questions remain visible.
- **Needs you**: an open question not past `expiresAt` is a `NeedsYouItem` with reason `.question`, after blocked terminals and before markers, so ⌘J (which gives it the keyboard: 1–9 pick, Return answers, Tab to the note, Esc back) and Go to's flagged rows visit it; `AsksChip` beside the drawing toolbar counts `Board.waitingQuestions` and goes to the next on a click. `object.find` with `type` (and `status`) lists them, oldest first.

## Ownership rules for slices

- The schema file is the only place API shape changes. Changing it means regenerating clients (`bun scripts/gen-clients.ts`) in the same change.
- Swift model types mirror the schema; a slice that needs a new field adds it to the schema first.
- No slice introduces a new socket, environment variable, or on-disk location without adding it here.
